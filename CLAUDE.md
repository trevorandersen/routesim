# RouteSim

Interactive network topology simulator. Canvas-based editor with discrete frame-level ping simulation, animated hop-by-hop forwarding, and per-device CLI terminals.

## Goals & principles

RouteSim is a teaching tool: it makes the invisible parts of a network visible by simulating real Ethernet frames (ARP, ICMP, DHCP, DNS, TCP) and watching them hop through switches and routers. Design decisions follow from a few principles. The first three are about the **learner** — they're what make this a *teaching* tool rather than an emulator, and they take precedence when they pull against the engineering principles below:

- **Explain, don't just show.** Making behaviour *visible* is the floor, not the ceiling — the tool's highest leverage is showing *why*. Every visible outcome (a delivered ping, a dropped frame, a chosen route, a NAT rewrite) should be traceable to a plain-language reason, not just rendered. A new protocol isn't done when it works; it's done when a learner can see why it did what it did. The `logStep` reason strings, the frame inspector, and the sim log are the substrate — compose them into explanations, don't bury the causality.
- **Failure is a lesson.** A broken network must diagnose itself, never fail silently. Every drop, timeout, refusal, or unmet goal-check states *why* in terms a learner can act on (`No route to X — dropping`, `Cannot reply — no default gateway`, a lossy-link note) — the difference between a tool that grades ("ping failed") and one that teaches ("PC-A's gateway is unset, so it never ARPs off-subnet"). When adding a way for a network to fail, add the diagnosis in the same change.
- **Perceivable by everyone.** "Make the invisible visible" has to hold for every learner. The tool leans heavily on **colour** to convey meaning (per-protocol packet/transit colours, red for errors), which silently excludes colour-blind learners — so meaning must never be carried by colour *alone*: pair it with a glyph, shape, label, or text. Concretely, every packet's category carries a **monochrome glyph** alongside its colour (`frameGlyph`/`toneGlyph` in frame.ts — a per-protocol letter, `✕` for an error), shown in the packet list next to the protocol name and drawn in the canvas transit dot; the dots also keep their text label. When you add a colour-coded signal, add its non-colour partner in the same change. Accessibility (keyboard reach, ARIA, contrast, redundant encoding) is a first-class goal, not a Reach-list afterthought.
- **Zero-install, single file.** The whole app builds to one portable `rs-web.html` that runs offline by opening it in a browser with **zero runtime requests** — default topologies and scenarios are compiled in; persistence is JSON import/export.
- **Minimal toolchain.** What's constrained is **the artefact and the pipeline that produces it**, not your desk. `rs-web.html` must be pure, self-contained JS — no runtime dependency on anything, no network requests — and the build/test path that makes it uses only two binaries: `esbuild` (bundle) and `bun` (run, test, serve, inline). No Node.js, no npm, no `package.json`, no `node_modules`, no Python **in the build, the tests, or the shipped file**. Incidental local conveniences that never touch the output — serving the directory over `python3 -m http.server`, a throwaway script, your editor — are not covered and are nobody's business. Hard constraint — see Build.
- **Faithful to the protocols.** Simulated behaviour should match how real ARP, switching, routing, RIP, and DHCP work — down to frame fields and the order of operations. Correctness over shortcuts.
- **Determinism & honest divergence.** The same topology plus the same inputs produces the same result — the engine is deterministic, and tests depend on that. The **ephemeral, protocol-visible randoms** (TCP source ports, DHCP transaction ids, DNS transaction ids, attack scan ports, APIPA fallback addresses, and which frames a lossy link drops) come from a **seeded per-run PRNG** (`src/prng.ts`), reseeded at each run: by default from the wall clock (so runs vary like real traffic), or from a fixed value pinned with the console **`seed <n>`** command — pinning makes captures / NAT translations / DHCP ids bit-for-bit reproducible, which is what makes the saved-capture Compare a true before/after diff. Frame ids are a monotonic counter (no wall-clock component). New engine randomness **must** draw from `simRandom`/`simRandomInt`, never `Math.random()`/`Date.now()`, or reproducibility silently breaks. (Per-link loss has its own stream, `lossRandom`, which `beginRun` reseeds for every animated run — some animated runs go through no seeding builder, and a builder draws before the run starts.) Where two paths over the same topology *must* differ (the animated run applies per-link loss; the headless run stays deterministic so checks are stable), the difference is **surfaced, never silent**: the headless run notes the lossy link it skipped, derived state (RIP `learnedRoutes`, STP port roles) is recomputed rather than trusted, and any new source of animated/headless divergence ships with the same kind of surfaced note. Silent divergence is a bug.
- **Typed, tested, and small.** Prefer concrete types over `any`, keep per-device handlers focused, and cover new behaviour with tests.
- **Performance is a feature.** The simulation engine runs hot — device/port lookup, per-device frame processing, routing, and RIP convergence are all on the critical path. Keep them fast, and add a benchmark with a p99 budget for any new performance-sensitive code so regressions are caught early.
- **Keep everything fresh.** Documentation (`docs/`), the `README`, the **in-app guide** (`src/help.ts`, Help → Guide), tests, and benchmarks are part of every change, not an afterthought — update them in lockstep with the code so they never drift. New behaviour ships with matching docs and tests; new hot-path code ships with a benchmark; removed or renamed things get scrubbed from the docs/README the same commit. Where to update: a module change → its `docs/src/<module>.md`; a new test file → the coverage map in `docs/testing.md`; a new benchmark → the cases table in `docs/benchmarking.md`; a new scenario → `docs/scenarios.md` + the solvability suite in `tests/scenarios.test.ts`; **a new device type or a new simulation setting → its entry in `src/help.ts`** (the in-app reference the user reads); user-visible behaviour → the relevant section of this file and `README.md`. The `src/help.ts` coverage is not optional — `tests/help.test.ts` fails until every user-addable device and every Settings-pane toggle is documented there.
- **Scoped work.** When exploring or searching the codebase, stay within this repository — don't scan the home directory or the wider filesystem.

**Known tension — approachable faithfulness.** "Faithful to the protocols" (real FRR/SONiC CLIs, real frame fields, real order of operations) pulls against "a beginner can start here", and "Explain, don't just show" pulls against "small". These aren't bugs to resolve once — they're standing tradeoffs to decide *per feature*. The pattern the codebase already reaches for is **progressive disclosure**: default to the legible view and let the learner descend to full fidelity (the silent-protocol toggles, Instant DNS, the Packets/Events log views are all this). When faithfulness would block a beginner, prefer a legible default with the full fidelity one layer down — rather than either dumbing the model down or making the beginner cope. Name which side you're choosing and why in the change.

## Build

```bash
bash build.sh          # dev build  → rs-web.html
bash build.sh --minify # minified build
```

The project uses only two tools: `esbuild` (bundler) and `bun` (runtime, test runner, test server, build inlining). The build bundles `src/app.ts` into an IIFE via esbuild, then `bun build-inline.ts rs-web.html` inlines the JS + CSS into `template.html`. The result is a **single self-contained** `rs-web.html` with **no runtime requests**: default topologies (`state.ts`) and scenarios (`scenarios.ts`) are compiled in, and persistence is JSON import/export (`io.ts`). There is no `config.json`, no fetch, no File System Access, and no build-time flags.

**`build-inline.ts` gotcha:** it inserts CSS/JS via `String.replace` **replacer functions**, not string replacements — a string replacement would interpret `` $` ``/`$'`/`$&`/`$$` in the bundle as special patterns and corrupt the output. Its `inlineTemplate` **refuses to write a broken page** (the build fails): each of `{{STYLES}}`/`{{SCRIPT}}` must appear in `template.html` exactly once, no other `{{NAME}}` may remain, neither input may be empty, and neither may contain its own closing tag (`tests/build-inline.test.ts`).

**Do not introduce any other build-time or runtime dependencies.** No `npm`, no `package.json`, no `node_modules`, no Node.js, no Python in the build, the test suite, or `rs-web.html` itself — the pipeline is `esbuild` (single binary) + `bun` (single binary), and the output is plain self-contained JS. This is intentional and must be preserved. It does **not** govern how you serve or poke at the files locally: `.claude/launch.json` serving the directory with `python3 -m http.server` is fine, because nothing it does reaches the artefact.

## Serving

```bash
bun test-server.ts               # default port 8767, bound to 127.0.0.1
bun test-server.ts 8765          # custom port
bun test-server.ts 8767 0.0.0.0  # share on the LAN — deliberate, never the default
```

The server runs unauthenticated test execution and serves repository files, so it binds to **loopback by default**; pass a host only when you mean to share it. It refuses dotfiles and `.git`, serves only known static types, accepts a `file` for `/api/run` only if it names one of the enumerated test files, sets no CORS header (its pages are same-origin), and bounds concurrent runs. It also answers only to **its own address** — a request whose `Host` is not loopback (or, when deliberately shared, an IP literal or the bound name) is refused, which defeats DNS rebinding — and the API refuses **cross-site** callers (`Origin` / `Sec-Fetch-Site`); **`/api/run` is POST-only** (a cross-site image or link can only GET). The policies are pure exported helpers (`isServablePath`, `isAllowedTestFile`, `isAllowedHost`, `apiRequestBlockReason`) covered by `tests/test-server.test.ts`; the server itself starts only under `import.meta.main`.

Open `http://localhost:8767/rs-web.html` for the app (`/` redirects there), `/test.html` for the test runner, `/benchmark.html` for benchmarks.

## Architecture

Single-page canvas app. All state lives in one `AppState` object (`state.ts`). No framework, no virtual DOM — imperative `render()` redraws the full canvas, `syncPanel()` rebuilds inspector HTML (blurring a focused panel field first, so an edit still being typed commits rather than vanishing with the old markup), `syncTerminal()` rebuilds terminal HTML.

**[docs/architecture.md](docs/architecture.md) is the map of the whole codebase**: every source file by layer (foundation → model → network logic → engine and CLIs → presentation → application → entry), the state-mutation rules, both callback bridges, the four front doors that converge on one set of mutators, the simulation pipeline, the topology lifecycle, and extension recipes. Keep it current when adding, removing, or re-layering a module.

**Import cycles exist and are tolerated.** The model layer (`state`, `devices`, `normalise`) and **the engine** stay out of them via the callback bridges below — `engine.ts` imports no view and no device shell: it reports a run's result with `sessionFor`/`appendSessionLine`, opens the Sim Log with `showDock` (all `state.ts`) and redraws through `sync()`; the sim-log pane is `simlog-view.ts`. Two cycles remain: the device shells (`terminal/core` ↔ each shell) and the application layer (`ui` ↔ `config`/`commands`/`console`/`io`/`scenarios`). `tests/architecture.test.ts` pins all of this from the real import statements. The rule that keeps this safe: **inside a cycle, call imported functions only from function bodies, never at module top level.** Break it and the failure is quiet: esbuild's IIFE lowers every top-level `const` to `var`, so a use of a not-yet-evaluated import is not a temporal-dead-zone error in the shipped file — it is silently `undefined`, and fails later, far from its cause. Unit tests import modules one at a time, in other orders, so they may never see it. **`tests/bundle.test.ts` builds the bundle the way `build.sh` does, evaluates it, and drives `window.routesim`** (boot, a routed ping, the device shells, a scenario) — it is the only test that runs what ships, and it is part of the default `bun test`.

### Callback bridges

Two registration patterns break circular dependencies:

- **`registerCallbacks()`** in `state.ts` — provides `render`, `syncPanel`, `syncTerminal`, `resizeCanvas` (and `stopSimulation`, the engine's run teardown — `undo`/`redo` and the scenario Check call it before replacing or running over the simulation state) to any module via `sync()`.
- **`registerDeviceCallbacks()`** in `devices.ts` — provides `setTool`, `setNetworkPanel`, `openTerminal` (configure auto-opens a CLI device's terminal, gated by `canOpenTerminal`), and `stopSimulation` (`clearNetwork` tears down an active run *before* deleting the topology it references — the same stop-before-replace order `applyConfigWithoutUndo` follows) so devices.ts can trigger UI/engine work without importing ui.ts/engine.ts/terminal/. (It also still declares an optional `linkUp` hook that `addLink` fires, but nothing registers it since first boot moved to Play.)

Both are wired in `app.ts` at startup.

**Mutators return results, surfaces show them.** A model-layer mutator (`addLink`, `collapseLan`/`expandLan`; `runTerminalCommand` for a shell line) returns a `MutationResult` — `{ ok, error?, message?, warnings[] }` — and does **not** write the status line: the canvas shows `mutationText(result)` on `#modeLabel`, the console returns it, a script import counts a refusal. So a refusal, a warning (a port that could not be honoured, a WiFi association that cannot authenticate) and a no-op read the same from every front door. New mutators follow this; never report through `dom.modeLabel` from `devices.ts`. **One mutator per action, for every front door**: link admin status is `setLinkShutdown`, power is `setDevicePower`, a switch's management plane is `setSwitchManaged` (all devices.ts), the DHCP range/router option/listening ports are `setDhcpRange`/`setDhcpRouterOption`/`setListeningPorts`, a router's static routes are `addStaticRoute`/`removeStaticRoute` (terminal/) — the inspector control, the context menu, the canvas gesture and the console command all call the same one, so they recompute the same derived state (the spanning tree) and validate the same way. Do not set `link.shutdown`, `device.poweredOff` or `config.managed` by hand.

**Sync convention after a mutation:** call `sync().syncPanel()` when inspector
content changes; additionally call `sync().render()` only when the change
affects the canvas (device/link add/remove/move, power, port mode/trunk
lines). Pure inspector-data edits (e.g. adding a VLAN) need only `syncPanel()`.
Reassigning `state.devices`/`state.links` always implies a `render()`.

**HTML safety:** all user-controlled text (device/port/peer names, terminal
command text, config values) must pass through `escapeHtml()` before being
placed in an `innerHTML` template. Only system-generated ids, numbers, and
fixed enums may be interpolated raw.

## Simulation model

Ping generates real Ethernet frames (ARP + ICMP) that traverse the network hop by hop:

1. **Computer** issues ping → `buildPingEvents()` creates ARP request (if needed) + deferred ICMP in `pendingArp`.
2. **Switch** MAC-learns on ingress, then forwards (known unicast) or floods (broadcast/unknown). The learnt table is derived from the cabling, so **every link change invalidates it**: `linksChanged(ids)` (`state.ts` — fired by add/remove/shut/no-shut/device delete, and for all bridges on load/undo/redo; LAN collapse is a view and changes no cabling) flushes the DYNAMIC entries on the affected L2 domain (stopping at routers) and recomputes STP — implicit ports renumber densely, so a stale entry would name the wrong port. A stale entry that survives anyway is forgotten with a logged reason and the frame flooded, never dropped.
3. **Router** matches ingress interface by peerId, takes up only frames addressed to that interface's MAC (or a link-layer broadcast it handles locally, like DHCP — a hub-repeated frame for another host is ignored, never routed — the internet cloud applies the same rule), handles ARP on-interface, routes IPv4 by longest-prefix match, decrements TTL, rewrites L2 headers, may ARP-resolve on egress (buffering the frame in `pendingArp`).
4. **Computer** receives ICMP echo reply → ping success.

ARP never ages out (the simulator has no clock), so **a MAC that leaves the wire takes every cached ARP entry pointing at it along** (`forgetArpEntries` in `devices.ts`, undoable): deleting a device drops its MACs, and unplugging a router cable (`deleteLink`, or deleting the device at the far end) drops the MAC of the router interface it fed — re-cabling a router port to a different peer creates a fresh interface with a new MAC, so without this the hosts would keep addressing the old one. A router re-added at the old gateway address, a router cable moved to another switch, or a replaced LAN switch is then reached. A stale entry that survives anyway (a changed MAC, an imported cache) is named in a failed run's diagnosis (`staleArpEntries` — a cached MAC no cabled device presents), with the remedy `ip neigh flush all` on the host or, for a router's next hop, in the router's privileged mode.

Each hop is an animated dot on the canvas (amber = ARP, blue = ICMP request, green = ICMP reply, red = ICMP Time-Exceeded/TCP RST/DNS NXDOMAIN, violet = DHCP, orange = TCP, cyan = DNS). Speed is controlled by `simulation.speed` (ms per hop, default 1000).

### TCP connect (L4)

`nc -z <host> <port>` (PC terminal) / `connect <src> <dst> <port>` (console) run a real **three-way handshake**: `buildConnectEvents` sends a SYN (ARP-ing the next hop first if needed), the destination answers SYN-ACK if listening (`config.openPorts` undefined = listen on all ports; a list = only those, others RST; an *empty* list = refuse everything — `ports <host> none` vs `ports <host> closed`, and the script export preserves which), and the origin completes with ACK (`sim.tcpSuccess`). RST → "connection refused"; silence → timeout. This is what makes firewall `-p tcp --dport` rules and future NAT/DNS meaningful.

### HTTP (L7)

`curl http://<host>[:port][/path]` (PC terminal) / `http <src> <host> [path]` (console) run the application layer **on top of** the TCP handshake (sim mode `"http"`). `buildHttpEvents` reuses `buildConnectEvents` for the SYN/ARP/DNS plumbing (default port 80) and tags the flow with the requested path; once the handshake establishes, the client immediately sends an **HTTP GET** (`createHttpRequest`), and a server with its web service on answers **200 OK** (`createHttpResponse`, body = `config.httpTitle`). HTTP rides a data (`flags:"ack"`) TCP segment carrying a `TcpPayload.http` (`HttpInfo`: request method/path/host or response status/title), so the packet list shows it as **HTTP** (lime; a 4xx/5xx reads red). The server gate is **`config.httpEnabled`**: an open TCP port with no web service connects but the GET goes unanswered (curl: "Empty reply"), a closed port RSTs ("Connection refused"). Enable it via the inspector (server panel), the `web <server> on|off [title]` console command (round-tripped through the script export), or the **web-server** Server tool variant (preset: `openPorts:[80]`, `httpEnabled:true`). `sim.httpSuccess`/`httpStatus`/`httpStatusText`/`httpServerTitle`/`httpPath` hold the result; the `http` scenario-check kind asserts a 200 (or a given status). See docs/src/engine.md + frame.md.

### NAT / PAT

Routers do Cisco-style source NAT with overload: mark interfaces `ip nat inside` / `ip nat outside` (interface mode) and every inside→outside flow is translated onto the outside interface address (`natTranslateOutbound`), recorded in `config.natTranslations`, and restored on the return path (`natRestoreInbound`, checked before the router's self-IP handling). TCP flows map by allocated source port, ICMP echo by sequence-as-flow-id. **ICMP errors** (Time-Exceeded / Dest-Unreachable) are restored too: every error-generation site quotes the offending datagram (`IcmpPayload.original` via `icmpOriginalOf`, like real ICMP embedding the original header), and the NAT router matches that quoted flow — so **traceroute from behind NAT sees every hop**, including the internet cloud's gateway. `show ip nat translations` / `clear ip nat translation *`; the router's inspector lists the live table (`renderNatTranslations`) and **flashes** the entry a frame just created or used (`NatEntry.lastStep`, stamped by `touchNat`, stripped from the payload) — issue #2. **DNAT / port-forwarding** is the inbound mirror: a static rule (`config.portForwards`, set by `ip nat inside source static tcp <insideIp> <insidePort> <outsideIp> <outsidePort>` in router config mode) redirects a TCP segment to a published outside IP:port to an inside server (`dnatInbound`, applied before the self/route decision so the packet is forwarded not consumed), and the inside server's reply is source-translated back to the outside IP:port (`dnatReturn`, checked before the PAT block so it isn't re-PAT'd) — so an outside client reaches an inside web server through the router's public address. Doesn't require the inside/outside marks; round-trips via JSON config (`normalisePortForwards`). Routers also carry netfilter INPUT/FORWARD chains (`iptables …` in the router terminal, shared engine in `terminal/iptables.ts`) — INPUT guards the router itself, FORWARD filters routed traffic; the transparent firewall device stays FORWARD-only. **nftables is a second front door** onto the same model (`terminal/nftables.ts`): both shells always accept `nft …` and `iptables …`, a per-device `config.ruleLang` toggle (console `rulelang`, or the inspector's Rule language select) picks the dialect the native view / rule rows / script export speak, and `nft`↔`iptables` round-trip because they share `parseFirewallRule` (see docs/src/firewall.md). The filter is **stateful**: `-m state`/`-m conntrack --ctstate` rules match a frame's connection state (`connectionState`/`trackConnection` in engine.ts, gated by `firewallUsesConntrack`; `new`/`established` are assigned, `related`/`invalid` parse but never match), so the canonical "default-drop + accept ESTABLISHED,RELATED + accept the host's NEW" pattern works. **REJECT** sends a response (`rejectResponse`): a TCP RST for TCP (a scan reads the port as closed; a `connect` is refused), else an ICMP destination-unreachable — not a silent drop. `FirewallRule` gained `states?`/`rejectWith?`; `SimulationState.conntrack` is runtime per-device. See docs/src/nat.md and docs/src/firewall.md.

### DNS & the server device

A **server** is a host that also runs **dnsmasq** (DNS A-records + DHCP, one daemon — `systemctl stop` kills both). Hosts resolve via their `/etc/resolv.conf` nameserver (`config.dnsServerIp`, set by terminal/inspector/console or learned from DHCP option 6). `ping`/`nc`/`traceroute` with a hostname **resolve first, then act**: a real UDP/53 query frame (`DnsPayload { op, id, name, address }`, protocol 17) travels to the nameserver — through switches, routers, firewalls (`-p udp`), and NAT (PAT keyed by the transaction id, `protocol: "udp"`) — and on the answer the origin launches the ICMP/TCP flow (`buildFollowOnFrames`); `address: null` = NXDOMAIN. `nslookup <name>` runs the lookup alone (sim mode `"dns"`). A server answers from its manual `dnsRecords` **and an auto-zone** — `hostnameToIp(name)` (simulation.ts) maps any device's hostname to its IP, so every device name resolves with no `address=` record (the fallback in `processAtServer`'s query handler). Whether a device *name* used as a target resolves via that real query or shortcuts straight to the IP is the **`instantDns`** option (default on): `buildPingEvents`/`buildConnectEvents` take the `findPingTarget` name→IP match only when it's on, otherwise they emit a real DNS query (or fail "cannot resolve" with no nameserver). It defaults **on for topologies** (`loadTopology`) and **off for scenarios** (`loadScenario`) — goal checks resolve names to IPs themselves (`scenarios.ts`), so they're unaffected. `processAtServer` answers service frames and falls through to `processAtComputer`. See docs/src/dns.md.

### Traceroute / TTL

A router checks the TTL **before** the forwarding decision: when a packet's TTL reaches 0 it drops it and (if the ingress interface has an address) sends an **ICMP Time-Exceeded** (type 11) back to the source — `createIcmpTimeExceeded` in `frame.ts`, handled in `routeIpv4Frame`. `runTraceroute(source, target)` (engine.ts) drives this: it warms ARP along the path, then sends probes with increasing TTL (1..30), recording who answered each round (a router's Time-Exceeded = intermediate hop; the destination's Echo Reply = final hop). Exposed as the `traceroute`/`tracert` command in the PC terminal and the console. It runs over `runSimulationHeadless`, which sets `sim.headless` so per-step rendering and terminal output are skipped.

### Failure diagnosis

A failed run says why (the "Failure is a lesson" principle, made mechanical). **`linkDataBlockReason(link)`** (`devices.ts`) is the data gate with a reason — shut, spanning-tree blocked, WiFi password mismatch, unauthorized 802.1X port (force-unauthorized vs. an `auto` port awaiting authentication), failed MACsec — and `linkAuthorizedForData` is its boolean wrapper; `findFirstHop` returns that reason (or a powered-off peer), so every builder's `Network is unreachable (…)` names the cause ("no link" only when there is no cable), and `admitOnLink`'s drop line does too. `processNextStep` logs `<name> is powered off — <frame> dropped` once, before dispatch. `finishSimulation` runs a **post-mortem** (`runPostMortem`) before clearing its queues: a storm is the whole story, otherwise each `pendingArp` entry still holding frames is an ARP nobody answered, explained on the device that waited — naming the **default gateway** when it is the cause, and quoting the real drop reason when the ARP was dropped on the way (`sim.arpDrops`: a data gate, shut cable, powered-off device or link loss, rather than a guessed "is the address right?") — into `sim.diagnosis` → `SimResult.diagnosis`, the `run` output, the origin's terminal after a failed ping/nc/curl/nslookup, and after a traceroute that does not arrive (`TracerouteResult.diagnosis`). A run that met its goal (a sweep that found hosts) logs its unanswered ARPs as plain notes and keeps `diagnosis` empty. `SimResult` also carries **`storm`** (headless storms used to be invisible; `runTraceroute` now stops at the storming probe) and **`unreachableFrom`**; a failed ping prints `From X icmp_seq=1 Time to live exceeded` / `Destination Port Unreachable` / `Destination Host Unreachable` like Linux. A router answers TCP/DNS to its own IP with a RST / ICMP Port Unreachable (nothing listens there) instead of swallowing it. See docs/src/engine.md ("Failure diagnosis").

### Routing

Routers forward IPv4 frames using a merged routing table built by `buildRoutingTable(router)` in `routing.ts`. The table combines three sources in priority order: connected routes (metric 0), static routes (metric 1), and RIP learned routes (metric 2+). `routingLookup(router, dstIp)` finds the best matching route and resolves the next-hop to an egress interface. Static routes are configured per-router via the `ip route` terminal command or the console `route` verb — one mutator, `addStaticRoute` (CIDR network required, valid next hop, stored with host bits masked, duplicates refused as a no-op) — and stored in `config.staticRoutes`. The `RouteEntry` type (`types.ts`) holds `{ network, nextHop, interface, type: "C"|"S"|"R", metric }`.

### RIP

`runRipConvergence()` runs automatically before each simulation starts. It iterates up to 15 rounds, exchanging route advertisements between RIP-enabled routers until the network converges (no changes in a round). Split-horizon prevents re-advertising routes back toward the interface they were learned from. **A `network` statement enables RIP on the interfaces it covers** (as in FRR) — an exchange happens only when *both* ends' interfaces are covered, so a router with an empty network list learns nothing and a transit link left out of RIP carries no advertisements. Metric 16 = unreachable. A router cabled to an **internet cloud** also **originates a default** (`0.0.0.0/0`) into RIP (like `default-information originate`), so routers several hops from the edge learn a way out — an edge itself never *learns* a default (it has its own implicit one), keeping dual-edge topologies symmetric. **Learned routes are derived state** (like STP's port roles): cleared and recomputed from the live topology at each convergence — a removed link or router takes its routes with it — and **not serialised** (only `enabled`/`networks`/`passiveInterfaces` round-trip) — nor stored in undo snapshots (`persistentDevice` in state.ts strips RIP routes, STP roles, dynamic MAC entries and `link.stpBlocked`, so snapshots of the same network compare equal). **Every reader converges first**: the run (`beginRun`) and the router's `show ip route`/`show ip rip` commands call `runRipConvergence()` rather than trusting what is stored, so the table is right before the first run and right after an unlink — a new reader of `learnedRoutes` must do the same. RIP config per router: `config.rip = { enabled, networks, passiveInterfaces, learnedRoutes }`.

### Spanning Tree (STP)

`runStpConvergence()` (`stp.ts`) runs before each simulation (right after `runRipConvergence`) and on topology/STP-config change (the `recomputeStp` callback). It's the L2 analogue of RIP: it elects a **root bridge** per connected switch component (lowest bridge id = priority + base MAC), BFS-costs each bridge to the root (fixed per-link cost 1), assigns every port a **role** (root/designated/alternate) and **state** (forwarding/blocking), and sets `link.stpBlocked` on each alternate port. **On by default for managed switches** (`isStpParticipant`; only `stp.enabled === false` opts out). Derived fields (`bridgeId`/`rootId`/`rootCost`/`ports`) are recomputed, never serialised — only `enabled` + non-default `priority` round-trip. The block takes effect through `linkAuthorizedForData` (see below), so a redundant L2 path is cut and the loop broken. With STP off and a loop, broadcasts multiply without bound — a **broadcast storm**, detected **by evidence, identically on both paths** (`loopedBack`: the same frame lineage crossing the same wire in the same direction, at the same IPv4 TTL, a second time — a copy came back round the loop; the sim log names that wire) into `sim.stormDetected`, with a shared `STORM_BACKSTOP_STEPS` backstop counting only steps that send frames, so a large loop-free run (a ping sweep, a DHCP lease on a big LAN) is never mistaken for one and an IP routing loop (TTL-bounded) never is — surfaced on both paths (`SimResult.storm` + a `STORM_DIAGNOSIS` log line; see Failure diagnosis). `stp`/`run stp` animate the BPDU flood (`handleBpdu` relays a Configuration BPDU from the root down the designated ports; faithful `bpdu` frame, dst `01:80:C2:00:00:00`). Simplifications: one tree per bridge (not per-VLAN), cost 1, instant convergence, loops across directly-linked managed switches only. See `docs/src/stp.md`.

### DHCP

**Network boot**: adding/cabling/powering a host does **not** auto-configure it — an unconfigured host stays "unassigned" until the user **starts the simulation**. Clicking **Play** while idle (or `startNetworkBoot()`) boots every unconfigured, cabled, powered-on host with an **animated** DHCP exchange in turn (`bootQueue` chained through `finishSimulation` so they boot one at a time), self-assigning **APIPA** (`169.254.x.y/16`, no gateway) only **after** the simulated DHCP times out — like a real machine on carrier detect, but visible (`ipSource` = `dhcp`/`apipa`). `unconfiguredBootableHosts()` is the qualifying set (excludes configured, powered-off, and uncabled hosts). The `dhcp` terminal/console command boots a single host the same animated way. (This replaced the old silent, instant headless boot on cable-up/power-on.) Two **independent global toggles** gate this (pedagogical, in the **Settings** pane opened by the cog button on the Main tab, **both off by default** — `state.options.autoDhcp`/`apipaFallback`): with **Auto-DHCP on**, Play runs the animated DHCP exchange, self-assigning **APIPA** on timeout only if APIPA fallback is also on; with **Auto-DHCP off but APIPA on**, Play skips the DHCP frames entirely and the host self-assigns a link-local address **directly** (`assignApipa`, instant — no run); with **both off**, Play does nothing and the host stays unassigned. (So APIPA no longer depends on Auto-DHCP — clearing Auto-DHCP while APIPA is on still yields a 169.254 address.) The manual `dhcp` command always attempts DHCP regardless of the toggles.

`buildDhcpEvents(source)` in `simulation.ts` creates the initial DHCP Discover frame. The four-message exchange (Discover → Offer → Request → ACK) is handled by `processAtComputer`, `processAtRouter`, and `processAtServer` in `engine.ts`. Frame factories in `frame.ts`: `createDhcpDiscover`, `createDhcpOffer`, `createDhcpRequest`, `createDhcpAck`. The router allocates from the interface's **usable range for its real prefix** (starting at `.100` for a `/24` or larger, else the first usable address — a `/25` at `.129` leases from *its* half, never `.100` from the other); a server allocates from its configured `dhcp-range` and additionally hands out the router option (`option:router`, defaulting to the server itself, as dnsmasq does) and itself as nameserver (option 6). On ACK, the client assigns IP/prefix/gateway (+ nameserver if offered) and learns the server's MAC. Multi-server segments behave correctly: the client takes the **first Offer** (`sim.dhcpOfferTaken`), and a server/router only ACKs Requests whose `serverIp` names it.

### Frame history

Every link records frames that traverse it (`link.frameHistory[]`), capped at 200 entries per link and excluded from undo snapshots — a lightweight per-wire traffic counter. Selecting a link in select mode shows the count in the inspector; the individual frames are **not** listed there. Instead a **View frames in the packet log** button jumps to the Sim Log packet list filtered to that wire (`state.dock.logFilter.link = link.id`, opens the dock on the sim log, `logView: "packets"`) — the richer, columned, filterable view is the single place to inspect frames, so the inspector doesn't duplicate it with a stripped-down list.

## State conventions

- `state.selectedId` — currently selected device (null if none).
- `state.selectedLinkId` — currently selected link (null if none). Mutually exclusive with selectedId.
- `state.configuringId` — device whose config fields are shown (requires double-click or configure tool).
- `state.simulation.status` — `"idle"` | `"running"` | `"paused"` | `"done"`.

## Common tasks

**Adding a device type**: (1) add the `DeviceType` union member + config interface in `types.ts`; (2) add a `DeviceSpec` entry to `DEVICE_SPECS` in `device-registry.ts` (label, name prefix, size, palette var, icon paths, default config, `defaultPorts` if it has an Ethernet port count, and its **`roles`** — `host` (an IP end-system: ping/name target, inspector host fields, IP label, a MAC on creation), `singleNic` (one cable, no port picker), `bootable` (Play network-boots it), `dot1xSupplicant`, `hostname`/`terminal` (`true`/`false`/`"managed"`)) — this drives naming, drawing, inspector labels, `add`/`tool` validation, and every capability check (via the role helpers) automatically; `tests/device-registry.test.ts` checks each consumer agrees with the spec, so **never add a hand-written list of device types**; (3) add the `--<paletteVar>-fill/-stroke/-accent/-icon` vars to **each theme** in `styles.css` (the parity test enforces this); (4) add a normalise branch in `normaliseDeviceConfig`; (5) implement `processAt<Type>` in `engine.ts` and register it in the `PROCESSORS` map; (6) optionally add a CLI in `src/terminal/`, register it in `CLI_DISPATCH` (`terminal/core.ts` — must agree with the `terminal` role), and give it a prompt in `terminalPromptText`; (7) add the tool button in `template.html` + `toolCopy` entry and keyboard shortcut in `ui.ts` — either a plain `tool-button` or a variant inside an existing **split-button group** (`.tool-split`: Computer / Server / Switch / Security / Legacy), whose face + menu are driven by `syncToolGroups`; placement resolves through `placeToolDevice`/`PLACEMENT_TOOLS` in `devices.ts` (a UI-only variant tool that isn't a `DeviceType` — like `managed-switch` or the `*-server` presets — maps to a real type + preset config there, and needs a `toolCopy` entry but no `DEVICE_SPECS` entry); (8) give it an inspector panel — add a section to `INSPECTOR_SECTIONS` (`inspector.ts`) if it has settings of its own, and list its sections in the registry test in `tests/inspector.test.ts`, which fails until every user-addable type is listed; (9) add a `DEVICE_DOCS` entry in `src/help.ts` (the in-app **Help → Guide** reference — `tests/help.test.ts` fails until every user-addable type is documented; variants like Managed/Border/the `*-server` presets fold into their parent's blurb). The **firewall** is the worked example — see [docs/src/firewall.md](docs/src/firewall.md). The **hub** (a layer-1 repeater under the **Legacy** tool group — floods every frame, no MAC learning; `processAtHub`) is a second, minimal worked example.

**WiFi** (`laptop` + `access-point`) is a heavy-reuse example needing no new processor: a **laptop** is a WiFi-only host (reuses `processAtComputer`, added to the `HOST_TYPES`/CLI/ping/boot host checks); an **access point** is a transparent L2 bridge that reuses `processAtSwitch` (unmanaged) over all its links — with a single wired uplink (`clampApPortCount`), since wireless associations are not ethernet ports. The new concept is the **wireless association** — a `Link.wireless` flag created by the Connect tool only for a laptop↔AP pair (`classifyLink`/`linkBlockReason` in `devices.ts` enforce that a laptop associates to exactly one AP), drawn dotted on the canvas. Forwarding "just works" because `l2Reachable` already treats anything-not-a-router as L2-transparent. Both carry an **SSID** (capped at 32 **octets** as 802.11 requires — `normaliseSsid` keeps whole code points, so a CJK or emoji name is not silently over-long) (+ optional `wifiPassword`), defaulting to a shared `DEFAULT_SSID` so fresh devices associate; `classifyLink` gates the join on a matching SSID then password (set via the inspector or the `ssid` command, round-tripped by config/script export). The **802.11 association handshake** is a real simulated exchange: `associate <laptop>` (or the laptop inspector button) animates `dot11` frames — Probe / open-system Auth / Association, plus the WPA2 4-way EAPOL handshake on a secured AP — driven by `handleDot11` (a reactive state machine shared by `processAtComputer`/`processAtSwitch`, each frame triggering the next), built by `buildAssociationEvents`, shown in the packet list (`packetColumns` → "802.11"/"EAPOL"). It's a separate `dot11` payload on `EthernetFrame` (etherType `0x888e`); these frames live only on the air (the AP does not bridge them). A **wrong password** is faithful: the SSID match lets the link form (`classifyLink` no longer rejects on password), but `wifiLinkAuthenticated(link)` (live, no stored state — a matching SSID, and an open network or matching password; `wifiLinkBlockReason` is the reason form, so re-pointing the laptop's SSID after it associates fails the join — review R15) is false, so the WPA2 handshake deauthenticates at the M2 MIC check and the link carries no data — it gates `l2Reachable`/`findFirstHop`/the engine transit path (data only; `dot11` management still passes), and is drawn red. Fixing the password authenticates it live.

**802.1X** (port-based access control) reuses that same substrate. The data-path gate is unified into **`linkDataBlockReason(link)`** (`devices.ts`; `linkAuthorizedForData` is its boolean wrapper — the reason feeds "Network is unreachable (…)" and the transit drop line), consulted by all three chokepoints (`l2Reachable`/`findFirstHop`/the engine transit step) — it returns false for an unauthenticated WiFi association, an unauthorized 802.1X port, a failed MACsec link, *or* a spanning-tree alternate (blocked) port (`link.stpBlocked`), while `dot11`/`dot1x`/`bpdu` control frames bypass it. The three roles: a **supplicant** host (`config.dot1x = {identity, password}`), an **authenticator** managed-switch port (`config.portAuth[Ethernet_N] = "auto" | "force-authorized" | "force-unauthorized"`), and a **RADIUS server** (`config.radius.users`, on a server adjacent to the switch — RADIUS is abstracted to one hop). `dot1x <host>` / `run dot1x` run a reactive `handleDot1x` state machine routed by frame subtype: EAPOL-Start → EAP-Req/Resp-Identity (host↔switch) → RADIUS Access-Request/Accept|Reject (switch↔server) → EAP-Success/Failure. **The authenticator obeys the port's control mode** (as the 802.1X PAE state machine does): only an `auto` port runs that exchange; a `force-unauthorized` port answers EAPOL-Start with a canned EAP-Failure and a `force-authorized` one with a canned EAP-Success, neither asking RADIUS nor touching `link.dot1xAuthorized`. **Changing a port's mode (`portauth`) ends its session** — it clears `link.dot1xAuthorized`, so an authorisation earned under one mode never opens the port under another. A failed login states its cause (`sim.dot1xFailure`, set by the handler that decided it — forced-closed port, no RADIUS server, Access-Reject — and carried into `SimResult.diagnosis`). A new `dot1x` payload on `EthernetFrame` (etherType `0x888e`; `packetColumns` → "EAPOL"/"EAP"/"RADIUS"). **Port control is a property of the switch port, not the peer**: whatever is cabled to an `auto`/`force-unauthorized` port — a PC, a Kali PC, a Red Team host, a hub (and everything behind it), an AP uplink, a router — faces the same gate (`dot1xLinkInfo`/`dot1xPortAuthorized`; both ends of a switch↔switch link are checked), and a peer that can't or doesn't run a supplicant simply never authenticates. Which devices can be supplicants is the registry's `dot1xSupplicant` role (every host, offensive ones included). An `auto` port stays unauthorized (`link.dot1xAuthorized`, set on Access-Accept) until success; the server validates the identity against the supplicant's own `dot1x.password` (no plaintext in the frame). The exchange is **correlated by the supplicant's MAC** (`Dot1xPayload.supplicantMac`), so two hosts presenting the same identity validate and authorise independently. Config via `supplicant`/`portauth`/`radius` commands, round-tripped through JSON + the script export.

**MACsec** (802.1AE link encryption) is the third consumer of the unified gate. A per-peer pre-shared key (`config.macsec[peerId] = {cak, mode}`, on any device; `macsec <device> <peer> <key> [must|should]`) drives **`macsecState(link)`** (live): both ends matching → `secured`; a mismatch, or a `must`-secure end facing a bare peer → `failed`; otherwise `open` (incl. a `should`-secure fallback). `linkAuthorizedForData` drops data on `failed`. Frames crossing a `secured` link are marked `CaptureEntry.macsec` in `deliverCompletedTransits` and re-rendered by `renderPacketTable` as "MACsec — Encrypted … (SecTAG, ICV)" (the engine still processes the real inner frame at the far end); `drawLink` colours secured links teal, failed red. Round-trips via JSON + script (`macsecPayload`/`normaliseMacsec`, each end emits its own `macsec` line). **802.1X-derived keying** (Phase 3 / MKA — the enterprise "authenticate, then encrypt" story) reuses the `dot1x` flow with no new frame type: `macsec <device> <peer> dot1x [must|should]` stores `{derive: true, mode}` (no `cak`), and `macsecState`'s both-ends branch keys it from the EAP exchange — `secured` once `link.dot1xAuthorized` is set (by the same Access-Accept step), otherwise `failed`/`open` by mode; a derive end facing a static-CAK end is an incompatible method (treated like a mismatch). So a `must`-secure derive link is `failed` (data blocked, alongside the `auto`-port gate) until `dot1x` authenticates, then auto-secures.

**Spanning Tree (802.1D)** is the fourth consumer of the unified gate, but unlike the per-link auth/encryption above it's a *computed topology property*: `runStpConvergence()` (`stp.ts`, see the Simulation model section) sets `link.stpBlocked` on each alternate port, and `linkAuthorizedForData` drops data there — breaking L2 loops at the same chokepoints. STP config lives on a managed switch as `config.stp = { enabled, priority }` (the rest is derived/transient); it's edited via the inspector Spanning-tree section (`renderStpSection`/`bindStpControls`), the SONiC `config spanning_tree …` CLI, or the console `stp <switch> on|off|priority`. The animated run reuses the reactive-handler pattern (`handleBpdu`, a `bpdu` frame on `EthernetFrame`, etherType sentinel `0x0802`, dst the bridge group `01:80:C2:00:00:00`). The new console **`managed <switch> [on|off]`** command (and a `managed <name>` line in the script export) closes a pre-existing gap where a managed switch's management plane wasn't reproducible from a script (JSON already round-tripped it). `drawLink` draws a blocked link dashed-amber (`--stp-block`); `drawRootBridgeBadge` marks the root.

**IDS (Snort) + SPAN port mirroring** add a passive intrusion-detection sensor and the port mirroring that feeds it. A managed switch can run one **SPAN** session (`config.mirror = { name, dest, sources? }`): in `processAtSwitch` the monitor (`dest`) port is excluded from normal forwarding, and each matching ingress frame is **copied** to it (`-span` id; control frames not mirrored). The **IDS** device (`type: "ids"`, an eye icon, Security tool group, shortcut `I`) is a single-NIC passive sink (`processAtIds`): it runs **Snort rules** (`config.idsRules`, raw `local.rules` lines — named `idsRules` to avoid colliding with `FirewallConfig.rules` in the `DeviceConfig` superset) against the mirrored frame via `runIdsRules` (`snort.ts`: `parseSnortRule`/`matchSnortRule`/`formatAlert`), appends a Snort fast-alert to `config.alerts` (runtime, **not** serialised), and logs `sim-ids` — it alerts but never forwards/drops (it's not inline). Config via the SONiC `config mirror_session span add` CLI + the `snort` IDS terminal (`terminal/ids.ts`: edit `/etc/snort/rules/local.rules`, read `/var/log/snort/alert`), the inspector (`renderMirrorSection` — monitor-port dropdown + per-port source checkboxes / `renderIdsSection` rule textarea + alert log), and the console (`mirror <switch> <dst> [src…]`, `idsrule <ids> <rule>`). The `alert` scenario-check kind asserts a sensor fired. See `docs/src/ids.md`.

**Offensive hosts (Kali PC + Red Team actor)** are the **blue-team counterpart** — two devices sharing one **Kali Linux** attack engine. A **Kali PC** (`type: "kali"`, a monitor-with-prompt icon, **Computer** tool group, shortcut `K`) is a pentest *workstation* the user drives by hand. A **Red Team actor** (`type: "attacker"`, a skull icon, **Security** tool group, shortcut `A`) is an *autonomous* adversary that launches its configured plan on **Play** (`launchRedTeam`, filtered to `attacker` only; an unconfigured actor is network-booted by Play first like any host, and with actors placed but none ready Play says why — powered off, no IP / no cable, no attacks). Both are real single-NIC hosts (IP/MAC/ARP, reuse `processAtComputer`) that run **attacks**: an `nmap -sS` **port scan** (a SYN to each of `SCAN_PORTS`; open→SYN-ACK, closed→RST), an `nmap -sn` **ping sweep** (ICMP echo across a subnet, routed via the gateway for a remote subnet), and **ARP spoofing** (`arpspoof [-r] [-t <victim>] <gateway>`: a gratuitous reply poisoning a victim's ARP cache — broadcast by default, `-t` unicast to one victim, `-r` also poisons the gateway for a two-way MITM; issue #5). With **`sysctl -w net.ipv4.ip_forward=1`** (`config.ipForward`, off by default) a Kali host becomes a *transparent* MITM: `forwardIntercepted` (engine.ts) relays a frame unicast to its MAC but bound for another IP to the true next hop from its own unpoisoned ARP cache — TTL decremented, IPs untouched — so a poisoned victim's ping still succeeds and the extra hop shows (issue #4). The builders live in `simulation.ts` (`buildScanEvents`/`buildSweepEvents`/`buildArpSpoofEvents`/`buildAttackEvents`, each returning a `PingSetup`); a run is sim mode `"attack"` (`startSimulation(..., "attack")`). `processAtAttacker` (registered for **both** types) tallies replies into `sim.scanOpen`/`scanClosed`/`sweepLive`; `finishSimulation`'s `"attack"` branch builds an nmap-style `PORT STATE SERVICE` report onto `config.attackLog` (runtime, **not** serialised). Both are full hosts: they serialise via the shared host helpers (`hostConfigForPayload`/`normaliseHostFields`), and the Kali CLI (`terminal/attacker.ts`) **falls through to the host shell** (`runHostTerminalCommand`) for ordinary commands — which is what the inspector's IP/gateway/DNS/MAC fields commit through. Triggers: the Kali terminal (`nmap -sS`/`-sn`, `arpspoof`), the console (`attack <node> [scan|sweep|arp-spoof] [target]`, `redteam <node> target|attacks|spoof …`), the **actor's** inspector panel (`renderAttackerSection`/`bindAttackerControls`), and autonomous **Play**. The `alert` scenario-check launches the scan when its `from` is an attacker; the `red-team-scan` scenario pairs it with an IDS (red vs blue). See `docs/src/red-team.md`.

**Hostname = canvas name.** A CLI device's `device.name` *is* its hostname — the canvas label, the terminal prompt (`devicePrompt` in `terminal/core.ts`), and the name it resolves as (the DNS auto-zone / `findPingTarget`). `applyHostname(device, name)` (devices.ts) is the shared setter: it validates against `isValidHostname` (RFC-1123 label), pushes undo, sets `device.name`, and re-syncs panel/terminal/canvas. The realistic CLI paths all call it — host `hostname <name>` / `hostnamectl set-hostname <name>` / `echo <name> > /etc/hostname` (`terminal/host.ts`), router `hostname <name>` in config mode (`terminal/router.ts`, registered in `ROUTER_COMMANDS`), managed-switch `config hostname <name>` (`terminal/switch.ts`) — as does the inspector name field, which is labelled **Hostname** for `hasHostname(device)` types (hosts/router/firewall/managed switch) and **Name** otherwise. The permissive console `rename` stays unvalidated against the hostname rule (a meta tool). **Names are unique, ignoring case** — `deviceNameBlockReason(name, self?)` (devices.ts) is the one rule, asked by `applyHostname`, the console's `add`/`rename` and the inspector's plain Name field before any undo point, because every text front door resolves a device by name case-insensitively; auto-generated names skip taken ones, and the script export renames any duplicate it still finds (a JSON import) deterministically, with a `#` note. The **inspector name field** routes through `applyHostname` too for `hasHostname` types — committing on change/Enter like the other device fields (per-keystroke validation would reject every prefix of a valid name), reverting and reporting on rejection; for the remaining types (LAN, hub, unmanaged switch, AP, cloud) the field is a plain name and stays free text.

**Adding a terminal command**: `runTerminalCommand()` in `terminal/core.ts` dispatches via the `CLI_DISPATCH` map — computers → `runHostTerminalCommand` (`terminal/host.ts`), servers → `runServerTerminalCommand` (`terminal/server.ts`, falls through to the host shell), routers → `runRouterTerminalCommand` (`terminal/router.ts` — also add the command to the `ROUTER_COMMANDS` registry so abbreviation and `?` help pick it up), switches → `terminal/switch.ts`, firewalls → `terminal/firewall.ts`. **Match the device's reference NOS** — FRRouting (vtysh) for routers, SONiC for switches, Linux/dnsmasq for hosts/servers — so new commands stay faithful to a real CLI rather than inventing syntax.

**Adding a simulation protocol**: Create frame factories in `frame.ts`, handle in the appropriate `processAt*` function in `engine.ts`, update `frameLabel`/`frameColor` for display.

**Adding a console command**: Add a handler to the `COMMANDS` registry (and a `HELP` entry) in `commands.ts`, reusing existing action functions. If the command sets something a saved network keeps, **teach `exportTopologyScript` to write it** — `tests/roundtrip.test.ts` exports every built-in topology and scenario, replays the script from empty and compares the two networks field by field, so a field the export cannot express fails there (always `quoteArg` a free-text value, and write an empty one as `""`). It's automatically available in the console panel, `window.routesim`, and scripts. For commands that build/observe state, prefer the headless `runSimulationHeadless` (engine.ts) over the animated path. **Undo contract:** a command that mutates the topology/config must be undoable — either call a helper that already pushes undo (`addLink`/`deleteLink`/`addDevice`/`deleteSelection`/switch mutators) or `pushUndo()` yourself *after validation, before the first mutation* (so a rejected command adds no spurious undo entry). Sim-running commands (`ping`/`run`/`attack`/…) and pure read/UI commands don't push. `tests/commands.test.ts` pins this — undo a representative command and assert the state is restored. See `docs/scripting.md`.

**Adding a scenario**: Add a `Scenario` (initial `topology` + a `checks` goal) to `src/scenario-library.ts`, append it to `CURRICULUM`, and add its id to a group in `SCENARIO_GROUPS` (the curated, ordered grouping that drives the chooser's flyout submenus and `scenario list`; a `tests/scenarios.test.ts` check enforces that every scenario is grouped exactly once — an ungrouped one would otherwise land under "Other"). Check kinds: `link`, `config`, `ping`, `ping-fail` (isolation), `tcp`/`tcp-fail` (port reachability) — **give every `ping-fail`/`tcp-fail` a `blockedBy: "<device>"`**: a bare one passes on *any* failure (a closed port, a re-subnetted host), so the scenario can be solved without its concept; with `blockedBy` the check also requires that the flow *would succeed with that device's policy removed* (a what-if run over copied configs — firewall/router rules cleared, or a switch made unmanaged), and a wrong-cause failure carries a `note` the banner and `scenario check` show — `http` (an HTTP GET returns 2xx, or a given `status`), `dns` (name resolution, optionally to a given address), `dhcp`, `alert` (an IDS raises an alert containing a substring for a flow). It appears automatically in the chooser, the console (`scenario list/load/check`), and the goal banner; checks reuse the headless runner. Add a runnable reference solution as `scenario-solutions/<id>.routesim.txt` (a console script: `scenario load <id>` → the fix → `scenario check`) — these are the single source of truth, both the learner-facing answer key and what the solvability suite runs. `tests/scenarios.test.ts` reads every script and asserts the scenario starts unsolved and passes after, so the scripts can't drift. See `docs/scenarios.md`.

**Built-in topologies**: The File-tab Topologies `<select>` (`loadTopology` in `config.ts`) offers three built-in topologies: Basic Network, VLAN Router-on-a-Stick, and 5-Router Partial Mesh. Their coordinates are spaced so label text (name/IP/MAC/VLAN + router interface lines) never overlaps another device — keep ≥150px vertical spacing for stacked computers when editing them.

## Style notes

- **Commonwealth English** in all code and documentation. Use `-ise`/`-isation` (e.g. `normalise`, `initialise`), not `-ize`/`-ization`.
- **No emoji in user-facing messages** (status text, banners, terminal/console output, log lines). Emoji used as functional glyphs/icons (e.g. status marks like `✓`/`✗`/`○`) are fine.
- **Prefer concrete types over `any`.** Function parameters take real types (`Device`, `Link`, …). `Device.config` is `DeviceConfig` — a permissive superset of the per-type `ComputerConfig`/`SwitchConfig`/`RouterConfig`/`LanConfig` shapes (every field optional) so `device.config?.x` access stays ergonomic while typos are caught; the strict per-type interfaces type the `normalise.ts` layer. The codebase is **tsc-clean** (`bunx tsc --noEmit`) — keep it that way. Remaining intentional `any`: the File System Access API and DOM `dataset` extensions, documented where they occur.
- **Keep handlers focused.** When a `processAt*` or convergence function grows large, extract private helpers rather than inlining everything (e.g. `handleRouterArp`, `routeIpv4Frame`, `buildRipAdvertisements`).
- **Cover new behaviour with tests.** Add or extend a `tests/*.test.ts` suite when changing simulation logic.
- **Benchmark hot paths.** Add a `bench:` case in `tests/bench.test.ts` (with a p99 budget via `tests/bench-harness.ts`) for any new performance-sensitive code, and keep existing benchmarks within budget. Favour allocation-free, tight implementations on the simulation critical path.
- CSS variables for theming (dark/light). All colours are CSS custom properties.
- Terminal uses monospace font, dark background regardless of theme.
- Sim log line classes: `sim-arp` (amber), `sim-icmp` (green), `sim-learn` (grey), `sim-forward` (blue), `sim-drop` (red), `sim-tcp` (orange), `sim-nat` (teal), `sim-dns` (cyan), `sim-attack` (crimson — Red Team findings).
