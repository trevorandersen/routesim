RouteSim: user guide and simulation mechanics

RouteSim is a single-file teaching simulator. You build a network on a canvas, configure it the way you would a real one, and watch real Ethernet frames (ARP, ICMP, DHCP, DNS, TCP, HTTP and more) hop from device to device.

Part 1 is for people using the tool. Part 2 explains what the simulator actually does when you press Play, and where it deliberately departs from a real network.

Part 1 · User guide

Everything you need to build, run and read a network.

1. Getting started

RouteSim ships as one file, rs-web.html. Open it in any modern browser; there is nothing to install and the page makes no network requests, so it works offline. The built-in topologies and the scenario curriculum are compiled in.

To build it yourself you need only esbuild and bun:

bash build.sh            # dev build, writes rs-web.html
bash build.sh --minify   # minified build
bun test-server.ts       # optional: serve on http://localhost:8767

Your first ping, in five steps

  1. Press C and left-click the canvas twice to drop two PCs. A faint preview of the device follows the cursor; right-click or Esc puts the tool down.
  2. Press S and click once to drop a switch.
  3. Press L (Connect), click a PC, then the switch. Repeat for the other PC.
  4. Select a PC with V, and in the inspector on the right give each PC an address in the same subnet, for example 192.168.1.10/24 and 192.168.1.11/24.
  5. Open the first PC’s terminal (double-click it) and type ping PC-2 (use the name shown on your canvas). Open the Sim Log tab in the bottom dock and watch the ARP request, the ARP reply, then the ICMP echo and its reply cross the wires.

Tip. The Help → Tutorial menu plays a hands-off demo that builds two LANs joined by a router and pings across them. It drives the real interface, so it shows exactly what you would do by hand, and you can step through it with the arrow keys.

2. The screen

Ribbon

Four tabs. Main has the drawing tools, undo/redo/delete/Clear and the play controls. File has topologies, the scenario chooser, import/export and Copy link. View has themes, label toggles and Packet callouts. Help has the Guide, the Tutorial and About.

Canvas

Pan by dragging the background, zoom with the scroll wheel. Devices snap to a grid. Frames in flight are drawn as coloured dots, each carrying a text label and a letter glyph so colour is never the only signal.

Inspector

The right-hand panel. It shows whatever is selected: a device’s settings, a link’s name, latency and loss, or the full field breakdown of a frame you clicked.

Bottom dock

One resizable panel with a tab per open device terminal, the command console, and the Sim Log. Drag its top edge to resize it.

Transport pill

While a run is active, a play/pause/step/stop pill floats over the canvas, whichever ribbon tab you are on. Space pauses and resumes.

Settings pane

The cog on the Main tab opens a right-docked pane with the boot, name-resolution, autosave and silent-protocol switches (section 11).

3. Building a network

Placing devices

Pick a tool from the ribbon or press its key. Related devices share a split button: the face places the last variant you used and the caret opens the rest. Left-click drops a device and the tool stays armed for the next one. Right-click or Esc returns to Select. Names are assigned automatically (PC1, MSW-1, and so on) and can be changed in the inspector.

Cabling

With the Connect tool, click one device and then another. The first free port on each end is chosen for you. Shift-click the second device to pick ports by hand; a port chosen that way is pinned and keeps its name as other cables come and go. Computers and servers have a single network card, so they accept one cable. Double-click a cable to shut it without deleting it (shut cables are drawn dashed red with a “down” label).

Link properties

Select a cable to give it a name, a latency (its frames visibly crawl) and a loss rate (animated runs drop that share of frames). Non-default values appear on the canvas as text, for example WAN · 40 ms · 5% loss.

Undo, redo, Clear

Ctrl/Cmd+Z undoes topology and configuration changes and Ctrl/Cmd+Shift+Z (or Ctrl/Cmd+Y) redoes them. Clear wipes the canvas and ends any active scenario with it; one Undo brings both back.

5. Configuring devices

Double-click a device (or use the Configure tool, W) to open its inspector and, for a command-line device, its terminal.

The inspector

Addresses accept address/prefix; a bare address keeps the existing prefix. A pill beside the address tells you where it came from (static, dhcp or apipa), and the canvas label reads “unassigned” until a host has one. Committing a host field runs the matching Linux command in the host’s terminal, flagged as simulator-issued, so the GUI and the shell never disagree. Routers and firewalls show an editable rule list with a default policy for each chain.

6. Running a simulation

There are three ways to start a run, and they all produce the same frames.

  • From a terminal. ping, traceroute, nc, curl, nslookup, dhcp. The result is written to the terminal that started the run.
  • From the console. ping PC1 PC2, connect PC1 Server1 80, http PC1 Server1, associate Laptop1, stp.
  • Play. On an idle network Play boots any unconfigured, cabled, powered-on hosts, one at a time (see Settings), and then launches any ready Red Team actor. During a run it pauses and resumes.

The transport controls are Play/Pause, Step (advance one hop at a time, useful for following a single frame), Stop (Ctrl+C in a terminal does the same) and a Speed setting in milliseconds per hop (default 1000).

One run at a time. A second animated run is refused with the reason while yours is running or paused. A headless check (the console’s run, traceroute, or a scenario Check) stops the animated run first and says so. The terminal that started a run is read-only until it ends, but other devices’ terminals stay usable, so you can run arp -n or show ip route mid-run.

7. Reading the results

The packet list

Every animated run fills a Wireshark-style list in the Sim Log: one row per frame per wire crossing, with columns for number, step, source, destination, protocol, info and link. Rows are coloured by protocol and also lead with a monochrome glyph.

ARP ICMP request ICMP reply DHCP TCP DNS Errors (RST, NXDOMAIN, TTL exceeded)

Click a row (or a dot on the canvas) to pause the run and open the frame breakdown in the inspector: every Ethernet, IP and transport field. The row’s wire and both endpoint devices glow on the canvas so the list and the topology point at each other. The Packets / Events toggle switches to the narrative log of MAC learns, routing decisions and verdicts.

Filtering

Combine clickable protocol chips, a per-device dropdown and a Wireshark-style display filter. The three are ANDed, and a status line reads “Showing N of M”.

dns || icmp && !arp
ip.addr == 10.0.0.0/24
tcp.port == 22 && device contains PC

An invalid expression flags red but does not empty the list. Fields include ip, eth, tcp, device and frame; operators are ==, !=, <, >, contains, with CIDR matching on addresses.

Captures and Compare

Each finished run is archived (the last twelve are kept). Switch between them from the capture dropdown, or turn on Compare to see two runs side by side, baseline on the left. This is the way to check a fix: run, change one thing, run again, and read the difference.

Packet callouts

In the View tab, Packet callouts draws a small field summary beside each frame in flight. A field that the last hop rewrote (the MACs at a router, the source address at a NAT router) is underlined and pulsed, and a reply field echoed from its request is marked, so you can see exactly what changed at each hop.

8. Why? and Likely cause

RouteSim is built to explain itself. Every captured packet remembers what its sender logged, what its receiver did with it, and which earlier packet caused it.

  • Why? Under a frame’s field table, a summary sentence and then a chain of earlier packets, each a jump button, with the reason its sender gave (“PC-A has no ARP entry for 10.0.1.1, so it must learn that MAC address…”). In the console, why <packet no> prints the same.
  • Likely cause. When a ping, nc, curl, nslookup, dhcp or traceroute fails, or a scenario goal is unmet, a probe names the most probable misconfiguration, such as a gateway that no device owns. It names the cause and never the fix, and stays quiet when the failure already explains itself.
  • Post-mortems. A failed run says what happened in plain words: an ARP nobody answered (naming the default gateway when it is the culprit), a shut cable, an unauthorised 802.1X port, a spanning-tree block, a powered-off peer.

9. Console, scripts and sharing

The console (dock → Console) is a text front door to everything the GUI does. It is the same engine behind window.routesim and behind script files, so a topology can be built, run and checked from text.

add router R1
add computer PC1
add computer PC2
link PC1 R1
link PC2 R1
ip PC1 192.168.1.10/24
gateway PC1 192.168.1.1
ping PC1 PC2
help           # every command; "help ping" for one
  • Export a script (export or File → Export) writes your topology as a reproducible command script. Importing it replays it as one undo step.
  • Copy link (File tab) packs the whole network, and the scenario in progress, into the link itself (rs-web.html#net=…). Whoever opens it gets the network. The fragment never leaves the browser, so nothing is uploaded.
  • Autosave. The network on the canvas is kept in your browser’s storage and restored on your next visit. Turn it off in Settings, or open the page with ?autosave=0 for a visit that keeps nothing.
  • URL settings. A link can pre-set options, for example ?theme=dark&names=0&autodhcp=on&silentarp=1&speed=400.

Each line turns to a tick or a cross, with the reason beneath any failure. The banner can collapse to a small progress pill.

Part 2 · Simulation mechanics

What the engine does when you press Play, why it is built that way, and where it is honestly simpler than the real thing.

1. The model

RouteSim does not move “pings” or “connections”. It moves frames. A ping becomes a small cast of real Ethernet frames: an ARP request, an ARP reply, an ICMP echo request, an echo reply. Each is an object with source and destination MACs, optional IP and transport headers, and a payload. Every device on the path takes a frame in, decides what to do with it using the same information a real device would have, and emits zero or more frames in response.

That choice is the whole point. A learner can see why the first ping to a new host is slower than the second (the ARP), why a switch floods the first frame and not the next, and why traffic that crosses a router has different MAC addresses on each side while the IP addresses stay put.

Underneath is one mutable state object holding the devices, links and options, a callback registry that lets the engine ask for a redraw without importing the drawing code, and a deliberately small set of principles that decide hard cases:

  • Faithful to the protocols: real frame fields and real order of operations beat shortcuts.
  • Explain, don’t just show: every outcome carries a reason string a learner can act on.
  • Failure is a lesson: nothing fails silently; each drop says why.
  • Determinism: the same topology and the same inputs give the same result.

2. Anatomy of a run

Every run has four stages.

  1. Setup. A builder such as buildPingEvents validates the request and returns either an error string or a starting queue of events plus a table of frames waiting on ARP. Because validation returns before any run begins, every command’s error path is testable and costs nothing.
  2. Process. The engine dequeues one event and calls the handler for the receiving device’s type. Handlers exist for computers, servers, switches (and access points), routers, the internet cloud, hubs, firewalls, IDS sensors and the two attack hosts. A handler returns the frames it wants to send.
  3. Animate. Every outgoing frame passes through one admission point that applies the data-plane gates (a spanning-tree-blocked link, an unauthorised 802.1X port, an unassociated WiFi client, an unkeyed MACsec link) and, in animated runs, the link’s loss. An admitted frame becomes a dot that moves along the link at a speed scaled by the link’s latency. On arrival a row is added to the packet capture (capped at 1000 rows) and the arrive event is queued.
  4. Finish. A mode-specific result (ping statistics, a DHCP lease, an nmap-style table) is written to the origin device’s terminal, even if you are looking at another tab. The capture is archived for Compare, and the boot queue advances.

Animated and headless runs

The same handlers also run headless: the queue is drained synchronously, with no drawing, no capture and no loss. Headless runs power the console’s run, traceroute and scenario Check, so a check gives a stable answer even though your animated run drops frames on a lossy link. Where the two differ the difference is surfaced, not silent: a headless run notes each lossy link it ignored.

3. Layer 2: ARP, switching and VLANs

A host that wants to send to an IP on its own subnet needs the destination MAC, so it ARPs. The first frame it wanted to send is held in a pendingArp buffer and released when the reply arrives. If the destination is off-subnet, the host ARPs for its default gateway instead, which is why an unset gateway produces the diagnosis “never ARPs off-subnet”.

What a switch does

  • Learns the source MAC on the ingress port.
  • Forwards known unicast out the learnt port, floods broadcast and unknown unicast out every other port (within the VLAN).
  • Enforces 802.1Q: an access port belongs to one VLAN, a trunk carries tagged traffic with a native VLAN and an allowed list.
  • Honours spanning tree (section 5) and SPAN mirroring: a copy of selected traffic goes to a monitor port.

The learnt table is derived from the cabling, so any cable change invalidates it. Adding, removing or shutting a link flushes the dynamic entries on the affected LAN and recomputes the spanning tree, just as a real topology change would. A stale entry that survives anyway is forgotten with a logged reason and the frame flooded, never dropped.

A hub does none of this. It repeats every frame out every other port, so every device on it hears every frame. A router on a hub still takes up only frames addressed to its own interface MAC.

4. Layer 3: routing, TTL and ICMP errors

A router admits a frame only if it is addressed to the ingress interface’s MAC (or is a broadcast it handles locally, like DHCP). It then decides in a fixed order:

  1. Handle ARP on the interface.
  2. Check the TTL before the forwarding decision. At zero it drops the packet and sends an ICMP Time Exceeded back to the source.
  3. Apply NAT and the INPUT or FORWARD chains (section 7).
  4. Look up the destination by longest-prefix match, decrement TTL, rewrite the Ethernet header for the next hop, and ARP for that next hop if needed.

The routing table merges three sources in priority order: connected routes (metric 0), static routes (metric 1) and RIP-learned routes (metric 2 and up). An internet cloud presents an implicit default route to each router cabled to it.

traceroute is implemented the real way. It sends probes with TTL 1, 2, 3… (up to 30) and records who answered each: a router’s Time Exceeded marks an intermediate hop, and the destination’s echo reply marks the end. Because ICMP errors quote the offending datagram, traceroute still sees every hop from behind NAT.

Interfaces belong to ports. A router interface’s address, prefix, NAT role and MAC stay with the port when you unplug the cable and follow it onto the next cable, so moving a cable keeps the interface and only a cable on a different port creates a new one.

5. Control planes: RIP and spanning tree

Both are computed before each run and whenever the topology changes, and both are treated as derived state: recomputed from the live topology, never trusted from storage, never saved in undo snapshots.

RIP

runRipConvergence iterates up to 15 rounds, exchanging advertisements between RIP-enabled routers until a round changes nothing. Split horizon stops a route being advertised back where it came from, and metric 16 means unreachable. A network statement enables RIP on the interfaces it covers, and an adjacency forms only when both ends are covered. Neighbours are found per segment, not per cable: because RIPv2 multicasts, routers joined through a switch form adjacencies with each other. A router cabled to an internet cloud originates a default route into RIP, so routers several hops from the edge learn a way out.

Spanning tree (802.1D)

runStpConvergence elects a root bridge per connected set of switches (lowest priority, then lowest bridge MAC; the MAC derives from the switch’s name so the same script always builds the same tree). It costs each bridge to the root, gives every port a role (root, designated, alternate) and a state, and marks each alternate port as blocked. The block is enforced at the same admission gate as every other data-plane rule, so a redundant path is cut and the loop broken. Blocked links are drawn dashed amber.

Turn STP off on a looped topology and the point becomes visible: a broadcast circulates forever. The engine detects this by evidence rather than a step count: the same frame lineage crossing the same wire in the same direction, at the same TTL, a second time means a copy came back round the loop. The sim log names that wire. Because detection counts only steps that send frames, a large loop-free run is never mistaken for a storm.

6. Services: DHCP, DNS, TCP and HTTP

DHCP

The four-message exchange (Discover, Offer, Request, Ack) is handled by the client, a router or a server. A router leases from the usable range of its interface’s real prefix; a server leases from its configured dhcp-range and also hands out a router option and itself as nameserver. The client takes the first Offer, and a server only ACKs a Request that names it, so multi-server segments behave properly. A client that asks again keeps its address.

Network boot is deliberate. Adding or cabling a host does not configure it; pressing Play does, one host at a time, with a visible exchange. If DHCP times out and APIPA is enabled, the host self-assigns a link-local address, as a real machine would.

DNS

Name resolution is a real UDP/53 query that crosses switches, routers, firewalls and NAT. When a host pings or connects by name, it resolves first and launches the ICMP or TCP flow on the answer. An NXDOMAIN reply is drawn red. A server answers from its manual records and from an automatic zone containing every device’s hostname. Instant DNS short-circuits the query for beginners; turning it off requires a reachable nameserver, as in the real world.

TCP and HTTP

nc -z host port runs a genuine three-way handshake: SYN, then SYN-ACK if the port is listening (RST if not), then ACK. A silent drop produces a timeout, which reads differently from a refusal; that difference is what makes firewall DROP versus REJECT instructive. HTTP rides on top of the handshake: once established, the client sends a GET as a data segment and a server with its web service on answers 200 OK. An open port with no web service connects but gives an “empty reply”; a closed port is “connection refused”.

7. NAT and firewalling

NAT and PAT

Mark router interfaces ip nat inside or ip nat outside. An inside-to-outside flow is source-translated onto the outside address and recorded in the router’s translation table; TCP flows map by an allocated source port, and ICMP echo by its sequence. The return path is restored before the router considers the packet its own. The inspector lists the live table and flashes the entry a frame has just created or used. Port-forwarding is the inbound mirror: a static rule redirects a published outside address and port to an inside server, and the server’s reply is translated back.

Netfilter

Routers carry INPUT (traffic to the router itself) and FORWARD (traffic through it) chains; the transparent firewall device is FORWARD-only. Rules match protocol, source, destination, port and connection state. The filter is stateful: a connection-tracking table lets the canonical ruleset work, where default-drop plus accept ESTABLISHED,RELATED plus accept the inside hosts’ NEW traffic blocks unsolicited inbound flows while the inside hosts browse freely. REJECT answers back (a TCP RST, so a scan reads the port as closed, otherwise an ICMP unreachable) whereas DROP is silent. iptables and nft are two front doors onto one model, and rules round-trip between them.

8. Port security, encryption and detection

  • 802.1X. A switch port in auto mode blocks data until the supplicant authenticates. The EAP exchange runs supplicant, authenticator, RADIUS server and back, animated. A bad credential gets Access-Reject then EAP-Failure. Port control belongs to the port, so whatever is plugged in, a PC or a hub or anything else, is subject to it. Control frames such as EAPOL and BPDUs are exempt from the gates, as they must be.
  • MACsec (802.1AE). A link encrypted with a pre-shared key shows frames as encrypted in the packet list. A must-secure key mismatch drops traffic; should-secure falls back to plaintext. With dot1x the key is derived from the 802.1X exchange: the link stays unsecured until the port authenticates, then keys itself.
  • WiFi. A laptop associates to an access point over a matching SSID, with a visible probe, authentication and association exchange, plus the WPA2 four-way handshake on a secured network. A wrong password still associates but fails the key handshake, leaving the link unauthenticated and carrying no data.
  • IDS and SPAN. A managed switch copies selected traffic to its monitor port. The Snort sensor on that port is a passive sink: it parses your local.rules, matches mirrored frames, and records alerts. It cannot affect the traffic it watches.
  • Offensive hosts, for training. The Kali PC and Red Team actor share one engine, kept in its own module so it is easy to review in isolation. It models a SYN scan (an open port answers SYN-ACK, a closed one RST), a ping sweep, and ARP cache poisoning, and reports an nmap-style table. A host with IP forwarding enabled relays intercepted traffic on to its real next hop, so a victim’s connection keeps working while the extra hop appears in the packet list. The purpose is detection practice: pair these hosts with an IDS rule or a static ARP entry and see what each catches.

9. Failure and diagnosis

The sim is built so that a broken network teaches. Several layers cooperate:

  1. Reasoned gates. The data-path check returns a reason, not just a boolean: shut, spanning-tree blocked, WiFi password mismatch, unauthorised 802.1X port, failed MACsec, powered-off peer. Every “Network is unreachable” names the real cause, and “no link” appears only when there really is no cable.
  2. Step logs. Each handler logs why it did what it did (“No route to X, dropping”, “Cannot reply, no default gateway”). These strings are the raw material for everything below.
  3. Post-mortem. When a run ends, any ARP still waiting is an ARP nobody answered. It is explained on the device that waited, naming the default gateway when that is the cause and quoting the actual drop reason when the ARP died on the way.
  4. Why? chain. The engine tags each captured frame with what its sender logged, what its receiver logged, and the packet that caused it. The explain module walks that back into a causal chain.
  5. Likely cause. A prober looks at the failed flow in order: the origin, name resolution, the run’s decisive drops, then gateway, target, VLAN and return-path addressing, and names the most likely misconfiguration.

Observable symptoms match Linux where they can: a failed ping prints Time to live exceeded, Destination Port Unreachable or Destination Host Unreachable as the real tool would.

10. Determinism, randomness and loss

The engine is deterministic given a topology and a seed, and the tests depend on it. The values that are random in reality, TCP source ports, DHCP and DNS transaction ids, scan ports, APIPA addresses, and which frames a lossy link drops, come from a seeded per-run generator that is reseeded at the start of each run. By default it is seeded from the clock, so runs vary like real traffic. The console command seed <n> pins it, making captures, NAT translations and DHCP ids reproducible bit for bit. That is what makes Compare a true before-and-after diff: only your change differs, not the dice.

Link loss has its own stream, reseeded for every animated run. Frame ids are a monotonic counter with no wall-clock component. Any new engine randomness must draw from the seeded generator, never from the system clock or Math.random(), or reproducibility quietly breaks.

11. What is simplified

RouteSim aims to be faithful, but it is a teaching tool and is honest about where it simplifies. Knowing these edges stops them being surprises.

TimeNo clock. ARP never ages out; a MAC leaving the wire takes its cached ARP entries with it.Entries expire on timers.
HostsOne NIC per computer or server, so one cable.Multi-homed hosts.
Spanning treeOne tree per bridge (no per-VLAN trees), a fixed cost of 1 per link, instant convergence, loops across directly linked managed switches.PVST/RSTP, path costs, listening and learning timers.
RIPConverges before the run begins, up to 15 rounds.Periodic updates, timers, triggered updates.
AddressingIPv4 only.IPv6 and NDP.
Link bandwidthStored as metadata; it does not yet limit throughput.Congestion and queues.
TrafficDiscrete frames, one flow at a time, one animated run at once.Many concurrent flows.
LossApplied in animated runs only; headless checks stay deterministic and say so.Always present.
Firewall statenew and established are tracked; related and invalid parse but never match.Full conntrack.

The approach to every such choice is progressive disclosure: a legible default, with full fidelity one layer down. Silent protocols, Instant DNS and the Packets/Events toggle are all instances. A beginner can start simple and descend to the real thing when ready, without the tool becoming either a toy or a wall.
