# `src/engine.ts` — The simulation engine

The largest and most important module. Drives a ping/DHCP simulation through two phases — **process** (dequeue an event, run the per-device handler, collect outgoing frames) and **animate** (interpolate transit dots, deliver on arrival) — and implements per-device packet processing, routing, and RIP.

## Public API (lifecycle)
- **`startSimulation(setup, sourceId, targetIp, mode?, targetPort?)`** — returns `null` once the run is going, or the reason it was refused (see **Run ownership** below). Seeds the queue from a `PingSetup`/DHCP setup and starts the rAF animation loop. The setup's first event (an arrive at the first hop) is seeded as a **transit** rather than an arrive event, so the opening frame animates *off the source* — otherwise it would appear to originate at the connected switch/router (every later hop already animates because a completed transit creates the next arrive event). The headless runner keeps draining events directly.
- **`stopSimulation`, `pauseSimulation`, `resumeSimulation`, `stepOnce`** — sim controls (wired to the on-canvas play/pause/step buttons).
- **`syncSimLog()`** (now in **`src/simlog-view.ts`**, a presentation module — the engine calls it only through `sync().syncSimLog()`) — rebuilds the sim-log dock pane: the Wireshark-style **packet list** (`renderPacketTable` over the filtered `sim.capture`, columns via `packetColumns` in `frame.ts`) or the narrative **event view** (`renderEventLog` over `sim.log`), per `state.dock.logView`. In the packet view it also syncs the **capture-history controls** (`syncSimLogCaptureBar` — which saved run to view + the compare toggle/baseline, shown only when idle with ≥1 archived run) and the **display-filter toolbar** (`syncSimLogFilterBar`): the protocol chips (class-toggled, dimmed when absent from the capture), the device `<select>` (rebuilt from the devices present in the capture), the expression input (with an `invalid` marker on a parse error), and the "Showing N of M" / error status. The filter itself lives in [packet-filter.ts](packet-filter.md) (`applyLogFilter`); see also the **Packet capture** section below.
- **`startNetworkBoot()` / `unconfiguredBootableHosts()`** — network boot: adding/cabling/powering a host no longer configures it (it stays "unassigned"). When the user starts the sim — **Play** while idle calls `startNetworkBoot()` — every unconfigured, cabled, powered-on host (`unconfiguredBootableHosts`) boots with an **animated** DHCP exchange in turn (a `bootQueue` chained through `finishSimulation`), self-assigning **APIPA** (`169.254.x.y/16`) only after the simulated DHCP times out. The `dhcp` command boots one host the same way. Two **independent** global toggles gate this (`state.options.autoDhcp`/`apipaFallback`, in the **Settings** pane opened by the Main-tab cog button, both **off by default**): auto-DHCP on → animated DHCP, with `finishSimulation` self-assigning APIPA on timeout only if APIPA is on; auto-DHCP **off but APIPA on** → `bootNextHost` skips the DHCP frames and calls `assignApipa` directly (instant, no run); both off → `startNetworkBoot` boots nothing. A Play press that boots anything pushes exactly one undo entry; a user's run started mid-boot preempts it and cancels the rest of the queue (see **Run ownership**). `assignApipa(device)` is the shared link-local self-assign used by both the DHCP-failure fallback and the direct path.
- **`runSimulationHeadless(setup, sourceId, targetIp, mode?, targetPort?, purpose?)`** — never refused (an animated run in flight is stopped first, with a note naming `purpose` — see **Run ownership**); drains the queue synchronously (no rAF, no per-step render/terminal output — it sets `sim.headless`) and returns a `SimResult` (`{ success, ttl, responderIp, timeExceeded, unreachableFrom, assignedIp, assignedGateway, storm, diagnosis, log, steps }` — `storm` is the broadcast-storm flag, `diagnosis` the post-mortem's plain-language reasons; see **Failure diagnosis**). Powers the console `run` verb, `window.routesim`, scenario checks, and tests.
- **`runTraceroute(source, target, maxHops?)`** — resolves the target like ping (a name shortcuts to its IP only when **Instant DNS** is on; otherwise a real DNS query, which fails `unknown host` with no nameserver — review R16), warms ARP along the path, then sends probes with increasing TTL (1..maxHops) via `runSimulationHeadless`, recording each hop's responder (a router's ICMP Time-Exceeded, or the destination's Echo Reply). Returns a `TracerouteResult`; when a probe (or the ARP warm-up) storms it stops there with `storm: true` and the printers show `STORM_DIAGNOSIS` instead of 30 lines of `*`. A trace that does not reach the destination carries the last probe's post-mortem as `diagnosis`, printed after the hop list (the part real traceroute's `!H` plays): a missing on-subnet host, or a router's next hop that never answered ARP, is named rather than left as a column of `*`. Backs the `traceroute`/`tracert` command in the PC terminal and console.
- **`launchRedTeam(): boolean`** (moved to **`src/security/offensive/red-team.ts`**; it imports the engine's `startSimulation`, so it is no longer engine-side) — the autonomous **Play** trigger for the **Red Team actor**, filtered to **`type === "attacker"`**: when the canvas is idle and a *ready* actor exists (an IP and ≥1 enabled attack), it finds the first one, builds its frames via `buildAttackEvents` (`src/security/offensive/attacks.ts`), and `startSimulation(setup, attacker.id, "", "attack")`. A **Kali PC** (`type: "kali"`) is never launched this way. An unconfigured offensive host — Kali PC *or* Red Team actor — boots over DHCP like any other host: `hostNeedsBoot` asks the registry's `isBootable` role rather than a hand-written type list (the actor used to be missing from it, so Play reported "every host already has an address" and launched nothing). Wired into the ui.ts Play handler after `startNetworkBoot`, so a Play press boots any unconfigured hosts and, when there is nothing to boot, fires the attack. With actors placed but none ready, it says why on the status line (`redTeamNotReadyReason` — powered off; no IP, with or without a cable; no attacks enabled) instead of returning silently. See [red-team.md](red-team.md).

### Run ownership
One run owns `state.simulation` at a time. Both entry points go through the private **`beginRun`**, which settles whatever is in flight, converges RIP and STP, and then performs the **one** shared per-run reset (`resetRunState`). The two entry points used to carry byte-identical ~35-line copies of that reset and checked nothing, so a second command silently replaced a run mid-animation: its result never printed, its capture was never archived, the transport pill stayed up, and a preempted network boot resumed afterwards (review R5/R61). The mode union is now one name, **`SimMode`** (`types.ts`), and the run label (`runLabel`) and the headless success test (`runSucceeded`) are exhaustive `switch`es, so a new mode is a compile error rather than a silent "ping" fallback.

The policy is chosen for the learner:

| In flight | New animated run | New headless run |
|-----------|------------------|------------------|
| nothing | starts | starts |
| the user's animated run (running or paused) | **refused** with `RUN_BUSY` — that run is the lesson on screen, and the way out (wait, or Ctrl+C / Stop) is one keystroke away | the animated run is **stopped first** (the Stop teardown) — a headless run finishes in one call, so refusing it would only make the learner stop the animation by hand |
| a network-boot run | the boot is **preempted** — boot DHCP is background chatter Play started, not an experiment | the boot is stopped first |

Every preemption is surfaced, never silent (`preemptActiveRun`): a note in the interrupted run's terminal session, on the status line, and — through **`takePreemptionNote()`**, which `runConsoleCommand` collects after each verb — at the top of the console output (`Simulation stopped before it finished — a traceroute from PC3 needed the simulator.`, or `Network boot interrupted — …; 2 hosts still unassigned (press Play to finish booting).`). Any run that isn't part of the boot chain clears `bootQueue`, so the chain can't resume behind the user's run. The note names the run that needed the simulator in the learner's words (`describeRun`): an animated run by what it is (`a ping from PCA`, `a DHCP request from H1`), a headless one by the `purpose` its caller passes to `runSimulationHeadless` — `a traceroute from PC3` (`runTraceroute`), `the scenario Check` (`scenarios.ts`), `the console's \`run ping\`` (`cmdRun`) — or `a background check from …` when it names none; never the internal word "headless". A terminal command that preempts a run gets the note in its own session too (`runTerminalCommand` collects it, unless the interrupted run was that device's own).

**`animatedRunBlockReason()`** returns `RUN_BUSY` or `null`. Every caller that starts an animated run (the host shell's `ping`/`nc`/`curl`/`dhcp`/`nslookup`, the Kali shell, the console's animated verbs, the inspector's Launch/Associate buttons) checks it **before building its frames**: the builders reseed the run PRNG (`seedSimRng`), and reseeding under an in-flight run would rewind its stream — under a pinned seed, the run would no longer reproduce. `startSimulation` still refuses on its own as a backstop.

**A host's ARP cache holds on-link neighbours only.** A host answering a TCP SYN or a DNS query learns the sender through `learnOnLinkArp`, which files it only when the source address is on the host's own subnet. A routed packet arrives with the router's MAC as its source, so learning from it unconditionally listed every off-subnet client against the gateway's MAC in `arp -n` (display only — replies already went via the gateway; review R70).

**A renewing DHCP client keeps its address.** `allocateDhcpIp(iface, router, clientMac)` (router pools) and `allocateServerDhcpIp(device, clientMac)` (dnsmasq ranges) take the requester's MAC: its own lease and the address it currently holds are not counted as taken (`dhcpClientsOwn`), and its existing binding is offered again while it is still inside the pool and nobody else holds it. They used to treat the client's own lease as used, so a host that ran `dhcp` twice alternated between two addresses (review R69).

**A headless DHCP failure does not re-address the host.** With APIPA fallback on, the animated path self-assigns a link-local address when no server answers; a headless run (`run dhcp`, the scenario Check) observes only, so it leaves the host's address alone and surfaces the difference — a line in `SimResult.diagnosis` (which `run` prints) and a `sim-drop` log entry on the host. It used to assign 169.254.x.y, over a static address too, while reporting just "no response" (review R67).

**Undo points.** An animated run is an undo point (so the tables it learns can be undone) — except a boot run. `startNetworkBoot` arms **one** snapshot for the whole chain (and the direct-APIPA path, which had none), so one Ctrl+Z undoes one Play press rather than one host (review R59). It is taken lazily (`takeBootUndo`), the first time `bootNextHost` actually starts a boot run or assigns APIPA — a press whose every host fails to build its DHCP frames changes nothing, so it adds no undo entry and keeps the redo stack.

**The terminal lock follows the run.** `syncTerminal` derives the input lock on every sync from the same policy — `animatedRunBlockReason() !== null` — scoped to the session whose device started the run (see [terminal.md](terminal.md)), so no later re-render can unlock it mid-run, and a network boot (which a user's run may preempt) locks nothing; `finishSimulation`/`stopSimulation` unlock it simply by syncing, and `pauseSimulation`/`resumeSimulation`/`stepOnce` re-sync it so the placeholder says "paused".

**A headless run always ends.** `runSimulationHeadless` drains inside `try/finally`: a run that throws mid-drain is left `done` (events, transits and pending ARP cleared, `headless` false) instead of a stale `running` headless run, which would make `beginRun` refuse every later animated run and lock the origin terminal with no transport pill on screen to stop it from.

> Because `startSimulation` starts a `requestAnimationFrame` loop, it must **not** be called in unit tests with the preload's synchronous rAF stub (infinite recursion). Tests call the `processAt*` handlers (or `runSimulationHeadless`/`runTraceroute`) directly — or, for genuinely animated behaviour, stub rAF to a no-op and pump with `stepOnce()`. See [testing.md](../testing.md).

### Link cost (latency / loss)
A transit dot's crossing time is `sim.speed × latencyFactor`, where **`linkLatencyFactor(link)`** maps the link's `latency` (ms) to a clamped multiplier (10 ms = 1×, range 0.25–20×) baked onto each `ActiveTransit` — so a far/WAN link visibly crawls. A link's **`loss`** (%) probabilistically drops each forwarded frame at transit-creation time — drawn from the seeded link-loss stream (`lossRandom`, reseeded by `beginRun` for every animated run, so `seed <n>` reproduces which frames drop; see [prng.md](prng.md)) — but **only in animated runs** (`!sim.headless`), so headless reachability checks (scenarios, `run`) stay deterministic — and the divergence is **surfaced, not silent**: a headless run logs a note the first time it crosses each lossy link (`sim.lossNoted`, reset per run), so a passing check on a flaky wire explains itself; `bandwidth` is metadata for the future streams mode.

### Packet capture
During animated delivery, `deliverCompletedTransits` records each wire traversal into `sim.capture` (a `CaptureEntry`: running number, step, frame, endpoint devices, link — capped at 1000). This is the packet list the sim-log pane renders. Headless runs neither record nor clear the capture, so background boot chatter and scenario checks never wipe a visible packet list; `startSimulation`/`stopSimulation` do clear it.

### Display filtering
The packet list is **filterable** (`state.dock.logFilter`, a `LogFilter` of ANDed dimensions — protocol chips, a device select, an optional link id set by the link inspector's jump, and a display-filter expression). `syncSimLog` enriches each `CaptureEntry` into a `FilterRow` (`buildFilterRows` — the frame plus its wire endpoints) and runs `applyLogFilter` ([packet-filter.ts](packet-filter.md)) before `renderPacketTable`, so only matching frames are drawn while the underlying capture is untouched (clearing the filter shows them all again). The compiled expression predicate is cached by its source text, so re-filtering on every animation step is cheap. The filter is a *view* preference — it survives across runs (Wireshark keeps the display filter), but a deleted device referenced by the device dimension falls back to "All".

### Capture history (multi-run compare)
Each finished animated run is archived to `state.savedCaptures` (a `SavedCapture` ring, cap 12) by `saveCurrentCapture` in `finishSimulation`, with a derived label (`captureLabel` — mode + endpoints + ✓/✗) and a monotonic id (`cap-<index>`). `state.dock.captureView` selects which capture the packet list shows ("live" while a run animates, else a saved id), and `state.dock.compareBaseId` ("" = off) names a baseline shown **side by side** on the left in compare mode. `displayedPanes()` resolves these to the 1-or-2 panes `syncSimLog` renders; the device dropdown and chip-dimming span every displayed pane. Rows carry `data-cap` so a click resolves against the right capture (`captureEntriesFor`), and the selected-row highlight is scoped by entry identity (capture numbers restart per run). Starting a run points the view at "live"; stopping falls it back to the most recent saved run; loading a topology clears the history (the captures reference devices that no longer exist).

## Per-device processing
Each handler takes a device, an incoming frame, and the ingress peer id, and returns `OutgoingFrame[]`:

- **`processAtComputer`** — answers ARP for its own IP, replies to ICMP echo requests, marks ping success on echo reply, drives the DHCP client (Discover→Offer→Request→Ack, assigning IP/gateway/prefix and learning the router MAC on Ack), and speaks **TCP**: a SYN to a listening port (no `openPorts` list = listen on all; otherwise only those) answers SYN-ACK, a closed port answers RST, and the origin completes the handshake with ACK (`sim.tcpSuccess`). It also speaks **HTTP** (mode `"http"`): on the SYN-ACK the origin sends both the ACK and an **HTTP GET** (`createHttpRequest`, path `sim.httpPath`); a server with `config.httpEnabled` answers the GET with **200 OK** (`createHttpResponse`, body `config.httpTitle`), recorded at the origin as `sim.httpStatus`/`httpSuccess`/`httpServerTitle` — an open port with no web service leaves the GET unanswered (curl "Empty reply"), a closed port RSTs.
- **`processAtSwitch`** — MAC-learns on ingress, then forwards (known unicast) or floods (broadcast/unknown). A destination learnt on the ingress port is filtered (802.1D), with that reason in the log. The table is flushed on every link change (`linksChanged` — see [state.md](state.md)); as a backstop, an entry naming a port with no cable is treated as **stale** — forgotten (a `STATIC` one is only ignored), logged ("Stale MAC entry … no cable on that port now"), and the frame flooded as unknown unicast rather than dropped. Also the processor for the **access point** (an unmanaged L2 bridge). Managed switches enforce 802.1Q VLANs: access ports tag/untag, trunk ports carry allowed VLANs with a native VLAN. A `bpdu` frame early-returns to `handleBpdu` (like `dot11`/`dot1x`). When a managed switch carries a SPAN session (`SwitchConfig.mirror = { name, dest, sources? }`), the **monitor (`dest`) port is excluded from normal forwarding** and each ingress frame matching the session is **copied** to the monitor port's peer (`id` suffixed `-span`) — feeding a cabled IDS. Control frames terminated earlier (BPDU/dot11/dot1x) aren't mirrored (a documented simplification). See [ids.md](ids.md).
- **`processAtRouter`** — matches the ingress interface by peer, then dispatches: ARP → `handleRouterArp`, broadcast DHCP → `handleRouterDhcp` (allocates a lease, sends Offer/Ack), otherwise → `routeIpv4Frame`. **L2 admission comes first**, as a real NIC filters: an IPv4 frame is taken up only when its destination MAC is the ingress interface's MAC or a link-layer group address (broadcast/multicast, `isGroupMac` — the I/G bit). A unicast frame for another host — repeated by a hub, or flooded by a switch that hasn't learned the destination — is ignored with a `sim-learn` line ("is for <mac>, not this interface's MAC … not ours to route"); before this, a router on a hub segment routed the hosts' own on-link exchange and handed the recipient a TTL-63 duplicate. When two untagged interfaces share a peer (two cables to one hub or switch), the ingress interface is the one the frame is addressed to, so a frame for the second interface's MAC is admitted. A group-addressed frame is handled locally only (the DHCP server) and never routed off the segment. `handleRouterArp` learns from a reply only when it is sent to the interface's MAC (the answer to its own request), or is a broadcast (gratuitous) reply refreshing an entry the router already holds or is resolving — Linux's `arp_accept` off; a reply unicast to another host is not learned. Routing checks TTL **before** the forwarding decision (so an expired packet to an unrouteable destination still replies): on TTL 0 it drops the packet and sends an **ICMP Time-Exceeded** back from the ingress interface (the traceroute signal); otherwise it decrements TTL, rewrites L2 headers, and ARP-resolves on egress (buffering the frame in `pendingArp` on a miss). Both forward paths — immediate, and the flush when the ARP reply arrives — build a **fresh frame with a fresh payload** (`{ ...ipv4, ttl: ipv4.ttl - 1 }`); the inbound frame is never edited, because the capture, the wire's frame history and the inspector hold it by reference (the flush used to decrement the shared payload in place, so a cold-start routed ping showed its PC→router rows at TTL 63 and `ip.ttl == 64` missed them — review R17). The self-IP branch (after the INPUT chain accepts) answers ICMP echo to the router's own interface IP — and narrows on `payload.type === "icmp"` so a DHCP packet addressed to the router IP isn't mistaken for a self-ping. Nothing else on the router listens, and it says so the way a real kernel does: a TCP SYN gets a RST (`nc` reads "refused", not a DROP-like timeout) and a DNS query an ICMP Port Unreachable (via `rejectResponse`), each with a `sim-drop` line; anything else addressed to the router is logged as unhandled rather than swallowed.

- **`processAtInternet`** — the **internet cloud** (`type: "internet"`), an **L3 transit** that stands in for the public internet. It is **not** an L2 bridge: it routes IPv4 between the routers cabled to it, each on its own public subnet. Per connected router it derives a **gateway address** on that router's WAN subnet (`internetGatewayIp` in utils — the subnet's highest host) and **answers ARP** for it, so the router can resolve a default next-hop; an inbound IPv4 frame is forwarded to the connected router whose WAN subnet **owns the destination** (or is the destination), with the L2 header rewritten and TTL decremented (one L3 hop). On **TTL expiry** it sends an **ICMP Time-Exceeded** from the gateway it presents to the sending router — so the internet shows up as a real traceroute hop, not a silent gap. **The gateway answers ping**: an echo request to any gateway address the cloud presents (`isInternetGatewayIp` — the sender's own, or another site's) gets an echo reply from that address, since a hop traceroute shows and ARP resolves must not then read "No route to <gateway> on the internet" (review R23). Nothing else is served there, and the cloud says so as a router does for its own address: a TCP SYN gets a RST and a DNS query an ICMP Port Unreachable (`rejectResponse`), each with a `sim-drop` line saying the gateway answers ping only; anything else is logged and dropped. A destination no connected router owns is **dropped** ("No route … on the internet"). It keeps no MAC table, and applies the same L2 admission as a router: an IPv4 frame not sent to the gateway MAC it presents (`deriveMac(cloud.id)`) is ignored, not routed. The router side needs no manual config: `buildRoutingTable` adds an **implicit default route** (`0.0.0.0/0` via the cloud's gateway) for any interface cabled to an internet cloud, and `buildRipAdvertisements` **originates that default into RIP unconditionally** (like Cisco's `default-information originate`, via the shared `internetDefaultGateway` helper) so a router several hops from the edge still learns a way out — an edge itself never *learns* a default (`applyRipUpdates` skips `0.0.0.0/0` for internet-cabled neighbours, the default-route analogue of the connected-network skip), so dual-edge topologies stay symmetric and no edge's origination depends on iteration order. Paired with NAT out + a port-forward in, a private host reaches a service published at a different site (the `across-the-internet` scenario).

`processAtRouter` is decomposed into `handleRouterArp` / `handleRouterDhcp` / `routeIpv4Frame` for clarity; the orchestrator just matches the ingress interface and dispatches. When interfaces carry `ip nat inside`/`outside` marks, `routeIpv4Frame` also translates inside→outside flows and restores the return path — including **ICMP errors** (Time-Exceeded / Dest-Unreachable), matched on the error's embedded original datagram (`IcmpPayload.original`, populated by every error-generation site via `icmpOriginalOf`) since their sender isn't the flow's destination, which is what makes traceroute from behind NAT show every hop; a static **DNAT / port-forward** (`config.portForwards`) redirects an inbound connection to a published outside IP:port onward to an inside server (`dnatInbound` before the self/route decision) and source-translates the reply back (`dnatReturn`) — see [nat.md](nat.md); the router's own **stateful** netfilter INPUT (traffic to the router) and FORWARD (routed traffic) chains filter before delivery/forwarding — each classifying the frame's connection state, tracking accepted flows, and answering a REJECT with an RST/ICMP-unreachable, like the firewall device. The un-NAT happens before the FORWARD chain, so conntrack sees consistent tuples. See [firewall.md](firewall.md).

- **`processAtServer`** — answers DNS queries from its A-records (a `DnsPayload` response; unknown name → NXDOMAIN) and serves DHCP from its configured `dhcp-range` (`handleServerDhcp`, with router + nameserver options), both gated on `dnsmasqRunning`; everything else falls through to `processAtComputer`, so a server is also an ordinary host endpoint. See [dns.md](dns.md).

- **`processAtHub`** — a layer-1 repeater (the **Legacy** device class): copies every incoming frame out all other ports, with no MAC learning and no forwarding logic — the dumb predecessor to a switch (one collision domain; floods unicast too, which is the teaching contrast with a switch).
- **`processAtFirewall`** — a transparent inline packet filter: bridges ARP/control frames to the other port(s) and evaluates each IPv4 packet against the FORWARD chain. It first classifies the frame's connection state via `connectionState(device, ipv4)` — `"new"` (no matching conntrack entry) or `"established"` (the reply of a flow we already let out, matched on the swapped 5-tuple, or a later packet of one) — then runs `evaluateFirewall(device, ipv4, "FORWARD", conn)` (first-match-wins, else the chain policy) over `firewallRuleMatches(rule, ipv4, conn)` (src/dst CIDR, protocol, ICMP type, TCP dport, **connection state**). On ACCEPT it forwards and calls `trackConnection(device, ipv4)` to record the flow; on REJECT it emits a response via `rejectResponse` (a TCP RST for a TCP segment, else an ICMP destination-unreachable) rather than dropping silently; DROP discards. Logged with the state, e.g. `Firewall DROP … (FORWARD, new)`. Conntrack only runs when a rule uses `-m state` (`firewallUsesConntrack`), so a stateless ruleset has no per-frame cost; `related`/`invalid` parse but are never assigned. See [firewall.md](firewall.md).
- **`processAtIds`** — a passive Snort sensor: a **sink**, never in the data path. It runs the rule set (`config.idsRules`) against the mirrored frame via `runIdsRules` (`snort.ts`), appends any fast-alert line to `config.alerts` (capped, runtime-only — not serialised), logs a `sim-ids` line, and returns **no** outgoing frames — so it **alerts but never drops**. Fed the SPAN copy from `processAtSwitch`. See [ids.md](ids.md).
- **`processAttacker`** (in **`src/security/offensive/engine-logic.ts`**, injected into the engine via an `AttackContext` and wired into `PROCESSORS`; formerly the engine's `processAtAttacker`) — the shared **Kali-Linux attack handler** for both offensive host types: the hand-driven **Kali PC** (`type: "kali"`) and the autonomous **Red Team actor** (`type: "attacker"`). For ordinary host behaviour it delegates to `processAtComputer` (passed in via the context); the extra logic only fires during a sim in mode `"attack"`, where the offensive host is the run origin, on replies addressed to it: a **SYN-ACK** records an open port (`sim.scanOpen.push(srcPort)` + a `sim-attack` log), a **RST** records a closed one (`sim.scanClosed`), and an **ICMP echo reply** (`icmpType 0`) marks a live host (`sim.sweepLive`). The scan is **half-open** — it never completes the handshake with an ACK. Registered in the `PROCESSORS` map for **both** `attacker` and `kali`, so a hand-run Kali PC scan tallies too. See [red-team.md](red-team.md).

## Routing & RIP
- **`buildRoutingTable(router)`**, **`routingLookup`**, **`runRipConvergence`** now live in **`src/routing.ts`** (re-exported here for compatibility): the table merges connected (metric 0), static (metric 1), an **implicit internet default** (`0.0.0.0/0` via the cloud's gateway, metric 1) for any interface cabled to an `internet` cloud, and RIP-learned (metric 2+) routes — the internet default sits **after** statics (so an explicit default still wins) but **before** RIP (so a router on the internet prefers its own path over a default it might learn back from a LAN neighbour); the lookup resolves a destination to an egress interface. `routingLookup(router, dst, prebuilt?)` accepts an already-built table so a caller resolving several frames for one router in a single pass (an ARP reply flushing buffered frames) builds the table once instead of per frame. **Parsed once, compared as integers:** each `RouteEntry` carries its network parsed to a `Cidr` (`cidr`, utils.ts — null for a junk static network, which then never matches), the lookup parses the destination and next hop once, and the longest-prefix scan (`longestMatch`) is an AND and a compare per route — it used to re-validate and re-split the same strings about four times per route per frame. `buildRoutingTable` asks for `routerInterfacesWithNames(router, true)` — the cabled interfaces only (the only ones that carry routes) — so it doesn't build and discard a placeholder for every free port.
- **`runRipConvergence()`** — runs automatically before each simulation. **Learned routes are derived state**: every RIP router's `learnedRoutes` are cleared at the start and recomputed from the live topology (real RIP ages routes out on timers; the sim converges instantly, so a clean slate is the honest equivalent — a removed link or router takes its routes with it rather than leaving a stale, serialisable black hole). They are also **excluded from the config payload** (only `enabled`/`networks`/`passiveInterfaces` round-trip). Iterates up to 15 rounds exchanging advertisements between RIP-enabled routers until no route changes. **Neighbours are found per segment, not per cable** (`ripNeighboursOn`, once per interface per convergence): RIPv2 multicasts its updates, so an interface cabled to a switch, hub or access point is heard by every RIP router with an interface in the **same subnet on the same L2 segment** — same VLAN (a sub-interface's dot1q tag, or the access / trunk-native VLAN of the managed-switch port it plugs into), with a live path between them (`routerIfacesShareSegment` in simulation.ts, over `l2Reachable`: a shut cable, a powered-off bridge or a blocked link breaks it) — while an interface cabled straight to a router has that one neighbour. Routers joined through a core switch used to form no adjacency and fail with "No route", unexplained (review R19). Each end must still run RIP on its interface (a covering `network`, not passive), and a powered-off router neither sends nor learns. One simplification: a transparent firewall on the segment is a wire to this exchange — its rules are not applied to RIP's updates. Implements split-horizon (don't advertise a route back out the interface it was learned on) and metric 16 = unreachable. Decomposed into advertisement-building and update-applying helpers. Everything that can't change while it runs is computed **once per convergence** per router, on first touch (a `RipRouterView`): the named cabled interfaces, each interface's RIP-active flag (does a `network` statement cover its address — parsed via `cachedCidr`), its connected advertisements and originated default, its directly-connected network set (never learned), whether it is an internet edge, and a `network → route` index over `learnedRoutes` (replacing a linear `find` per advertisement). The per-iteration work is then building this round's advertisements and applying them — no string parsing in the inner loops. Learned routes and their order are byte-identical to the string version (cross-checked on randomised topologies); the 15-router benchmark fell from ~4 ms to ~0.3 ms p50 on a fixture that does ~3× the work. Benchmarked.

## Routing lookup resolves the *selected* route's interface

`routingLookup` picks the longest-prefix route and then resolves the **stored** `RouterInterface` object (the engine reads and learns its ARP table, so a normalised copy would not do) by the stable identity the route carries — `RouteEntry.peerId` + `vlanTag`, set on connected routes by `buildRoutingTable`. It used to discard the chosen route and call `ifaceOnSubnet`, which returns the *first* raw interface whose subnet contains the address: with overlapping connected prefixes (`10.0.0.1/8` configured before `10.1.0.1/16`) a lookup for `10.1.2.3` selected the `/16` route and then egressed via the `/8` interface. Static and RIP routes resolve their next hop the same way — through the best *connected* route containing it (longest prefix; only live, un-shut interfaces make the table) — rather than the first raw subnet match. The old `ifaceOnSubnet` fallback is **gone** (it ignored shutdown and peer state — review R18): an unresolvable route now returns no egress rather than silently leaving via a dead interface. A **static whose next hop is not inside a live connected route is marked `inactive`** (`RouteEntry.inactive`): it is listed by `show ip route` (without the `>*` selected marker, like FRR) but never forwards and never adds its prefix to `seen`, so it no longer black-holes traffic or shadows a working RIP route or internet default. Still a single allocation-free pass. Tested in `tests/engine.test.ts` for both configuration orders, object identity, a static next hop, and the inactive-static cases.

## Router log lines name interfaces as the CLI does

A stored router interface is keyed by its peer's id (plus a VLAN tag for a sub-interface) and carries no name; the name — `Ethernet1`, `Serial2`, `Ethernet1.10` — is derived from the cabling by `routerInterfacesWithNames`. The router's log lines used to print `iface.name || iface.peerId`, so `Route … via`, `ARP miss … on`, `Received ARP … on`, `NAT … (PAT via …)` and `Forward deferred … via` named the interface by its peer's UUID — an explanation no learner could match to anything on screen (review R52).

`ifaceName(router, iface)` (engine.ts) now resolves the same name `show ip interface brief` and the inspector show. An interface with no port name (a cable beyond the port count) reads `the interface to <peer device>` — never an id.

These lines are written per routed frame and deriving names enumerates the router's cables, so the name map is **cached per router**: dropped at the start of every run (`resetRunState`), rebuilt when the device or link list changes (the identity + length test the lookup indexes in `devices.ts` use), and rebuilt once on a key it does not hold (a sub-interface made since). The `processAtRouter` benchmarks log a `Route … via` line per call, so they cover the lookup; their p99 is unchanged.

## Host replies go via the configured gateway

A host's **reply** (ICMP echo reply, TCP SYN-ACK/RST, DNS answer, HTTP response) now makes the same next-hop decision as a frame it *originates* (`buildFollowOnFrames`): an on-link peer directly, otherwise the **configured default gateway**, resolved through ARP — `hostReplyPath` decides, `emitHostReply` sends or buffers the reply behind an ARP Request in `sim.pendingArp` (the host's ARP-reply handler stamps the learnt MAC and flushes it). Replies used to reflect to the ingress frame's source MAC, so a host with a **wrong** gateway still answered across subnets — hiding exactly the misconfiguration the tool exists to teach. Now a wrong gateway ARPs into silence and the ping fails; an off-subnet gateway is diagnosed ("gateway X is not on this host's subnet"). `hostHasReturnRoute` remains the first gate (no address / no gateway at all). The origin's own follow-ups (ACK, GET) still reflect, which is correct: it resolved its gateway when it sent the SYN.

## One admission path for every transmission

`admitOnLink(device, link, frame)` is the single place a frame is admitted onto a cable: the data gate (link-layer control frames exempt via `isControlFrame` — dot11/BPDU and the EAPOL/EAP legs of 802.1X — but a `dot1x` **RADIUS** frame models RADIUS/UDP and is treated as data, so a failed must-secure MACsec or otherwise-blocked switch↔server link drops it; review R94) — whose drop line is `linkDataBlockReason`'s plain-language reason plus the frame (`SW Ethernet2 is under 802.1X control and PC2 has not authenticated — … — ARP Req dropped`), not a causeless "not authenticated" — and per-link packet loss (animated runs only; a headless run notes the lossy link once). Both `processNextStep`'s outgoing loop **and the seeded first leg in `startSimulation`** go through it — the initial transit used to be created directly, so the first frame crossed even a 100 %-loss link and a one-way attack still landed.

## Failure diagnosis

Every way a run can fail states why (CLAUDE.md, "Failure is a lesson"). Four pieces carry the reason from where it is known to where the learner reads it:

- **The data gate's reason** — `linkDataBlockReason(link)` (devices.ts) names the cause a link drops data: administratively down, spanning-tree blocked, a WiFi SSID or password mismatch (`wifiLinkBlockReason` — the laptop re-pointed at another network, or a wrong key), an unauthorized 802.1X port (force-unauthorized vs. an `auto` port whose host has not authenticated), or a failed MACsec link (mismatched keys, mismatched keying methods, or a must-secure end facing a bare peer). `admitOnLink` logs it, the shut-link drop in `processNextStep` logs it, and `findFirstHop` (simulation.ts) returns it, so the builders' errors read `Network is unreachable (LT1 ↔ AP1 never authenticated — the laptop's WiFi password does not match the access point's)` instead of "(no link)" — which now means only that there is no cable.
- **The powered-off guard** — `processNextStep` checks `device.poweredOff` once, before dispatch, and logs `<name> is powered off — <frame> dropped`. The processors' own early-outs remain (they are exported and called directly), but a run no longer loses frames there silently.
- **The post-mortem** — `finishSimulation` runs `runPostMortem(succeeded)` before clearing the queues. A storm is the whole story; otherwise every `sim.pendingArp` entry still holding frames is an ARP nobody answered, explained by `explainUnansweredArp` and logged on the device that waited: a host's **default gateway** ("… is this host's default gateway and no device answered for it — is the gateway address right …"), an on-subnet target, or a router's next hop. When the ARP was not ignored but **dropped on the way**, the drop's own reason replaces that generic hint: every drop path that can lose an ARP (the data gate in `admitOnLink`, link loss, a shut cable, the powered-off guard) files its reason in `sim.arpDrops`, keyed by the address being resolved (a request's target, a reply's sender) and flagged `atOwner` when the frame was headed into the device that owns that address. `arpDropReason` quotes an `atOwner` drop first; otherwise, when some device does own the address, any recorded drop (the ARP or its reply was lost on the path); when nothing owns it, a flooded copy dropped at someone else's port is beside the point and the "is the address right?" hint stands. A spanning-tree block is never filed, since the tree keeps every bridge reachable. So an unauthenticated 802.1X port, a failed MACsec link or a shut cable in front of the target reads `the ARP for 10.0.0.2 was dropped on the way — <reason>`, not "is the address right". A device with more than three silent addresses (a ping sweep) collapses to one line. A failed run also names any **stale ARP entry** (`staleArpEntries`) — a cache entry for one of the flow's endpoints (the target, the origin's gateway, nameserver or own address), or a router's next hop toward either end (`routingLookup`), whose MAC no cabled device presents any more (`liveMacsOf`, devices.ts; the owner, if any, from `macsOwnedBy`): a router (and the internet cloud) takes up only frames sent to its own interface MAC, so a routed flow addressed there is ignored and no unanswered ARP would otherwise explain the failure. (Hosts accept by destination IP, so a stale entry for an on-link host still delivers.) The line names the address, its role, the dead MAC and whose it was ("which belongs to R2's interface with no cable now"), and the remedy: `ip neigh flush all` on a host, or in the router's privileged mode for a router's entry. Removing a device or a router cable already drops every entry pointing at the MACs that left the wire (`forgetArpEntries` in `deleteSelection`/`deleteLink` — the stand-in for ARP ageing, which the clockless simulator lacks), so this mostly catches a changed MAC or an imported cache. The reasons land in `sim.diagnosis` (the origin's verbatim, others prefixed with their device name) → `SimResult.diagnosis`, the console `run` output, and — after a failed ping/nc/curl/nslookup — the origin's terminal. A run that **met its goal** (a sweep that found live hosts) logs its unanswered ARPs as plain `sim-arp` notes and leaves `diagnosis` empty: those silent addresses are expected, and the diagnosis explains failures. A storm is always reported.
- **The likely cause** — after the result and the post-mortem, a failed animated `ping` / `nc` / `curl` / `nslookup` / `dhcp` ends with one more line in the origin's terminal: `Likely cause: …` (`runHint` in hints.ts, kind `hint`) — what is most likely *wrong*, where the lines above say what *happened*. `runTraceroute` carries the same as `TracerouteResult.hint`, and the console's `run` prints it. See [hints.md](hints.md).
- **ICMP errors in the result** — the origin records a Destination Unreachable's sender in `sim.pingUnreachableFrom` (kept apart from `pingResponderIp`, which traceroute reads as the hop). A failed animated ping prints them as Linux does: `From 10.0.0.1 icmp_seq=1 Time to live exceeded`, `… Destination Port Unreachable`, and — when the origin's own ARP went unanswered — `From <self> icmp_seq=1 Destination Host Unreachable`, counted as `+N errors`. `run ping` appends the same in brackets, and `nslookup` against a host with nothing on UDP/53 reads `connection refused`.

## Router DHCP pool = the interface's real subnet

`allocateDhcpIp` leases from the interface's **usable range for its real prefix** (network+1 … broadcast−1), starting at the conventional `.100` when the network is a `/24` or larger, else at the first usable address, and falling back to the low addresses before reporting exhaustion. It used to lease from the textual `/24` slice (`.100–.254`) whatever the prefix, so a `/25` interface at `.129` leased `.100` from the *other* half and told the client it was on-subnet with a gateway it could never reach.

## 802.1X is correlated by the supplicant's MAC

`Dot1xPayload.supplicantMac` carries the initiating host's MAC through the exchange (set when the authenticator relays the identity to RADIUS, echoed back on Accept/Reject). RADIUS validates *that* host's credentials — not whichever device anywhere presents the same identity — and the authenticator authorises the port whose host has that MAC (`supplicantByMac`, falling back to identity). Two hosts presenting `alice` on separate ports no longer let a wrong password on one authorise the other's port.

## 802.1X port control is a property of the switch port

`dot1xLinkInfo` / `dot1xPortAuthorized` (devices.ts, feeding `linkAuthorizedForData`) key port control on the **switch port alone**: whatever is cabled to an `auto` or `force-unauthorized` port — a PC, a Kali PC, a Red Team host, a hub (and everything behind it), an access point's uplink, a router — faces the same gate, and a peer that can't or doesn't run a supplicant simply never authenticates. The gate used to apply only when the peer was a computer, laptop or server, so a Kali box on a locked port passed data as if it were open — the opposite of the NAC lesson. On a switch↔switch link both ends' port modes are checked. Which devices *can* be supplicants is the registry's `dot1xSupplicant` role (`isDot1xSupplicant`), shared by the `supplicant` command, `buildDot1xEvents` and the authenticator's identity fallback — every host, including the Kali PC and the Red Team actor (with valid credentials an attacker authenticates like anyone else).

## The 802.1X authenticator obeys the port-control mode

`handleDot1x` used to ignore `portAuth` (review R8): on a `force-unauthorized` port it relayed to RADIUS, set `link.dot1xAuthorized` and logged "the port is authorised, traffic may pass" while the data gate still held the port closed — and the stale flag then opened the port the moment it was switched to `auto`, with no exchange. Now, at EAPOL-Start, the switch reads its own port's mode (`dot1xPortFacing(sw, peerId)`, devices.ts) and behaves as the 802.1X PAE state machine does:

| Port mode | Answer to EAPOL-Start | RADIUS | `link.dot1xAuthorized` |
|---|---|---|---|
| `auto` | EAP-Request/Identity — the full exchange | asked | set by Access-Accept, cleared by Access-Reject |
| `force-unauthorized` | canned EAP-Failure | not asked | untouched (the gate is closed regardless) |
| `force-authorized` (default) | canned EAP-Success | not asked | untouched (the gate is open regardless; with no exchange there are no keys for a `macsec … dot1x` link to derive) |

Every 802.1X frame the handler emits is sourced from the sending device's **own unicast MAC** (`device.config.macAddress`, else a derived per-device MAC), never the PAE group address `01:80:C2:00:00:03` — that address is a *destination* (the supplicant's EAPOL-Start targets it), so echoing `frame.dstMac` into the reply's source put a multicast group address in the source MAC (review R94). The handler that decides a failure records why in `sim.dot1xFailure` — the forced-closed port (with the `portauth … auto` command to run), a switch with no RADIUS server attached, or an Access-Reject — and `runPostMortem` carries it into `SimResult.diagnosis`, so `run dot1x` prints the cause under `dot1x: authentication failed`. The supplicant's EAP-Failure line says "check the identity/password" only when credentials were actually checked.

The 802.11 handshake is SSID-aware at runtime, not only at link creation (review R15): `buildAssociationEvents` probes with the **laptop's** configured SSID, and `handleDot11`'s access-point branch answers a `probe-req` only when its SSID matches the one the AP broadcasts — a probe for a different network is dropped (`sim-drop`), the handshake stalls (no Probe Response, so `wifiAssociated` stays false), and the AP records the reason in `sim.wifiFailure`, which `runPostMortem` carries into `SimResult.diagnosis` exactly like `dot1xFailure`. So re-pointing the laptop with `ssid LT OtherNet` after it has associated fails both the animated join and the data path (`wifiLinkBlockReason`) instead of silently carrying traffic.

`portauth` (commands.ts) clears `link.dot1xAuthorized` on the port's cable whenever the mode **changes** (re-applying the same mode keeps the session), inside the same undo point, and says so in its output: a mode change ends the 802.1X session, as on a real switch.

## Two lifecycle details (LOW sweep)

- **Each captured frame carries its explanation.** `tagExplanation` (called once per step of an animated run) files what the device logged while handling a frame as that frame's `outcome`, as the `why` of every frame it sent in response, and records the handled frame's capture number as their `cause` — the data the "Why?" view walks back ([explain.md](explain.md)). The run's opening frames get `originReason`. Headless runs skip it.
- **Autoplay redraws once per tick.** In autoplay a step that sends nothing out is followed at once by the next (`settleStep`), so a broadcast reaching a LAN of N hosts is N steps inside one animation tick. Each step used to rebuild the packet list and redraw the canvas — up to 61 times in a tick on a 120-host LAN, for views nobody sees in between (review R110). `processNextStep` now wraps the step (`runNextStep`) with a depth counter: steps only set `stepViewsDirty`, and the outermost call syncs the sim log and renders once, after the last of them (in a `finally`, so a throwing handler still leaves the views current). Headless runs never mark it. `tests/capture.test.ts` counts the syncs per tick on a 40-host flood.
- **A device deleted mid-run no longer strands the simulation.** `processNextStep` used to `return` early when an event's target device was gone, skipping the completion check — if that was the last queued work the run sat on "running" with live controls. The drop is logged against the sender and the step still **settles** (`settleStep`: process the next event if any, else finish).
- **`syncSimLog` builds each pane's filter rows once** per sync (they were built twice — once for the union of present tokens, again per pane — every step of an animated run).

## `runSimulationHeadless` leaves no flag behind

The headless runner sets `sim.headless = true` for its duration and **restores it to `false` on exit**. It used to leave `true` on the shared state, so a scenario Check (or a console `run`) changed how the next UI sync interpreted the simulation until something started a new animated run.

## Spanning tree (STP)
- **`runStpConvergence()`** (in **`src/stp.ts`**, re-exported here) — runs automatically before each simulation, right after `runRipConvergence()` (both `startSimulation` and `runSimulationHeadless`). Computes the spanning tree across managed switches and mutates `config` in place (like `runRipConvergence`), electing a root per connected component and marking each alternate port's link `link.stpBlocked`. The blocked flag folds into `linkAuthorizedForData(link)` (devices.ts) alongside WiFi/802.1X/MACsec, so the two frame-path chokepoints (`findFirstHop`/the engine transit step) drop **data** on a blocked link (and `l2Reachable`, the L2 path query behind RIP's neighbour discovery, does not cross it); the transit step's control-frame `ctrl` set now includes `"bpdu"`, so BPDUs (alongside `dot11`/`dot1x`) bypass the gate. See [stp.md](stp.md) for the model.
- **`handleBpdu`** — relays a Configuration BPDU arriving on a bridge's root port out its designated ports (root cost + 1), toward other switches only; it terminates (never loops). `processAtSwitch` early-returns here for `bpdu` frames. `buildStpEvents` (simulation.ts) seeds the flood from each root bridge's designated ports for the animated `stp`/headless `run stp` mode.
- **Broadcast storm** — with STP off and an L2 loop, frames multiply without bound. A storm is detected **by evidence, identically on both paths**: `loopedBack` (called by `processNextStep` for every frame put on a wire) keys each crossing by the frame's **lineage** (`frameLineage` — the id it was created with; flood/route/firewall/SPAN copies only append a suffix), the wire, the direction and the IPv4 TTL, in the per-run `sim.loopTrace`. In a loop-free network a lineage crosses each wire at most once per direction, however many hosts a broadcast reaches; seeing a key again means a copy **came back round a switching loop**, which with no TTL at layer 2 circulates forever. That step logs the evidence on the sender (`ARP Req came back round to cross PC2 ↔ SW2 (SW2 → PC2) again — a switching loop: …`) and finishes the run. The TTL in the key keeps an IP routing loop (each lap one hop older, ended by Time-Exceeded) from reading as a storm; a host's sends are skipped (it never forwards, so each is a new lineage). The only backstop is `STORM_BACKSTOP_STEPS=10000` steps that put frames on the wire (`sim.wireSteps` — not every event, so hosts ignoring a flood don't count), shared by both paths; `drainHeadless` has no cap of its own. This replaced a fixed animated cap (`STORM_STEP_CAP=200` events / `STORM_TRANSIT_CAP=250`) that counted every host ignoring a flooded broadcast, so a loop-free 8-host sweep or a DHCP lease on a large LAN was stopped as a "storm" the headless run never saw (R2), while the headless run spun 10000 drain iterations before calling a real one. Detection sets `sim.stormDetected`, surfaced by `finishSimulation` ("Broadcast storm…") and the status line on an animated run, and — on **both** paths — by the post-mortem: a `sim-drop` `STORM_DIAGNOSIS` line on the origin, `SimResult.storm` + `diagnosis` for a headless run (`run ping` prints it; `runTraceroute` stops at the storming probe). Headless storms used to be invisible: `run ping` read "unreachable — 13998 steps" and traceroute printed 30 `*` lines. `finishSimulation` then clears the terminal event/transit queues so a stopped storm cannot retain thousands of frames or stale link references after a topology edit. The `silentStp` display option hides BPDU animation like the other silent protocols.

## Red Team (attack mode)
- **`SimulationState.mode`** gains **`"attack"`**, and `SimulationState` gains the attack accumulators **`scanOpen: number[]`**, **`scanClosed: number[]`**, **`sweepLive: string[]`**, and **`arpPoisoned: string[]`** — all cleared at each run start, as is every offensive host's `attackLog` (both `attacker` and `kali`). `processAttacker` fills the scan/sweep ones and `recordArpPoison` fills `arpPoisoned` (both now in **`src/security/offensive/engine-logic.ts`**; `recordArpPoison` runs at the engine's ARP-reply learn sites through the injected `AttackContext`); `SimResult.success` for an attack is `scanOpen.length > 0 || sweepLive.length > 0 || arpPoisoned.length > 0` (review R48).
- **`SERVICE_NAMES`** (in `src/security/offensive/engine-logic.ts`) maps a port to its service name (e.g. 21:ftp, 22:ssh, 23:telnet, 80:http, 443:https, 3306:mysql, 3389:rdp) for the report.
- **`finishSimulation`'s `"attack"` branch** writes an **nmap-style report** (built by `buildAttackReport` in `src/security/offensive/engine-logic.ts`): a `PORT  STATE  SERVICE` table of the **open and closed** ports (named via `SERVICE_NAMES`), a `Hosts up: N (...)` line for a sweep, and an `ARP cache poisoned on: …` line (review R48), falling back to "No open ports or live hosts found" only when nothing was found. It writes the report to the origin's terminal session **and** stashes it on `origin.config.attackLog` for the inspector.
- The attack frame builders (`buildScanEvents`/`buildSweepEvents`/`buildArpSpoofEvents`/`buildAttackEvents`) live in **`src/security/offensive/attacks.ts`** and are documented there and in [red-team.md](red-team.md); `launchRedTeam` (now in `src/security/offensive/red-team.ts`) is the **Play** trigger that runs them. See [red-team.md](red-team.md) for the full attacker model.

## How it fits

`engine.ts` sits at the centre of the simulation: it consumes `simulation.ts`'s event setup, creates response frames via `frame.ts`, reads/writes device config (ARP/MAC/DHCP tables) on `state`, and calls `sync().render()`/`sync().syncSimLog()` to animate. **It imports no view and no device shell** (review R106): a run's result is appended to the origin device's session with `sessionFor`/`appendSessionLine`, the Sim Log is opened with `showDock`, and the terminal is re-rendered through `sync().syncTerminal()` — all `state.ts` — so the engine is in no import cycle. Tests that assert on a view the engine refreshes register the real one (`registerNoopCallbacks({ syncTerminal })`). Forwarding decisions reuse `devices.ts` (interface enumeration) and `simulation.ts`/`utils.ts` (subnet maths).
