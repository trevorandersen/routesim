# `src/inspector.ts` — Right panel (device config & link history)

Builds the right-hand inspector panel: device configuration forms, the device list, link frame history, and display options. Like the rest of the UI it rebuilds HTML imperatively into `dom.detailsPanel` and re-binds event handlers each sync. Rows that a control re-renders *within* a sync (the port-count spinners redraw the switch port rows and router interface rows in place) are wired by **delegation on their stable container**, so a partial re-render can neither lose their listeners nor stack a second set.

## Key exports

### Panel orchestration
- **`renderFramePanel(frame)`** — the click-a-packet view: a full field table (Ethernet/ARP/IPv4/ICMP/TCP/DNS/DHCP) for a transit dot clicked mid-flight or a packet-list row; shown while `state.inspectedFrame` is set (the simulation pauses on capture). A packet-list row additionally sets `state.inspectedCapture`, which cross-links the canvas (its wire + endpoints glow — see [canvas.md](canvas.md)); the frame-panel Close clears both. The EtherType row labels the control sentinels `0x888e` (802.1X / EAPOL / 802.11) and `0x0802` (Spanning Tree / BPDU), and the payload table dispatches on `payload.type` for `dot11` (802.11 subtype + SSID), `dot1x` (802.1X subtype + identity), and `bpdu` (Configuration/TCN flavour, root/sending bridge id, root path cost, sending port). This also fixed a latent bug where `dot11`/`dot1x` frames fell through to the IPv4 branch and mis-rendered as IPv4. The breakdown goes as far as the packet list's label does: a segment carrying HTTP adds `HTTP request` (`GET /path HTTP/1.1`) + `Host`, or `HTTP response` (`HTTP/1.1 200 OK`) + `Page title`; a DHCP frame adds its `Transaction id` (`0x…`, via `dhcpXidText`), the `Requested IP` of a Request and the `Server identifier` — the fields that tell two competing servers' exchanges apart (review R102). Under the table, **`renderWhy(frame)`** adds the **Why?** section — the causal chain behind the frame (each earlier packet a jump button), then what its receiver did with it; see [explain.md](explain.md).
- **`syncPanel()`** — the entry point. Rebuilds the panel for the current selection: a link (editable name — empty reverts to the derived default — an **admin-status** shut toggle, **bandwidth/latency/loss** number fields, a **Delete link** button, and a frame-history summary: the count of frames this wire has carried plus a **View frames in the packet log** button that jumps to the Sim Log packet list filtered to this link — `state.dock.logFilter.link`, no inline per-frame list), nothing, or a device. Every panel opens with `panelHeading(title)` — the title (Selection/Configure/Link/Frame) plus the inspector close button, on one line and sticky at the top, so the close affordance stays in line with the heading as the panel scrolls. For a device it emits the name field, a **Terminal** button (CLI devices), a compact **Power / Delete** button row, then type-specific config fields, and wires all the inputs/buttons. Called via `sync().syncPanel()` whenever selection or config changes.
- **`syncDeviceList()`** — rebuilds the network device list (each row selects its device), followed by a **Cables** section listing every physical, visible link as a button that selects it — the keyboard path to the link inspector (review R103).

### Render helpers (return HTML strings)
- **`renderSwitchPorts(device)`** — per-port rows for a managed switch with an access/trunk **mode dropdown** and an **access-VLAN** or **trunk-native-VLAN** dropdown; unmanaged switches get a simpler peer/remove row. When spanning tree is on, each port also carries a **Root/Desig/Block** badge from `config.stp.ports[iface]` (`role`/`state`) — a `blocking` port reads "Block".
- **`renderSwitchVlans(device)`** — the VLAN list (a chip per VLAN with remove) plus an "Add VLAN" control.
- The router config panel opens with a **Role** select (Internal/core vs Border/edge → `config.role`, the border archetype drawing a "B" badge), above the Ethernet/Serial port counts.
- **`renderRouterInterfaces(device)`** — router interface rows, each stacked two lines: the interface name + peer name on top (peer right-aligned, ellipsised), the editable `address/prefix` input full-width below (a bare address keeps the prefix; the subnet shows as the tooltip). Stacking avoids the cramped horizontal layout that overlapped at narrow inspector widths. A **connected** port carries a `×` **unlink** button (deletes that port's cable, keeping the router selected); an **unconnected** port reads "not connected" (greyed) and still accepts an address — persisted by interface name via `routerInterfaceForName` ([devices.md](devices.md)), keyed by peer once a cable exists.
- **The device panel is a registry of sections** (`INSPECTOR_SECTIONS`, review R108). Each `InspectorSection` is `{ id, applies(device), render(device), bind?(device) }`; `syncPanel` renders every section that applies, in order, then calls their `bind`. The sections are `identity` (name/hostname), `actions` (Collapse / Expand / Terminal / Power / Delete), then one per kind of device — `host` (every IP end-system: addressing, plus the laptop's WiFi and the server's dnsmasq panel), `access-point`, `switch`, `router`, `firewall`, `ids`, `red-team`, `hub` — and `summary` (the type and link-count pills). `inspectorSectionsFor(device)` returns a device's list. Before this, `syncPanel` was one 444-line function with a branch per device type in its render half and again in its bind half. To change what a device shows, edit its section; **to add a device type, add a section** — `syncPanel` itself does not change. Two small helpers carry what sections share: `bindWifiControls` (laptop and access point) and `bindPortCountField` (switch and hub). The refactor was checked against the panel's HTML for all 13 device types, selected and configuring: identical.
- **The identity section's name field keeps names unique.** For `hasHostname` types it commits on change through `applyHostname`; for the rest (LAN, hub, unmanaged switch, AP, cloud) it is free text applied as it is typed. Both ask `deviceNameBlockReason` (devices.ts): a name another device has, in any case, is not applied — the field shows the reason as its validity message and reverts to the device's real name when it is left (review R38).
- **`syncPanel()` commits the field still being edited before it rebuilds** (`commitFocusedField`, review R45). A rebuild replaces the panel's HTML, and Firefox and Safari fire neither `blur` nor `change` on a focused field removed that way — so an address typed into PC-A and followed by a click on PC-B, or by a run finishing, was silently discarded and the undo snapshot taken on focus was orphaned. If the focused element is inside the panel it is blurred first, which fires both in every browser: the field commits through its own handler (to the device it was rendered for), as one undo step. A refused value is reported by that handler and does not stop the rebuild; focus outside the panel is left alone.
- **Edits take an undo point and surface their errors (review R92).** Ticking a Red Team attack pushes undo like any other edit. **Add VLAN** puts the mutator's answer on the status line and marks the field when the id is invalid (it used to look like a button that did nothing). A bad **STP priority** stays in the field with the reason on it and on the status line instead of snapping back silently — the rule is `stpPriorityError` (terminal/switch.ts), shared with the switch shell and the console's `stp`. The firewall's port-count field takes its range from `FIREWALL_PORT_RANGE`.
- **`renderDnsmasqSection(device)`** — the server's service panel: dnsmasq daemon state (start/stop), an **HTTP service** toggle (`config.httpEnabled`) with a **web page title** field (`config.httpTitle`, shown when enabled), DNS A-records (add/remove), the DHCP range/router-option fields, a **RADIUS users** editor (identity/password add/remove for the 802.1X back end), and a **listening TCP ports** field (comma-separated, 1–65535). `bindDnsmasqControls` wires them all.
- **Server fields commit through the shell's mutators** (`bindDnsmasqControls`, review R57). The DHCP range, the router option and the listening ports commit on **change** (blur/Enter) through `setDhcpRange` / `setDhcpRouterOption` / `setListeningPorts` ([terminal.md](terminal.md)) — the same functions the dnsmasq shell and the `ports` command call, so there is one validation. The range's two bounds are committed **together**: with one bound typed and no range stored yet, nothing is written until the other arrives. A refused value stays in its field with the reason as its validation message and on the status line; nothing is stored and no undo point is taken. Before this the range was written per field and per keystroke with a weaker check, so the inspector could store an inverted range the shell refuses — the engine then reported "no addresses available" and the exported script would not replay. **The listening-ports field shows all three listener states** (review R91): empty = any port, a list = those ports, and the word `closed` = an empty list (refuse everything) — with a note beneath saying which is in force. It takes the forms the `ports` command does (`80, 443` or `80 443`; `closed`; empty, `none` or `any`). Refuse-all used to render as an empty field, indistinguishable from accept-all, and committing the field flipped the server to accept-all.
- **`renderStpSection(device)`** — the managed-switch **Spanning-tree** section: an **Enabled** toggle, a **bridge priority** field (0–61440, step 4096, default 32768), and a one-line **status** (disabled / "this switch is the root bridge" / `root <id> · path cost <n>` from the derived `config.stp.bridgeId`/`rootId`/`rootCost`). See [stp.md](stp.md).
- **`renderMirrorSection(device)`** — the managed-switch **SPAN (port mirroring)** section: a **monitor-port dropdown** that picks the session destination from the switch's interfaces (a blank option turns mirroring off), and — once a destination is set — per-port **source checkboxes** for each *other* cabled port (the monitor port is excluded). Writes `config.mirror`: all ticked omits `sources` (mirror every port), a subset stores that list — see [ids.md](ids.md). Only managed switches carry it.
- **`renderIdsSection(device)`** — the IDS sensor's panel: a **`local.rules` textarea** (`config.idsRules`, one raw Snort line per row) plus the **alert log** (`config.alerts`, the runtime fast-alert lines — not serialised) with a **Clear** button. See [ids.md](ids.md).
- **`renderAttackerSection(selected)`** (moved to **`src/security/offensive/inspector.ts`**; imported here into `INSPECTOR_SECTIONS`) — the **Red Team actor's** (`selected.type === "attacker"`) **attack** panel: a **target** text input (`#selectedAttackTarget`, placeholder "e.g. 10.0.0.10 or SRV"), three **attack** checkboxes (`.attack-check`: scan / sweep / arp-spoof) bound to `config.attacks`, a **Launch attacks** button (`#launchAttack`), and a `<pre class="attack-log">` showing the last run's report (`config.attackLog`). Inserted after the IDS config fields. A **Kali PC** (`type: "kali"`) gets no attack panel — it has no stored plan and is driven from its terminal — so only the actor renders this. See [red-team.md](red-team.md).
- **`renderFirewallControls(device, chains)`** — the editable **netfilter** panel under Configure for routers (`["forward", "input"]`) and the transparent firewall (`["forward"]` only): a per-chain **default-policy** select (ACCEPT/DROP), the rule list (`renderFirewallRules`), and an **add-rule form** (`.fw-add-form`) — a target select (ACCEPT/DROP/REJECT), a chain select (`#fwAddChain`, only when the device has more than one chain), a protocol select (`#fwAddProto`: any / ICMP / TCP / UDP), a **connection-state** select (`#fwAddState`, options "any state" / NEW / "ESTABLISHED,RELATED" / "NEW,ESTABLISHED" — for `-m state` stateful rules), source/dest/dport inputs, an **Add rule** button (`#fwAddRule`), and a `#fwAddError` note line. It writes the same `config.rules`/`config.policy` the `iptables` CLI does. See [firewall.md](firewall.md).
- **`renderFirewallRules(device)`** — the rule list (`<ol class="fw-rule-list">`), one deletable row per rule showing the target badge, the chain, and the assembled iptables match — `-p`, `-s`, `-d`, `--icmp-type`, `--dport`, plus `--state <STATES>` (the rule's `states` upper-cased and comma-joined) and `--reject-with <type>` for stateful and REJECT rules; an empty list reads "No rules — the default policy applies to all traffic."
- **`renderArpTable`, `renderMacAddressTable`** — read-only tables.

### Binding & misc
- **`bindSwitchPortControls(device)`** — wires the switch/hub port rows and the managed-switch VLAN list by delegation: a `change` listener on `#switchPortList` routes the mode/VLAN/native dropdowns to the `terminal/` mutators (`setSwitchPortMode`/`setSwitchPortVlan`/`setSwitchTrunkNative`), a `click` listener there routes each port's link-remove button (`.port-remove`, via `closest`, so a click on its SVG counts) to `deleteLink`, and `click`/`keydown` listeners on `#switchVlanList` route Add VLAN (button or Enter) and the chip removes to `addSwitchVlan`/`removeSwitchVlan`. The mutators `pushUndo` and re-sync. Bound once per sync: the Ethernet-ports spinner redraws `#switchPortList` with no rebind, which used to stack a second Add-VLAN listener — one click, two adds and a dead undo entry (R90).
- **`bindRouterInterfaceList(device)`** — wires the router interface rows by delegation on `#routerInterfaceList`: an `input` listener commits each `.router-interface-ip` (`address/prefix`, keyed by peer or, for an empty port, by interface name; an invalid entry sets a validity message and stores nothing), `captureUndoOnFocusWithin` makes each edit one undo step, and a `click` listener routes the `.iface-unlink` × to `deleteLink`. The Ethernet/Serial spinners redraw the rows in place; the per-row listeners syncPanel used to bind were lost there, so an IP typed after a port-count change was silently dropped (R6).
- **`bindStpControls(device)`** — wires the Spanning-tree enable toggle and bridge-priority field to `setSwitchStp`, which `pushUndo` and reconverges (the `recomputeStp` callback re-runs `runStpConvergence` — see [stp.md](stp.md)).
- **`bindMirrorControl(device)`** — wires the monitor-port dropdown **and the source checkboxes** to `setSwitchMirror` ([terminal/switch.ts](terminal.md)), which `pushUndo` and re-syncs (a blank selection clears the session; changing the monitor port resets sources to the whole switch; a checkbox change stores the ticked subset, or omits `sources` when all are ticked). The session name is preserved across edits.
- **`bindIdsControls(device)`** — wires the `local.rules` textarea (commits the edited rule lines into `config.idsRules`) and the alert-log **Clear** button (empties `config.alerts`), each `pushUndo` and re-sync.
- **`bindAttackerControls(selected)`** (also in **`src/security/offensive/inspector.ts`**) — wires the **Red Team actor's** attack controls (actor only, alongside `renderAttackerSection`): the target input commits on change (to `config.attackTarget`); the `.attack-check` checkboxes set `config.attacks`; the **Launch attacks** button calls `buildAttackEvents` then `startSimulation(setup, id, "", "attack")`. See [red-team.md](red-team.md).
- **`bindFirewallControls(device, chains)`** — wires the netfilter panel (`renderFirewallControls`): the per-chain policy selects, the per-rule delete buttons, and the add-rule form. Reading the state select (`#fwAddState`) and storing it as `rule.states` — a comma-split array (so "ESTABLISHED,RELATED" becomes `["established", "related"]`), omitted for "any state". Mutates the same `config.rules`/`config.policy` as the `iptables` CLI, with the same validation (a `--dport` needs `-p tcp`; src/dst must be a valid IPv4 or CIDR), each edit `pushUndo` + re-sync. See [firewall.md](firewall.md). The **Add rule** form does not validate for itself: it states its fields as iptables flags (`-p tcp --dport 22 -j ACCEPT`) and calls **`appendFirewallRule`** (terminal/iptables.ts), the body of `iptables -A` — one parser and one set of checks for both front doors, and a refusal shows the shell's own message. (The form used to disagree with the shell: it read `1e2` as port 100 and took addresses the shell rejects — review R114.)
- **Options & layout** — `syncOptionControls`, `syncNetworkPanel`, `setNetworkPanel`, `toggleDisplayOptions`, plus the inspector-resize drag handlers (`setInspectorWidth`, `start`/`move`/`stopInspectorResize`).

## Behaviour notes

- **Config shows on selection** for all device types (selecting a device reveals its editable config — IP/MAC for computers, ports/VLANs for switches, interfaces for routers). The Configure tool/double-click select too, and additionally auto-open the device's terminal when it has one (the `openTerminal` callback, gated by `canOpenTerminal`).
- **Host IPv4 fields show and accept `address/prefix`** (a bare address keeps the existing prefix), with the derived subnet displayed live beneath the field (`refreshSubnetNote`). A pill beside the label shows the **address source** — `static` / `DHCP` / `APIPA`, or `unassigned` when there's none (`ipSourceInfo`/`config.ipSource`; a bare IP with no recorded source reads as static). When unassigned the field placeholder reads `0.0.0.0`. Hosts also expose a **DNS nameserver** field (`config.dnsServerIp`, the `/etc/resolv.conf` equivalent).
- The **power button** on hosts toggles power state only — an unconfigured host stays "unassigned" until the simulation is started (Play boots it via animated DHCP — see [engine.md](engine.md)).
- **The host fields and the Terminal button read the device registry's roles**: `isHost(selected.type)` gates the host IP / gateway / DNS / MAC fields, and the Terminal button shows wherever `offersTerminal(selected)` holds (every CLI device; a switch only when managed) — no hand-written type lists, so it can't drift from `CLI_DISPATCH`. Port-count inputs fall back to `defaultPortCount(type)`.
- **`isHost` includes both `"kali"` and `"attacker"`**, so both offensive hosts get the standard host IP / gateway / DNS / MAC fields alongside everything else a host shows. Only the **Red Team actor** additionally gets its attack section (`renderAttackerSection`), inserted into the device config panel after the IDS config fields; a **Kali PC** gets the plain host inspector and is driven from its terminal. For these offensive hosts the static-config fields are **live, not dead** — committing one runs the matching Linux command through the device terminal (the Kali terminal falls through to the host shell), exactly like a computer. See [red-team.md](red-team.md).
- A host's **IP / gateway / DNS / MAC** fields don't mutate config directly — committing one (blur/Enter), or a clear/random button, runs the matching device-CLI command via `terminal.runDeviceCommand` (e.g. `ip addr add 10.0.0.5/24 dev eth0`). The command appears in the host's terminal flagged **`injected`** (dark-grey styling — simulator-issued), validates server-side (no client-side clipping — an invalid value shows the command's error), and the command's mutator pushes undo + re-syncs.
- Other text inputs call `captureUndoOnFocus` so the whole edit is one undo step.
- All dynamic values (device/interface/VLAN names) are passed through `escapeHtml` before insertion.

## How it fits

`inspector.ts` reads `state` (selection + config), mutates config directly (or via `terminal/` mutators for VLAN edits), and re-renders. It reuses `devices.ts` interface enumeration (`switchInterfacesWithNames`, `routerInterfacesWithNames`), `frame.ts` for link history rendering, and `normalise.ts` for VLAN data. Its render helpers are unit-tested for the expected HTML.
