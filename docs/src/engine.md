# `src/engine.ts` — The simulation engine

The largest and most important module. Drives a ping/DHCP simulation through two phases — **process** (dequeue an event, run the per-device handler, collect outgoing frames) and **animate** (interpolate transit dots, deliver on arrival) — and implements per-device packet processing, routing, and RIP.

## Public API (lifecycle)
- **`startSimulation(setup, sourceId, targetIp, mode?)`** — seeds the queue from a `PingSetup`/DHCP setup and starts the rAF animation loop. The setup's first event (an arrive at the first hop) is seeded as a **transit** rather than an arrive event, so the opening frame animates *off the source* — otherwise it would appear to originate at the connected switch/router (every later hop already animates because a completed transit creates the next arrive event). The headless runner keeps draining events directly.
- **`stopSimulation`, `pauseSimulation`, `resumeSimulation`, `stepOnce`** — sim controls (wired to the on-canvas play/pause/step buttons).
- **`syncSimLog()`** — rebuilds the sim-log dock pane: the Wireshark-style **packet list** (`renderPacketTable` over the filtered `sim.capture`, columns via `packetColumns` in `frame.ts`) or the narrative **event view** (`renderEventLog` over `sim.log`), per `state.dock.logView`. In the packet view it also syncs the **capture-history controls** (`syncSimLogCaptureBar` — which saved run to view + the compare toggle/baseline, shown only when idle with ≥1 archived run) and the **display-filter toolbar** (`syncSimLogFilterBar`): the protocol chips (class-toggled, dimmed when absent from the capture), the device `<select>` (rebuilt from the devices present in the capture), the expression input (with an `invalid` marker on a parse error), and the "Showing N of M" / error status. The filter itself lives in [packet-filter.ts](packet-filter.md) (`applyLogFilter`); see also the **Packet capture** section below.
- **`startNetworkBoot()` / `unconfiguredBootableHosts()`** — network boot: adding/cabling/powering a host no longer configures it (it stays "unassigned"). When the user starts the sim — **Play** while idle calls `startNetworkBoot()` — every unconfigured, cabled, powered-on host (`unconfiguredBootableHosts`) boots with an **animated** DHCP exchange in turn (a `bootQueue` chained through `finishSimulation`), self-assigning **APIPA** (`169.254.x.y/16`) only after the simulated DHCP times out. The `dhcp` command boots one host the same way. Two **independent** global toggles gate this (`state.options.autoDhcp`/`apipaFallback`, in the **Settings** pane opened by the Main-tab cog button, both **off by default**): auto-DHCP on → animated DHCP, with `finishSimulation` self-assigning APIPA on timeout only if APIPA is on; auto-DHCP **off but APIPA on** → `bootNextHost` skips the DHCP frames and calls `assignApipa` directly (instant, no run); both off → `startNetworkBoot` boots nothing. `assignApipa(device)` is the shared link-local self-assign used by both the DHCP-failure fallback and the direct path.
- **`runSimulationHeadless(setup, sourceId, targetIp, mode?)`** — drains the queue synchronously (no rAF, no per-step render/terminal output — it sets `sim.headless`) and returns a `SimResult` (`{ success, ttl, responderIp, timeExceeded, assignedIp, assignedGateway, log, steps }`). Powers the console `run` verb, `window.routesim`, scenario checks, and tests.
- **`runTraceroute(source, target, maxHops?)`** — warms ARP along the path, then sends probes with increasing TTL (1..maxHops) via `runSimulationHeadless`, recording each hop's responder (a router's ICMP Time-Exceeded, or the destination's Echo Reply). Returns a `TracerouteResult`. Backs the `traceroute`/`tracert` command in the PC terminal and console.
- **`launchRedTeam(): boolean`** — the autonomous **Play** trigger for the **Red Team actor**, filtered to **`type === "attacker"`**: when the canvas is idle and a *ready* actor exists (an IP and ≥1 enabled attack), it finds the first one, builds its frames via `buildAttackEvents` (simulation.ts), and `startSimulation(setup, attacker.id, "", "attack")`. A **Kali PC** (`type: "kali"`) is never launched this way — an unconfigured offensive host boots over DHCP like any other host (`hostNeedsBoot` now includes `kali`). Wired into the ui.ts Play handler after `startNetworkBoot`, so Play boots hosts and then, if nothing else is running, fires the attack. See [red-team.md](red-team.md).

> Because `startSimulation` starts a `requestAnimationFrame` loop, it must **not** be called in unit tests with the preload's synchronous rAF stub (infinite recursion). Tests call the `processAt*` handlers (or `runSimulationHeadless`/`runTraceroute`) directly — or, for genuinely animated behaviour, stub rAF to a no-op and pump with `stepOnce()`. See [testing.md](../testing.md).

### Link cost (latency / loss)
A transit dot's crossing time is `sim.speed × latencyFactor`, where **`linkLatencyFactor(link)`** maps the link's `latency` (ms) to a clamped multiplier (10 ms = 1×, range 0.25–20×) baked onto each `ActiveTransit` — so a far/WAN link visibly crawls. A link's **`loss`** (%) probabilistically drops each forwarded frame at transit-creation time, but **only in animated runs** (`!sim.headless`), so headless reachability checks (scenarios, `run`) stay deterministic — and the divergence is **surfaced, not silent**: a headless run logs a note the first time it crosses each lossy link (`sim.lossNoted`, reset per run), so a passing check on a flaky wire explains itself; `bandwidth` is metadata for the future streams mode.

### Packet capture
During animated delivery, `deliverCompletedTransits` records each wire traversal into `sim.capture` (a `CaptureEntry`: running number, step, frame, endpoint devices, link — capped at 1000). This is the packet list the sim-log pane renders. Headless runs neither record nor clear the capture, so background boot chatter and scenario checks never wipe a visible packet list; `startSimulation`/`stopSimulation` do clear it.

### Display filtering
The packet list is **filterable** (`state.dock.logFilter`, a `LogFilter` of ANDed dimensions — protocol chips, a device select, an optional link id set by the link inspector's jump, and a display-filter expression). `syncSimLog` enriches each `CaptureEntry` into a `FilterRow` (`buildFilterRows` — the frame plus its wire endpoints) and runs `applyLogFilter` ([packet-filter.ts](packet-filter.md)) before `renderPacketTable`, so only matching frames are drawn while the underlying capture is untouched (clearing the filter shows them all again). The compiled expression predicate is cached by its source text, so re-filtering on every animation step is cheap. The filter is a *view* preference — it survives across runs (Wireshark keeps the display filter), but a deleted device referenced by the device dimension falls back to "All".

### Capture history (multi-run compare)
Each finished animated run is archived to `state.savedCaptures` (a `SavedCapture` ring, cap 12) by `saveCurrentCapture` in `finishSimulation`, with a derived label (`captureLabel` — mode + endpoints + ✓/✗) and a monotonic id (`cap-<index>`). `state.dock.captureView` selects which capture the packet list shows ("live" while a run animates, else a saved id), and `state.dock.compareBaseId` ("" = off) names a baseline shown **side by side** on the left in compare mode. `displayedPanes()` resolves these to the 1-or-2 panes `syncSimLog` renders; the device dropdown and chip-dimming span every displayed pane. Rows carry `data-cap` so a click resolves against the right capture (`captureEntriesFor`), and the selected-row highlight is scoped by entry identity (capture numbers restart per run). Starting a run points the view at "live"; stopping falls it back to the most recent saved run; loading a topology clears the history (the captures reference devices that no longer exist).

## Per-device processing
Each handler takes a device, an incoming frame, and the ingress peer id, and returns `OutgoingFrame[]`:

- **`processAtComputer`** — answers ARP for its own IP, replies to ICMP echo requests, marks ping success on echo reply, drives the DHCP client (Discover→Offer→Request→Ack, assigning IP/gateway/prefix and learning the router MAC on Ack), and speaks **TCP**: a SYN to a listening port (no `openPorts` list = listen on all; otherwise only those) answers SYN-ACK, a closed port answers RST, and the origin completes the handshake with ACK (`sim.tcpSuccess`). It also speaks **HTTP** (mode `"http"`): on the SYN-ACK the origin sends both the ACK and an **HTTP GET** (`createHttpRequest`, path `sim.httpPath`); a server with `config.httpEnabled` answers the GET with **200 OK** (`createHttpResponse`, body `config.httpTitle`), recorded at the origin as `sim.httpStatus`/`httpSuccess`/`httpServerTitle` — an open port with no web service leaves the GET unanswered (curl "Empty reply"), a closed port RSTs.
- **`processAtSwitch`** — MAC-learns on ingress, then forwards (known unicast) or floods (broadcast/unknown). Also the processor for the **access point** (an unmanaged L2 bridge). Managed switches enforce 802.1Q VLANs: access ports tag/untag, trunk ports carry allowed VLANs with a native VLAN. A `bpdu` frame early-returns to `handleBpdu` (like `dot11`/`dot1x`). When a managed switch carries a SPAN session (`SwitchConfig.mirror = { name, dest, sources? }`), the **monitor (`dest`) port is excluded from normal forwarding** and each ingress frame matching the session is **copied** to the monitor port's peer (`id` suffixed `-span`) — feeding a cabled IDS. Control frames terminated earlier (BPDU/dot11/dot1x) aren't mirrored (a documented simplification). See [ids.md](ids.md).
- **`processAtRouter`** — matches the ingress interface by peer, then dispatches: ARP → `handleRouterArp`, broadcast DHCP → `handleRouterDhcp` (allocates a lease, sends Offer/Ack), otherwise → `routeIpv4Frame`. Routing checks TTL **before** the forwarding decision (so an expired packet to an unrouteable destination still replies): on TTL 0 it drops the packet and sends an **ICMP Time-Exceeded** back from the ingress interface (the traceroute signal); otherwise it decrements TTL, rewrites L2 headers, and ARP-resolves on egress (buffering the frame in `pendingArp` on a miss). The self-IP branch answers ICMP echo to the router's own interface IP — and narrows on `payload.type === "icmp"` so a DHCP packet addressed to the router IP isn't mistaken for a self-ping.

- **`processAtInternet`** — the **internet cloud** (`type: "internet"`), an **L3 transit** that stands in for the public internet. It is **not** an L2 bridge: it routes IPv4 between the routers cabled to it, each on its own public subnet. Per connected router it derives a **gateway address** on that router's WAN subnet (`internetGatewayIp` in utils — the subnet's highest host) and **answers ARP** for it, so the router can resolve a default next-hop; an inbound IPv4 frame is forwarded to the connected router whose WAN subnet **owns the destination** (or is the destination), with the L2 header rewritten and TTL decremented (one L3 hop). On **TTL expiry** it sends an **ICMP Time-Exceeded** from the gateway it presents to the sending router — so the internet shows up as a real traceroute hop, not a silent gap. A destination no connected router owns is **dropped** ("No route … on the internet"). It keeps no MAC table. The router side needs no manual config: `buildRoutingTable` adds an **implicit default route** (`0.0.0.0/0` via the cloud's gateway) for any interface cabled to an internet cloud, and `buildRipAdvertisements` **originates that default into RIP unconditionally** (like Cisco's `default-information originate`, via the shared `internetDefaultGateway` helper) so a router several hops from the edge still learns a way out — an edge itself never *learns* a default (`applyRipUpdates` skips `0.0.0.0/0` for internet-cabled neighbours, the default-route analogue of the connected-network skip), so dual-edge topologies stay symmetric and no edge's origination depends on iteration order. Paired with NAT out + a port-forward in, a private host reaches a service published at a different site (the `across-the-internet` scenario).

`processAtRouter` is decomposed into `handleRouterArp` / `handleRouterDhcp` / `routeIpv4Frame` for clarity; the orchestrator just matches the ingress interface and dispatches. When interfaces carry `ip nat inside`/`outside` marks, `routeIpv4Frame` also translates inside→outside flows and restores the return path — including **ICMP errors** (Time-Exceeded / Dest-Unreachable), matched on the error's embedded original datagram (`IcmpPayload.original`, populated by every error-generation site via `icmpOriginalOf`) since their sender isn't the flow's destination, which is what makes traceroute from behind NAT show every hop; a static **DNAT / port-forward** (`config.portForwards`) redirects an inbound connection to a published outside IP:port onward to an inside server (`dnatInbound` before the self/route decision) and source-translates the reply back (`dnatReturn`) — see [nat.md](nat.md); the router's own **stateful** netfilter INPUT (traffic to the router) and FORWARD (routed traffic) chains filter before delivery/forwarding — each classifying the frame's connection state, tracking accepted flows, and answering a REJECT with an RST/ICMP-unreachable, like the firewall device. The un-NAT happens before the FORWARD chain, so conntrack sees consistent tuples. See [firewall.md](firewall.md).

- **`processAtServer`** — answers DNS queries from its A-records (a `DnsPayload` response; unknown name → NXDOMAIN) and serves DHCP from its configured `dhcp-range` (`handleServerDhcp`, with router + nameserver options), both gated on `dnsmasqRunning`; everything else falls through to `processAtComputer`, so a server is also an ordinary host endpoint. See [dns.md](dns.md).

- **`processAtHub`** — a layer-1 repeater (the **Legacy** device class): copies every incoming frame out all other ports, with no MAC learning and no forwarding logic — the dumb predecessor to a switch (one collision domain; floods unicast too, which is the teaching contrast with a switch).
- **`processAtFirewall`** — a transparent inline packet filter: bridges ARP/control frames to the other port(s) and evaluates each IPv4 packet against the FORWARD chain. It first classifies the frame's connection state via `connectionState(device, ipv4)` — `"new"` (no matching conntrack entry) or `"established"` (the reply of a flow we already let out, matched on the swapped 5-tuple, or a later packet of one) — then runs `evaluateFirewall(device, ipv4, "FORWARD", conn)` (first-match-wins, else the chain policy) over `firewallRuleMatches(rule, ipv4, conn)` (src/dst CIDR, protocol, ICMP type, TCP dport, **connection state**). On ACCEPT it forwards and calls `trackConnection(device, ipv4)` to record the flow; on REJECT it emits a response via `rejectResponse` (a TCP RST for a TCP segment, else an ICMP destination-unreachable) rather than dropping silently; DROP discards. Logged with the state, e.g. `Firewall DROP … (FORWARD, new)`. Conntrack only runs when a rule uses `-m state` (`firewallUsesConntrack`), so a stateless ruleset has no per-frame cost; `related`/`invalid` parse but are never assigned. See [firewall.md](firewall.md).
- **`processAtIds`** — a passive Snort sensor: a **sink**, never in the data path. It runs the rule set (`config.idsRules`) against the mirrored frame via `runIdsRules` (`snort.ts`), appends any fast-alert line to `config.alerts` (capped, runtime-only — not serialised), logs a `sim-ids` line, and returns **no** outgoing frames — so it **alerts but never drops**. Fed the SPAN copy from `processAtSwitch`. See [ids.md](ids.md).
- **`processAtAttacker`** — the shared **Kali-Linux attack handler** for both offensive host types: the hand-driven **Kali PC** (`type: "kali"`) and the autonomous **Red Team actor** (`type: "attacker"`). For ordinary host behaviour it delegates to `processAtComputer`; the extra logic only fires during a sim in mode `"attack"`, where the offensive host is the run origin, on replies addressed to it: a **SYN-ACK** records an open port (`sim.scanOpen.push(srcPort)` + a `sim-attack` log), a **RST** records a closed one (`sim.scanClosed`), and an **ICMP echo reply** (`icmpType 0`) marks a live host (`sim.sweepLive`). The scan is **half-open** — it never completes the handshake with an ACK. Registered in the `PROCESSORS` map for **both** `attacker` and `kali`, so a hand-run Kali PC scan tallies too. See [red-team.md](red-team.md).

## Routing & RIP
- **`buildRoutingTable(router)`**, **`routingLookup`**, **`runRipConvergence`** now live in **`src/routing.ts`** (re-exported here for compatibility): the table merges connected (metric 0), static (metric 1), an **implicit internet default** (`0.0.0.0/0` via the cloud's gateway, metric 1) for any interface cabled to an `internet` cloud, and RIP-learned (metric 2+) routes — the internet default sits **after** statics (so an explicit default still wins) but **before** RIP (so a router on the internet prefers its own path over a default it might learn back from a LAN neighbour); the lookup resolves a destination to an egress interface. `routingLookup(router, dst, prebuilt?)` accepts an already-built table so a caller resolving several frames for one router in a single pass (an ARP reply flushing buffered frames) builds the table once instead of per frame.
- **`runRipConvergence()`** — runs automatically before each simulation. **Learned routes are derived state**: every RIP router's `learnedRoutes` are cleared at the start and recomputed from the live topology (real RIP ages routes out on timers; the sim converges instantly, so a clean slate is the honest equivalent — a removed link or router takes its routes with it rather than leaving a stale, serialisable black hole). They are also **excluded from the config payload** (only `enabled`/`networks`/`passiveInterfaces` round-trip). Iterates up to 15 rounds exchanging advertisements between RIP-enabled routers until no route changes. Implements split-horizon (don't advertise a route back out the interface it was learned on) and metric 16 = unreachable. Decomposed into advertisement-building and update-applying helpers. Router interface normalisation is **memoised per run** for performance, and the whole thing is benchmarked.

## Routing lookup resolves the *selected* route's interface

`routingLookup` picks the longest-prefix route and then resolves the **stored** `RouterInterface` object (the engine reads and learns its ARP table, so a normalised copy would not do) by the stable identity the route carries — `RouteEntry.peerId` + `vlanTag`, set on connected routes by `buildRoutingTable`. It used to discard the chosen route and call `ifaceOnSubnet`, which returns the *first* raw interface whose subnet contains the address: with overlapping connected prefixes (`10.0.0.1/8` configured before `10.1.0.1/16`) a lookup for `10.1.2.3` selected the `/16` route and then egressed via the `/8` interface. Static and RIP routes resolve their next hop the same way — through the best *connected* route containing it (longest prefix; only live, un-shut interfaces make the table) — rather than the first raw subnet match. Still a single allocation-free pass; `ifaceOnSubnet` remains as the fallback. Tested in `tests/engine.test.ts` for both configuration orders, object identity, and a static next hop.

## Host replies go via the configured gateway

A host's **reply** (ICMP echo reply, TCP SYN-ACK/RST, DNS answer, HTTP response) now makes the same next-hop decision as a frame it *originates* (`buildFollowOnFrames`): an on-link peer directly, otherwise the **configured default gateway**, resolved through ARP — `hostReplyPath` decides, `emitHostReply` sends or buffers the reply behind an ARP Request in `sim.pendingArp` (the host's ARP-reply handler stamps the learnt MAC and flushes it). Replies used to reflect to the ingress frame's source MAC, so a host with a **wrong** gateway still answered across subnets — hiding exactly the misconfiguration the tool exists to teach. Now a wrong gateway ARPs into silence and the ping fails; an off-subnet gateway is diagnosed ("gateway X is not on this host's subnet"). `hostHasReturnRoute` remains the first gate (no address / no gateway at all). The origin's own follow-ups (ACK, GET) still reflect, which is correct: it resolved its gateway when it sent the SYN.

## One admission path for every transmission

`admitOnLink(device, link, frame)` is the single place a frame is admitted onto a cable: the auth/STP data gate (control frames exempt) and per-link packet loss (animated runs only; a headless run notes the lossy link once). Both `processNextStep`'s outgoing loop **and the seeded first leg in `startSimulation`** go through it — the initial transit used to be created directly, so the first frame crossed even a 100 %-loss link and a one-way attack still landed.

## Router DHCP pool = the interface's real subnet

`allocateDhcpIp` leases from the interface's **usable range for its real prefix** (network+1 … broadcast−1), starting at the conventional `.100` when the network is a `/24` or larger, else at the first usable address, and falling back to the low addresses before reporting exhaustion. It used to lease from the textual `/24` slice (`.100–.254`) whatever the prefix, so a `/25` interface at `.129` leased `.100` from the *other* half and told the client it was on-subnet with a gateway it could never reach.

## 802.1X is correlated by the supplicant's MAC

`Dot1xPayload.supplicantMac` carries the initiating host's MAC through the exchange (set when the authenticator relays the identity to RADIUS, echoed back on Accept/Reject). RADIUS validates *that* host's credentials — not whichever device anywhere presents the same identity — and the authenticator authorises the port whose host has that MAC (`supplicantByMac`, falling back to identity). Two hosts presenting `alice` on separate ports no longer let a wrong password on one authorise the other's port.

## Two lifecycle details (LOW sweep)

- **A device deleted mid-run no longer strands the simulation.** `processNextStep` used to `return` early when an event's target device was gone, skipping the completion check — if that was the last queued work the run sat on "running" with live controls. The drop is logged against the sender and the step still **settles** (`settleStep`: process the next event if any, else finish).
- **`syncSimLog` builds each pane's filter rows once** per sync (they were built twice — once for the union of present tokens, again per pane — every step of an animated run).

## `runSimulationHeadless` leaves no flag behind

The headless runner sets `sim.headless = true` for its duration and **restores it to `false` on exit**. It used to leave `true` on the shared state, so a scenario Check (or a console `run`) changed how the next UI sync interpreted the simulation until something started a new animated run.

## Spanning tree (STP)
- **`runStpConvergence()`** (in **`src/stp.ts`**, re-exported here) — runs automatically before each simulation, right after `runRipConvergence()` (both `startSimulation` and `runSimulationHeadless`). Computes the spanning tree across managed switches and mutates `config` in place (like `runRipConvergence`), electing a root per connected component and marking each alternate port's link `link.stpBlocked`. The blocked flag folds into `linkAuthorizedForData(link)` (devices.ts) alongside WiFi/802.1X/MACsec, so the three chokepoints (`l2Reachable`/`findFirstHop`/the engine transit step) drop **data** on a blocked link; the transit step's control-frame `ctrl` set now includes `"bpdu"`, so BPDUs (alongside `dot11`/`dot1x`) bypass the gate. See [stp.md](stp.md) for the model.
- **`handleBpdu`** — relays a Configuration BPDU arriving on a bridge's root port out its designated ports (root cost + 1), toward other switches only; it terminates (never loops). `processAtSwitch` early-returns here for `bpdu` frames. `buildStpEvents` (simulation.ts) seeds the flood from each root bridge's designated ports for the animated `stp`/headless `run stp` mode.
- **Broadcast storm** — with STP off and an L2 loop, frames multiply without bound. The headless path caps via `MAX_STEPS=10000`; the animated path caps via `STORM_STEP_CAP=200` / `STORM_TRANSIT_CAP=250`. Either sets `sim.stormDetected`, surfaced by `finishSimulation` ("Broadcast storm…") and the status line. `finishSimulation` then clears the terminal event/transit queues so a capped run cannot retain thousands of frames or stale link references after a topology edit. The `silentStp` display option hides BPDU animation like the other silent protocols.

## Red Team (attack mode)
- **`SimulationState.mode`** gains **`"attack"`**, and `SimulationState` gains the scan accumulators **`scanOpen: number[]`**, **`scanClosed: number[]`**, and **`sweepLive: string[]`** — all cleared at each run start, as is every offensive host's `attackLog` (both `attacker` and `kali`). `processAtAttacker` fills them (see above); `SimResult.success` for an attack is `scanOpen.length > 0 || sweepLive.length > 0`.
- **`SERVICE_NAMES`** maps a port to its service name (e.g. 21:ftp, 22:ssh, 23:telnet, 80:http, 443:https, 3306:mysql, 3389:rdp) for the report.
- **`finishSimulation`'s `"attack"` branch** builds an **nmap-style report**: a `PORT  STATE  SERVICE` table of the open ports (named via `SERVICE_NAMES`) plus a `Hosts up: N (...)` line for a sweep, falling back to "No open ports or live hosts found". It writes the report to the origin's terminal session **and** stashes it on `origin.config.attackLog` for the inspector.
- The attack frame builders (`buildScanEvents`/`buildSweepEvents`/`buildArpSpoofEvents`/`buildAttackEvents`) live in `simulation.ts` and are documented there and in [red-team.md](red-team.md); `launchRedTeam` (above) is the engine-side **Play** trigger that runs them. See [red-team.md](red-team.md) for the full attacker model.

## How it fits

`engine.ts` sits at the centre of the simulation: it consumes `simulation.ts`'s event setup, creates response frames via `frame.ts`, reads/writes device config (ARP/MAC/DHCP tables) on `state`, and calls `sync().render()`/`syncSimLog()` to animate. Forwarding decisions reuse `devices.ts` (interface enumeration) and `simulation.ts`/`utils.ts` (subnet maths).
