# RouteSim — code and architecture review

Branch `main`, commit `1bc69c4`. Read-only review. Every finding below was confirmed by adversarial verification, most of them by running a probe against the real code. I re-read the top findings against the source before writing them up (R1, R2, R3, R4, R6, R7, R9, R13).

---

## 1. Summary

RouteSim is in better shape structurally than its size suggests.

- **What is already solid:**
  - The value-import layering is clean: zero upward imports.
  - There are exactly the two documented import cycles.
  - HTML escaping is consistent everywhere I traced.
  - The validate → `pushUndo` → mutate contract is mostly honoured.
  - Both type-check configurations are clean.
  - The JSON round trip is idempotent across every built-in topology and every solved scenario.
- **Where the defects concentrate:** in a few recurring seams rather than random places.
  1. Learnt or derived state that is never invalidated: MAC tables, RIP routes shown by the CLI, 802.1X authorisation, terminal modes after undo.
  2. Nothing guarantees a simulation run has exclusive ownership of `state.simulation`, so one run silently replaces another.
  3. Capability lists such as "is this a host?" are duplicated about 21 times, with six different memberships.
  4. Several failure paths throw away the reason the engine already knows, which breaks the project's own "failure is a lesson" principle.
- **Most important problems:** seven high-severity findings. All are wrong results a learner will hit in ordinary use:
  - stale MAC tables after a cable delete;
  - a false "broadcast storm" on an 8-host LAN;
  - a router routing on-link traffic on a hub;
  - collapsing a LAN breaking routing;
  - a second terminal command wiping an in-flight run;
  - router interface edits silently ignored;
  - 802.1X not applying to Kali or attacker hosts.
- **Test gate:** the default `bun test` is red. 9–11 benchmark failures appear on the documented ~2 GHz hardware, and they are real cost, not timeouts.

## 2. Architecture assessment

### Strengths worth keeping

- **Layering.** The value imports respect the L0–L6 layers documented in `docs/architecture.md`. There are exactly two strongly connected components, both documented:
  - the engine plus `terminal/*`;
  - the application layer.

  The model layer (`state`, `devices`, `normalise`) stays out of both, thanks to the callback bridges.
- **Single chokepoints.** `admitOnLink` and `linkAuthorizedForData` are the right design. The 802.1X bug (R7) is in the predicate that feeds the gate, not in the gate itself.
- **Registries.** `PROCESSORS`, `CLI_DISPATCH` and `DEVICE_SPECS` are complete for dispatch.
- **Shared mutators.** Host edits are replayed as real shell commands, and switch and router mutators are mostly shared between the inspector, the CLI and the console.
- **Pure, isolated modules.** `packet-filter.ts`, `settings-url.ts`, `snort.ts` and `prng.ts` are well isolated. The packet-filter parser is robust against adversarial input.
- **Protocol fidelity is high where it matters most:**
  - NAT restore runs before INPUT/FORWARD, and DNAT before the self/route decision.
  - ICMP errors carry the quoted original datagram.
  - STP tie-breaking is correct, per 802.1D.
  - RIP learned routes are recomputed at every convergence.
- **Executable invariants.** `diagnostics.ts`, `stress.ts` and the lifecycle tests turn topology-replacement invariants into checks that actually run. Tests built from the scenario solution scripts are an excellent pattern.

### Structural problems

1. **Capabilities are not data.**
   - `DeviceSpec` holds presentation data and defaults only.
   - Behavioural capabilities are re-derived from about 21 hand-written type lists with six different memberships: host, single NIC, bootable, hostname, 802.1X supplicant, terminal-capable, and default port count.
   - This drift directly causes R7 (Kali and attacker bypass 802.1X) and R9 (attacker never boots).
   - Adding the `kali` device type touched 15 files. See R55.
2. **No run ownership.**
   - `startSimulation` and `runSimulationHeadless` each assume they own `state.simulation` exclusively.
   - Each duplicates about 35 lines of reset code (R61).
   - Only the scenario banner's Check calls `stopSimulation` first.
   - Result: silent run clobbering (R5), a stalled or leaked `bootQueue`, and divergence between the two copies of the reset code.
3. **Derived and learnt state is not invalidated.**
   - STP has a `recomputeStp` bridge. RIP, the switch MAC table, `link.dot1xAuthorized`, DHCP leases and terminal session modes have no equivalent.
   - Undo snapshots include derived state, even though the docs say they strip it.
   - Consequences: R1, R8, R33, R58, R78.
4. **Failure reasons are thrown away at the boundary.**
   - `findFirstHop` reduces five different gates to `null`, which callers report as "no link".
   - Processors return silently when a device is powered off.
   - `finishSimulation` discards `pendingArp` without explaining why.
   - Headless runs drop `stormDetected`. Ping ignores Time-Exceeded.
   - Consequences: R14, R24, R49, R50, R71, R22.
5. **Port identity has three models:**
   - `linkedPortsFor`: one dense numbering space, with implicit links filling the gaps;
   - `routerInterfacesWithNames`: a separate numbering per media type;
   - `portTaken`/`nextAvailablePort`: counts explicit links only.

   Consequences: R28, R29, R32, and the port renumbering behind R1.
6. **The model layer reports through the DOM.**
   - `addLink`, `collapseLan`, `expandLan` and `configure` return `void` and write their outcome to `dom.modeLabel`.
   - `cmdCli` ignores error lines.
   - So the console, scripts and `window.routesim` cannot see failures or warnings (R56, R60, R80).
7. **Presentation code lives in the engine and the inspector.**
   - `engine.ts` (2,759 lines) owns about 300 lines of packet-list DOM rendering, so the inspector imports `syncSimLog` back from the engine.
   - `syncPanel` is a 444-line function that renders and binds everything, with 24 `type ===` branches.
   - Partial re-renders lose or stack listeners (R6, R90).
   - The inspector uses three commit styles: per keystroke, on change, and via CLI injection. Together they cause the lost-edit and undo-gap bugs (R45, R46, R92).
8. **The hot path parses strings.**
   - `cidrContains` re-validates and re-splits the same address strings four times per call.
   - It is called per route per frame, and again inside RIP and the firewall.
   - This alone accounts for most of the failing bench budgets (R62, R63, R109).

### Prioritised refactor roadmap

The steps are ordered by how many bugs each one removes per unit of work.

1. **Run ownership** (fixes R5, R61; part of R59 and R49).
   - Add `beginRun(setup, { headless, mode })` in `engine.ts`. It should:
     - stop or refuse an active run;
     - clear `bootQueue` when a non-boot run preempts a boot;
     - perform the one shared reset of `SimulationState`.
   - Both entry points call it.
   - Derive the terminal-input lock from `state.simulation.status` inside `syncTerminal`.
2. **Capabilities in `DeviceSpec`** (fixes R7, R9, R55; also R101 and the Terminal-button gate).
   - Add `roles: { host, singleNic, hostname, bootable, dot1xSupplicant, terminal }` and `defaultPorts`.
   - Export `isHost`/`isBootable`/… from `device-registry.ts` and replace every literal list.
   - Add a registry test asserting that each helper agrees with the spec for every type.
3. **Failure-reason plumbing** (fixes R14, R22, R24, R49, R50, R71).
   - Add `linkDataBlockReason(link): string | null`, shared by `findFirstHop` and `admitOnLink`.
   - Add one powered-off guard, with a log line, in `processNextStep` before dispatch.
   - Add a post-mortem pass in `finishSimulation` covering:
     - unanswered `pendingArp` keys, naming the gateway when that is the cause;
     - the storm flag;
     - Time-Exceeded and Unreachable results.
   - Add `storm` to `SimResult`.
4. **Integer CIDR helper and parsed route entries** (fixes R62, R63, R109; turns most of R65 green).
   - Store `netInt`/`maskInt`/`prefix` on `RouteEntry` and on firewall rules.
   - Parse the frame's `dstIp` once.
   - Precompute each interface's network and RIP-active flag once per convergence.
5. **Derived-state invalidation** (fixes R1, R33, R58, R78).
   - Add a `recomputeRouting` bridge next to `recomputeStp`, fired from the same call sites.
   - Flush a switch's MAC table whenever its links change.
   - Clear `dot1xAuthorized` when `portAuth` changes.
   - Have `restoreSnapshot` reconcile terminal session modes and restore `activeScenarioId` and the relevant options.
   - Strip derived fields in `networkSnapshot`.
6. **One port-occupancy function** (fixes R28, R29, R32).
   - Make it media-aware and include implicit links.
   - Use it from `resolvePort`, `buildPortList` and the script export.
   - Have the export write `auto` for an unpinned end.
7. **Mutators return results** (fixes R56, R57, R60, R80; also R46).
   - `addLink`, `collapseLan`, `expandLan` and `runTerminalCommand` return `{ ok, error?, warnings[] }`.
   - Move the port-picker modal out of `devices.ts`.
   - Extract server mutators (`setDhcpRange`, `setListeningPorts`, …).
   - Route the inspector's shutdown, managed and IDS edits through the same mutators the console uses.
8. **Split presentation** (fixes R6, R90; addresses R106, R108).
   - Move `simlog-view.ts` to L4.
   - Split `engine/handlers/{host,switch,router,firewall,internet,ids,attacker}.ts`, registered in `PROCESSORS`, with `nat.ts`/`conntrack.ts` placed beside `routing.ts`.
   - Add an `INSPECTOR_SECTIONS` registry with delegated listeners on stable containers.
   - Call `blur()` on the active element before `syncPanel` rebuilds.
   - Report sim results through the `sync()` registry, which takes the engine out of the terminal cycle.
9. **Tooling** (fixes R65, R66, R114, R113).
   - Add a bundle smoke test.
   - Turn the round-trip probe (export → replay → compare) over every scenario into a permanent test.
   - Make the bench gate robust, or move it out of the default run.
   - Give the preload DOM stub one element per id, plus event dispatch.

## 3. Findings

Format: **severity · kind** · location. "Fix" gives the smallest correct change. Larger seams are covered by the roadmap above.

### High

#### R1 — Switch MAC table is never flushed; implicit-port renumbering makes stale entries drop or misdeliver unicast
**High · bug** · `src/engine.ts:1304`
- **What:**
  - `processAtSwitch` trusts `config.macTable`, which is keyed by port *name*, across runs.
  - Nothing ever ages or flushes it: not `deleteLink`, not `unlink`, not run start.
  - Implicit cables are numbered densely, so deleting one shifts later ports down by one.
  - A stale entry then maps to a missing index, giving `findIndex === -1`. The frame is dropped with the false reason "dest port is ingress". Alternatively the entry maps to a port that now has a different peer, and the frame is misdelivered.
- **Scenario:**
  1. SW has PC1, PC2 and PC3. `run ping PC2 PC3` succeeds.
  2. Run `unlink SW PC1`.
  3. `ping PC2 PC3` now fails: `SW: Drop ICMP Echo — dest port is ingress`.

  ARP caches are still warm, so no broadcast ever re-learns the port.
- **Fix:**
  - Flush the switch's MAC table on any link change on that switch (or key entries by link id).
  - Treat `portIdx < 0` as a stale entry: flood the frame and log the reason.

#### R2 — Animated runs declare a false "broadcast storm" after 200 events on loop-free LANs
**High · bug** · `src/engine.ts:424`, `:562`
- **What:**
  - `STORM_STEP_CAP = 200` counts every processed event, including each host that ignores a flooded broadcast.
  - The headless path caps at `MAX_STEPS = 10000`.
  - Same topology, different verdicts, and the animated path blames "an L2 loop with no spanning tree". This is silent divergence plus a false diagnosis.
- **Scenario:** a single unmanaged switch with no loop.

  | Run | Headless | Animated |
  |---|---|---|
  | Red Team sweep, 8 hosts | finds 8 live hosts | stops at step 201, `storm=true`, 0 live |
  | DHCP, 55 hosts | succeeds | lease succeeds but the result is replaced by the storm message |
  | DHCP, 70 hosts | succeeds | lease fails |
- **Fix:**
  - Detect a storm by evidence: the same frame lineage crossing the same link again, or transit growth.
  - At minimum, scale the cap with topology size.
  - Add a large loop-free animated-vs-headless parity test.

#### R3 — Router routes every IPv4 frame it receives, including frames addressed to another host's MAC
**High · bug** · `src/engine.ts:1556`
- **What:**
  - `processAtRouter` never checks `frame.dstMac` against the ingress interface MAC or broadcast before calling `routeIpv4Frame`.
  - `handleRouterArp` learns from ARP replies that were not sent to it.
- **Scenario:**
  - A hub with A (.10), B (.20) and router R (.1). Ping A → B.
  - R routes the on-link frame (TTL 64→63). B gets duplicate requests. A gets four replies, two of them with TTL 63.
  - The result line reads `reachable (ttl=63) — 36 steps`. With a switch instead of the hub it reads 9 steps, ttl 64.
- **Fix:**
  - Accept IPv4 only when `dstMac` is the ingress interface MAC or broadcast.
  - Learn ARP only from replies targeted at the interface. Log "not addressed to me — ignoring".
  - Add a hub-plus-router regression test.

#### R4 — Collapsing a LAN breaks routing to it; the drop is misreported as "No route"
**High · bug** · `src/devices.ts:552`
- **What:**
  - `linkedPortsFor` filters out hidden links and hidden peers.
  - After `collapseLan`, the router's real cable is hidden, and the proxy link's peer is the LAN id, which no interface config matches.
  - The interface loses its address, the connected route disappears, and interface names renumber.
  - "Collapse is presentation" is documented as the intent. Persistence was fixed for this (`physicalPeerIds`); the simulation was not.
- **Scenario:**
  1. `defaultConfig`, then collapse Access-SW-C.
  2. Ping PC-A1 → 192.168.30.11 gives `Router: No route to 192.168.30.11 — dropping`, and the router's Ethernet2 address field is blank.
  3. Expanding the LAN fixes it.
- **Fix:**
  - Resolve forwarding and interface naming over *physical* links: keep `collapsedBy`-hidden links and exclude proxy links.
  - Add a test that a ping across a collapsed LAN behaves the same as across the expanded one.

#### R5 — A new run (terminal, console, headless or scenario check) silently replaces an in-flight animated run
**High · bug** · `src/terminal/host.ts:285`, `src/engine.ts:25`, `src/engine.ts:190`, `src/commands.ts:703/790/1003`
- **What:**
  - Host `ping`/`nc`/`curl`/`dhcp`/`nslookup`/`traceroute`, console `run …`, `traceroute`, `scenario check`, and `startSimulation`/`runSimulationHeadless` themselves never check `sim.status`.
  - The only guard is `dom.terminalInput.disabled = true`, and `syncTerminal` (`core.ts:299`) re-enables it at the end of the same submit. A second command works even in the same tab.
  - A headless run's `finishSimulation` returns early (`engine.ts:2726`). So the animated run's result is never printed, `updateSimControls` and `saveCurrentCapture` are skipped, and the transport pill stays up.
  - `bootQueue` is cleared only by `stopSimulation`, so preempting a network boot strands the host being booted. The queue then resumes after the user's run.
  - The attacker shell (`attacker.ts:25`) and the banner Check (`scenario-ui.ts:55`) already guard against this. The docs record the banner case as a fixed bug.
- **Scenario:**
  1. Ping from PC-A's terminal. At 1 s per hop, the run is still animating.
  2. Type a second command, or switch to PC-B and `traceroute`, or type `scenario check` in the console.
  3. PC-A's ping ends with no reply, no timeout and no explanation.
- **Fix:** roadmap step 1.
  - Add a single `beginRun` that stops or refuses an active run with "A simulation is running — stop it (Ctrl+C) first".
  - Clear `bootQueue` when a non-boot run preempts a boot.
  - Derive the input lock from `sim.status`.

#### R6 — Changing a router's port count leaves every interface row without listeners; IP edits are silently dropped
**High · bug** · `src/inspector.ts:1419`
- **What:**
  - The router Ethernet/Serial count handler replaces `#routerInterfaceList` innerHTML and re-binds nothing.
  - The `.router-interface-ip` inputs and `.iface-unlink` buttons are bound only in `syncPanel` (lines 1359–1390).
  - No delegated handler exists, and the spinner's blur handler does not call `syncPanel`.
  - The switch branch at 1338–1340 *does* re-bind its controls, which suggests the router branch was simply missed.
- **Scenario:**
  1. Raise R1 from 4 to 6 Ethernet ports.
  2. Type `10.0.5.1/24` into Ethernet5. Nothing reaches the config.
  3. The field reverts on the next sync, and pings fail "no route".
- **Fix:** extract `bindRouterInterfaceControls(selected)` and call it after the re-render, or delegate on `#routerInterfaceList`.

#### R7 — 802.1X port control is skipped for any peer that is not computer, laptop or server
**High · security** · `src/devices.ts:188`
- **What:**
  - `dot1xLinkInfo` returns `null` unless the host end is one of `computer`/`laptop`/`server`.
  - `dot1xPortAuthorized` treats `null` as authorised.
  - So `auto` and even `force-unauthorized` ports pass all data for `kali`, `attacker`, a hub (and every host behind it), an AP or a router.
  - The rules are also inconsistent with each other: `cmdSupplicant` accepts `kali`, but `buildDot1xEvents` (`simulation.ts:439`) rejects it as "not a host".
- **Scenario:** the canonical NAC lesson. Lock a port, plug in the Kali PC, and `run ping K1 10.0.0.1` succeeds. The same setting blocks an ordinary PC.
- **Fix:**
  - Key port control on the switch port only: a non-supplicant peer simply never authenticates.
  - Share one supplicant type set (roadmap step 2).
  - Add tests for kali on force-unauthorized and for a hub on auto.

### Medium — bugs

#### R8 — Authenticator completes EAP/RADIUS on a `force-unauthorized` port, and the stale authorisation survives mode changes
**Medium · bug** · `src/engine.ts:786`
- **What:**
  - `handleDot1x` never reads the port-control mode.
  - On `force-unauthorized` it relays to RADIUS, sets `link.dot1xAuthorized = true` and logs "the port is authorised, traffic may pass", but the gate still blocks the port.
  - `cmdPortAuth` never clears the flag, so a later switch to `auto` opens the port without a new exchange.
  - (The finding's "wrong password stays authorised" sub-claim is roughly faithful to real 802.1X and is not a defect.)
- **Scenario:** `portauth … force-unauthorized`, then `run dot1x` reports authenticated while pings fail. Then `portauth … auto` and the scenario check passes with no exchange.
- **Fix:**
  - At `eapol-start`, answer `force-unauthorized` with `eap-failure` plus a reason, and `force-authorized` with `eap-success` (no RADIUS).
  - Clear `dot1xAuthorized` whenever `portAuth[port]` changes.

#### R9 — An unconfigured Red Team attacker is never network-booted, and Play reports a false "every host already has an address"
**Medium · bug** · `src/engine.ts:302`
- **What:**
  - `hostNeedsBoot` lists computer, laptop, kali and server, but not attacker.
  - The default attacker config has an empty IP.
  - Play prints "Nothing to boot — every host already has an address." Then `launchRedTeam` silently returns `false`.
  - `docs/src/red-team.md:43` promises the opposite.
- **Scenario:** a DHCP server, a switch and an attacker, with Auto-DHCP on. Press Play: no boot, no attack, and the message is wrong.
- **Fix:** use the shared host predicate (roadmap step 2). Have `launchRedTeam` say why no actor is ready.

#### R10 — Pause does not freeze in-flight frames: they keep moving, get delivered and get captured
**Medium · bug** · `src/engine.ts:469`
- **What:**
  - `animationTick` computes progress from wall-clock time regardless of status.
  - `deliverCompletedTransits` runs whenever every transit has reached 1; only `processNextStep` is gated.
  - `pauseSimulation` only flips the status.
- **Scenario:** click a transit dot to inspect it, which pauses the run. The dot keeps moving, is delivered and vanishes, and a capture row appears while the run reads "paused".
- **Fix:**
  - Skip the progress update while paused, and rebase `startTime` on resume.
  - Gate delivery on `running`.
  - Add an animated test.

#### R11 — Router CLI abbreviation rewrites wrong-mode `ip …` commands as `iptables`
**Medium · bug** · `src/terminal/router.ts:234`
- **What:**
  - In config and privileged mode, the single-token `iptables` spec prefix-matches the token `ip`.
  - The cross-mode fallback runs only when *nothing* matches, so it never gets a chance.
  - So `ip address …` typed in config mode becomes `iptables address …`, and the "% Interface mode required." diagnosis is never shown.
- **Scenario:** the commonest slip: forgetting `interface Ethernet1`. The learner gets `iptables: unknown operation "address"`.
- **Fix:** require at least `ipt` to abbreviate `iptables`, or require whole-token matches when a shorter spec shares the first token.

#### R12 — STP root bridge and blocked link change across replays of the same script
**Medium · bug** · `src/stp.ts:103`
- **What:**
  - The bridge MAC is `deriveMac(dev.id)`, and ids come from `crypto.randomUUID()`.
  - Switches never get a MAC, and the script export emits no MAC or priority.
  - A pinned `seed` does not help.
  - JSON, scenarios and built-ins use fixed ids and are unaffected. The tree is always valid.
- **Scenario:** replaying the same triangle script 30 times blocked each of the three links some of the time.
- **Fix:** give switches a deterministic base MAC when they are added (e.g. from name or creation order), and/or emit it in the export.

#### R13 — Animated per-link loss uses `Math.random()`, so `seed <n>` does not reproduce lossy captures
**Medium · bug** · `src/engine.ts:1682`
- **What:** this is the only engine randomness outside `simRandom`. It contradicts CLAUDE.md and `docs/src/prng.md`, which promise bit-for-bit captures for Compare.
- **Scenario:** `seed 42`, 30% loss, two runs: different frames are dropped.
- **Fix:**
  - Use `simRandom() * 100`.
  - Note that non-builder animated runs (association, STP, boot) also need a reseed.
  - Add a pinned-seed lossy test.

#### R14 — An unanswered ARP (wrong gateway or mistyped target) ends with no diagnosis; queued frames are discarded silently
**Medium · bug** · `src/engine.ts:2723`
- **What:**
  - `finishSimulation` clears `pendingArp` without looking at it.
  - Ping prints a bare "100% packet loss".
  - An on-subnet but wrong gateway, or a mistyped target, gets no explanation. This is the exact example CLAUDE.md gives.
- **Fix:** before clearing, log one `sim-drop` per pending key ("ARP for 10.0.0.254 got no reply — 1 queued ICMP Echo never sent; is the gateway right?"), naming the gateway when it matches. Surface it in the terminal result.

#### R15 — The 802.11 handshake ignores the laptop's SSID after the link exists
**Medium · bug** · `src/engine.ts:674`
- **What:**
  - The SSID is checked only when the link is created (`classifyLink`).
  - `buildAssociationEvents` (`simulation.ts:426`) probes with the *AP's* SSID.
  - `handleDot11` answers any probe.
  - `wifiLinkAuthenticated` checks the password only.
- **Scenario:** `ssid L1 SomeOtherNet`, then `run associate L1` reports "joined", and the ping is reachable.
- **Fix:** probe with the laptop's SSID, have the AP ignore a mismatched SSID with a reason, and make the live gate require a matching SSID.

#### R16 — `traceroute` bypasses the Instant DNS setting
**Medium · bug** · `src/engine.ts:381`
- **What:** `runTraceroute` calls `findPingTarget` unconditionally. Scenarios run with Instant DNS off.
- **Scenario:** with no nameserver, `ping PC-B` gives "cannot resolve", but `traceroute PC-B` succeeds.
- **Fix:** gate the shortcut on `state.options.instantDns !== false`, as `simulation.ts:140` and `:243` do.

#### R17 — Router ARP flush decrements TTL on a payload shared with already-captured frames
**Medium · bug** · `src/engine.ts:1606`
- **What:**
  - The buffered frame is a shallow copy, so its `payload` is shared.
  - `ipv4.ttl--` therefore mutates the inbound frame that `sim.capture`, `frameHistory` and the inspector hold by reference.
- **Scenario:** any cold-start routed ping. The PC→router rows show ttl=63, and the `ip.ttl == 64` filter misses them.
- **Fix:** build a fresh frame with `payload: { ...ipv4, ttl: ipv4.ttl - 1 }`, as the immediate-forward path does.

#### R18 — A static route with an unresolvable next hop stays installed, shadows RIP or default routes, and black-holes traffic
**Medium · bug** · `src/routing.ts:31`, `:104`
- **What:**
  - `buildRoutingTable` adds every static to `seen`, which blocks RIP and the implicit internet default for that prefix.
  - `routingLookup` takes the longest prefix and returns `null` if the next hop doesn't resolve; it never falls back.
  - The `ifaceOnSubnet` fallback ignores shutdown and peer state.
  - The engine logs "No route", while `show ip route` lists `S>*`.
  - FRR would mark such a static inactive.
- **Scenario:**
  - Static plus RIP redundancy, then `shut R1 R2`: traffic black-holes.
  - A mistyped next hop shadows a working default route.
- **Fix:**
  - Install statics only when the next hop is inside a live connected route. Show the others as inactive.
  - Drop the `ifaceOnSubnet` fallback.
  - Report "next hop X unreachable".

#### R19 — RIP never forms adjacencies across a switch
**Medium · bug** · `src/routing.ts:288`
- **What:** a neighbour must be the device at the other end of the cable and be a router. RIPv2 multicasts on the segment. Nothing logs this, and nothing documents it.
- **Scenario:** routers joined through a core switch with correct RIP config. Ping fails with "No route".
- **Fix:** discover router interfaces on the same subnet across L2, or document the limit and log "no RIP neighbour on <iface> (peer is a switch)".

#### R20 — Stateful `ESTABLISHED,RELATED` firewall drops ICMP errors; traceroute hops vanish
**Medium · bug** · `src/engine.ts:2067`
- **What:**
  - `connectionState` never returns `related`.
  - Time-Exceeded and Unreachable messages come from intermediate routers, so they read as `new`.
  - `docs/src/firewall.md` says the canonical rule "still works", which is false for these messages.

## 4. Tests & tooling

**Current state at 1bc69c4:**
- `bunx tsc --noEmit` and `bunx tsc --noEmit -p tsconfig.tests.json` are both clean.
- `bun test` gives 962–964 pass / 9–11 fail across 45 files. Every failure is in `tests/bench.test.ts`; 8–10 still fail when that file runs alone.
- A rebuild is byte-identical to the committed `rs-web.html`, so the artefact is fresh.

**Root cause of the bench failures: established, and they are not timeouts.**
- The ~500 ms shown next to each failing test is its wall time, which equals the harness default `minTime: 500` (1000/2000/3000 ms for the RIP cases).
- Bun's 5000 ms per-test timeout is never reached; the slowest bench takes about 3.1 s.
- Every failure is `expect(passed).toBe(true)` with p99 over budget, on an idle 2.1 GHz Xeon. That is the class of machine the budgets claim to be calibrated for.

The failures fall into three groups:

1. **Unmeetable even at p50** with the current string-parsing CIDR helpers:

   | Bench | Measured p50 | Budget (p99) |
   |---|---|---|
   | `routingLookup` prebuilt | 23–37 µs | 25 µs |
   | `routingLookup` build-per-call | ~40 µs | 60 µs |
   | RIP-15 | 3.8–5.2 ms | 5 ms |

   With memoised parsing, `routingLookup` drops to a p50 of 1.4 µs and RIP-15 to about 1 ms. The budgets were evidently set for integer maths, as the "allocation-free" comment says (R62, R63, R109).
2. **Fail only on the GC tail:** `buildRoutingTable` (p50 ~8 vs 20), `processAtRouter` connected/NAT, RIP-5, `evaluateFirewall`. The heap state left by earlier files moves p99 by 30–100%, which is why the full suite fails more cases than the single file.
3. **Harness weaknesses** (R111): single-shot p99, no `Bun.gc`, unused calibration, and sub-µs functions that measure only timer overhead.

**Recommendations, in order:**
1. Fix the hot paths: an integer CIDR helper and parsed route and firewall entries.
2. Gate on p50 or a trimmed p95, with p99 reported for information. Call `Bun.gc(true)` before measuring and batch fast functions.
3. Decide whether benches belong in the default glob. `docs/benchmarking.md:3` says they are deliberately enforced as ordinary tests. If they stay, re-baseline any budget that remains red after step 1.
4. Fix the `ripStress` fixture (R112) before re-baselining RIP.

**Coverage gaps:**
- No bundle smoke test (R66), even though CLAUDE.md names the bundle-only hazard. A working probe exists.
- No DOM-binding coverage (R114).
- No permanent script-export round-trip over every scenario. The reviewers' probe found R32, R36, R79 and R81 this way, and it should become a test.
- No animated-vs-headless parity test for large loop-free LANs (R2).
- No test of simulation across a collapsed LAN (R4).
- No hub-plus-router test (R3).
- Many `ok:false` assertions don't pin the reason. Instrumentation found one test passing for the wrong reason (R115).
- `diagnostics.ts` checks only device and link ids, selection, transits and captures. It doesn't check config-level references (router interface `peerId`s, MACsec peer keys, mirror ports) that point at deleted devices.

**Hygiene:**
- Cross-file state leaks (R113).
- `_ambient.d.ts` types `expect()` as `any`, so `tsconfig.tests` can't catch matcher misuse.
- `help.test.ts` reads `template.html` relative to the working directory, so it only works when run from the repo root.
- The test server needs a Host check (R116).
- `build-inline.ts` needs post-conditions (R117).
