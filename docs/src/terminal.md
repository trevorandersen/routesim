# `src/terminal/` — Per-device CLI

> Layout: `core.ts` (line buffer, prompt, CLI dispatch via `CLI_DISPATCH`, open/close/sync/submit UI) + one module per NOS — `host.ts` (Linux PC), `server.ts` (Linux + dnsmasq), `router.ts` (FRRouting), `switch.ts` (SONiC), `firewall.ts` (iptables), `ids.ts` (Snort 3 on Linux), `attacker.ts` (Kali Linux — shared by the Kali PC and the Red Team actor) — plus `iptables.ts`, the shared netfilter command engine (firewall device: FORWARD; routers: INPUT + FORWARD). The public API is unchanged, re-exported through `terminal/index.ts`, so `import { … } from "./terminal"` still works everywhere.

The bottom-panel terminal: a per-device command-line that emulates a Linux host shell, a server shell, a router CLI, and a managed-switch CLI. It contains three concerns — command **parsing/dispatch**, state **mutation**, and terminal **rendering**.

**CLI lineage (open-source references):** the router CLI follows **FRRouting** (vtysh — Cisco-IOS-like, with a mode state machine); the managed-switch CLI follows **SONiC** (flat, mode-less `config …` / `show …`); the server follows **dnsmasq** conventions (append directives to `/etc/dnsmasq.conf`, manage the daemon with `systemctl`); the IDS follows **Snort 3 on Linux** (no interactive CLI — edit the `local.rules` file, validate and run the sensor with `snort`, `cat` the alert log); the offensive hosts — the **Kali PC** (`type: "kali"`) and the **Red Team actor** (`type: "attacker"`) — both follow **Kali Linux** (a plain shell that drives the offensive tools — `nmap`, `arpspoof` — then falls through to the host shell for ordinary commands). Each device speaks the language of a real open-source NOS rather than an invented syntax.

## Command dispatchers
- **`runTerminalCommand(rawCommand)`** (`core.ts`) — top-level entry. Reads the active device from `state.terminal.deviceId`, echoes the prompt, and dispatches via the `CLI_DISPATCH` map: computers → `runHostTerminalCommand` (`ip addr`, `ip route`, `arp`, `cat /etc/resolv.conf`, `echo nameserver <ip> > /etc/resolv.conf`, `ping`, `traceroute`/`tracert`, `nslookup`/`host`/`dig <name>`, `nc -z <host> <port>`, `dhcp`, `help`, `clear`), servers → `runServerTerminalCommand`, routers → `runRouterTerminalCommand`, switches → `runSwitchTerminalCommand`, firewalls → `runFirewallTerminalCommand`, IDSes → `runIdsTerminalCommand`, **both** the Red Team actor and the Kali PC (`attacker` and `kali`) → `runAttackerTerminalCommand`. `hasTerminal(device)` derives the "has a CLI" check from the same map, which must agree with the registry's `terminal` role (`tests/device-registry.test.ts`); `canOpenTerminal` adds power and the role's management-plane gate (`offersTerminal` — an unmanaged switch has no shell), and the inspector's Terminal button shows for any device `offersTerminal` admits.
- **`runServerTerminalCommand(server, command)`** (`server.ts`) — the **dnsmasq** server shell: `cat /etc/dnsmasq.conf`, `echo <directive> >> /etc/dnsmasq.conf` (directives `address=/name/ip` — appending an existing name replaces it; `dhcp-range=start,end` — enables DHCP; `dhcp-option=option:router,ip`), and `systemctl start|stop|restart|status dnsmasq` (stopping stops both DNS and DHCP — one daemon). Everything else falls through to the host handler, so a server is also a full Linux endpoint. See [dns.md](dns.md).
- **`runRouterTerminalCommand(router, command)`** — the **FRRouting**-style CLI. Implements a **mode state machine** (`exec → privileged → config → interface/rip`) and the commands within each mode: `enable`, `configure terminal`, `interface <name>`, `ip address`, `encapsulation dot1q`, `ip route`, `router rip` + `network <cidr|ifname>`/`passive-interface`, `show ip route [rip]`, `show ip rip [status]`, `do <show …>`, `exit`/`end`; **NAT**: `ip nat inside|outside` (interface mode), `[no] ip nat inside source static tcp <insideIp> <insidePort> <outsideIp> <outsidePort>` (config mode — a static destination-NAT / port-forward), `show ip nat translations` (lists dynamic PAT + the static port-forwards), `clear ip nat translation *`; **netfilter**: `iptables …` on INPUT/FORWARD (privileged mode, shared engine). Decomposed into focused handlers (session/show/interface/RIP/static-route). A small command **registry** (`ROUTER_COMMANDS`) drives two vtysh conveniences: **command abbreviation** (`expandRouterCommand` expands any unambiguous prefix — `sh ip ro` → `show ip route`, `conf t` → `configure terminal`; ambiguous prefixes error) and a **context-sensitive `?`** (`routerHelp` lists the commands valid in the current mode, filtered by what's typed). Expansion is additive — a command missing from the registry just isn't abbreviated; typed in full it still dispatches.
- **`runFirewallTerminalCommand(device, command)`** — the **iptables**-style firewall CLI (FORWARD chain): `iptables -L/-A/-I/-D/-P/-F`, matches `-s`/`-d`/`-p`/`--icmp-type`, targets `ACCEPT`/`DROP`/`REJECT`. Parses into `FirewallRule`s; `showFirewallRules` renders `-L`. See [firewall.md](firewall.md).
- **`runIdsTerminalCommand(device, command)`** — the **Snort 3 on Linux** sensor shell (no interactive CLI — you edit the rule file and run the sensor): `snort -V` (version), `snort -T` (validate the rule set), `cat /etc/snort/rules/local.rules`, `echo <rule> >> /etc/snort/rules/local.rules` (append), `echo -n > /etc/snort/rules/local.rules` (clear), and `cat /var/log/snort/alert` (the alert log). Edits `config.idsRules` (the raw Snort lines); the alert log reads `config.alerts` (the runtime, non-serialised fast-alert log). See [ids.md](ids.md).
- **`runAttackerTerminalCommand(device, command)`** — the **Kali-Linux**-style shell, registered in `CLI_DISPATCH` for **both** the Kali PC (`kali`) and the Red Team actor (`attacker`) — the hand-driven workstation and the autonomous adversary share one shell (reference: Kali Linux with nmap 7.94). It drives the offensive tools and info commands: `nmap -sS <target>` (TCP SYN port scan), `nmap -sn <subnet>` (ping sweep / host discovery), `arpspoof [-t <victim>] <gateway>` (ARP cache poisoning — the last argument is the IP to impersonate), `nmap -V` (version), `clear`, and `?`/`help`. **Anything else falls through to `runHostTerminalCommand(device, command)`** — so the standard Linux host commands all work (`ip addr`, `ip route`, `ping`, `traceroute`, `nc`, `hostname`, `cat /etc/resolv.conf`), and both offensive hosts get a Linux shell prompt (`<name>$`). That fall-through is also what drives the inspector's host IP/gateway/DNS/MAC fields — they commit through the device terminal (`runDeviceCommand`), so they reach the host handler rather than dying on a "command not found". Each attack command starts the animated simulation (`startSimulation(…, "attack")`; refused with the engine's `RUN_BUSY` reason while another run is in flight — checked before the attack's frames are built, since building reseeds the run PRNG) and the nmap-style report lands in this terminal session when the run finishes (`finishSimulation`). See [red-team.md](red-team.md).
- **`runSwitchTerminalCommand(device, command)`** — the **SONiC**-style managed-switch CLI (flat, no modes): `show vlan brief`, `show mac`, `show interfaces status`, `show runningconfiguration all`, `config vlan add/del <vid>`, `config vlan member add [-t] <vid> <port>` (untagged/tagged), `config vlan member del <vid> <port>`. Rejects unmanaged switches. VLAN membership maps onto the internal access/trunk model: an untagged member is the port's access/native VLAN; a tagged member makes the port a trunk carrying that VLAN. The `sonicVlanMemberAdd`/`Del` helpers apply this in a single undo snapshot. The switch CLI is **exact** (no prefix abbreviation or `?` completion) — SONiC's `config`/`show` CLI is click-based and exact, so matching it keeps fidelity; abbreviation lives only on the FRR router side.

The current mode and interface selection live on the **session** (`state.terminal` — the active `TerminalSession`): `mode`, `interfacePeerId`, `interfaceVlanTag`. Every open device terminal is a session in `state.terminalSessions` with its own scrollback, history, and mode, so the router's config mode survives switching tabs; the console's `cli` command attaches to the same sessions (silently creating one when needed), which is why multi-line vtysh scripts work.

## State mutators
Pure-ish functions that change device config, `pushUndo`, and re-sync — shared across the terminal, the inspector GUI, and the console scripting engine (`commands.ts`):
- Host: `setHostIp`, `flushHostIp`, `setHostGateway`, `setHostDns` (the resolver).
- Server: `applyDnsmasqConfLine` (parses/applies one conf directive), `showDnsmasqConf`.
- Router: `setRouterInterfaceIp`, `clearRouterInterfaceIp`.
- Switch: `addSwitchVlan`, `removeSwitchVlan`, `setSwitchPortVlan`, `setSwitchPortMode`, `setSwitchTrunkNative`, `modifySwitchTrunkAllowed` (the inspector + console use these directly; the SONiC switch terminal applies membership via `sonicVlanMemberAdd`/`Del`).

They return a result string (the message shown in the terminal); callers detect errors by prefix (`"Invalid…"`, `"Unknown…"`).

## Display helpers
`show*` functions that format read-only output: `showHostIp`/`Route`/`Arp`, `showRouterInterfaceBrief`/`Route`/`RouteRip`/`Arp`/`DhcpBindings`/`Rip`(status)/`RipRoutes`/`RunningConfig`, `showSwitchInterfaces`/`Vlans`/`MacTable`/`RunningConfig` (the switch running-config is emitted as replayable SONiC `config …` commands).

## Dock & terminal UI
The bottom **dock** (`core.ts`) hosts three pane kinds behind one tab strip: the per-device terminal sessions (one tab each, closable), the command console, and the sim log (with a live entry-count badge). It is drag-resizable via its top edge (`startDockResize` → `--terminal-height`).

- **`openTerminalFor(device)`** — find-or-create the device's session (`ensureSession`, greeting on creation), make it active, open the dock on the terminal pane. Open failures (powered off, unmanaged switch) show a detached placeholder instead of creating a session.
- **`canOpenTerminal(device)`** — the gate: has a CLI (`hasTerminal`), powered on, and not an unmanaged switch. `configureDevice` consults it via the `openTerminal` device callback, so double-clicking a CLI device opens its terminal.
- **`closeSession(deviceId)`** — close one tab; the active pointer falls back to a neighbour, and closing the last tab closes the dock. A router's exec-level `exit` calls this (logout).
- **`openDock(tab)` / `closeDock()` / `toggleDockTab(tab)` / `setDockTab(tab)`** — dock state; `syncDock()` rebuilds the tab strip and pane visibility.
- **`syncTerminal()`** — render the active session into the terminal pane (a session whose device vanished is closed automatically). It also **derives the input lock** on every sync (`terminalBusy`), from the engine's own policy — `animatedRunBlockReason() !== null` — **scoped to the session whose device started the run** (`sim.originDeviceId`): that shell's input is `readOnly` (placeholder "Simulation running — Ctrl+C to stop", or "paused"), as a real shell is busy only while its own foreground job runs. Every other session stays usable mid-run — `arp -n`, `ip route`, `show ip route`, `show mac address-table`, router config mode — so the learner can pause on a frame and check a table to see why; a run-starting command there is refused with `RUN_BUSY` by the command itself (`refuseIfRunning`). A network boot locks nothing: a user's run may preempt it, so a terminal `ping` takes over from the boot just as the console's does. The lock used to be set by the command that started the run (`disabled = true`) and cleared again by the `syncTerminal` at the end of the very same submit, so it never actually held. It is `readOnly`, not `disabled`, because a disabled input can't keep focus or see the **Ctrl+C** that interrupts the run.
- **`submitTerminalCommand()` / `handleTerminalKeydown()`** — handle Enter and up/down history navigation (per-session history). A submit to the busy shell that slips through mid-run (a value typed before the run began) is refused with the engine's `RUN_BUSY` reason rather than run.
- **`runTerminalCommand(command)`** — echoes the command and dispatches it via `CLI_DISPATCH`. If the command stopped another run (a ping preempting a network boot, a traceroute stopping an animation), it collects the engine's note (`takePreemptionNote`) and writes it under the command in this session — unless the interrupted run was this device's own, whose session the engine already wrote it to.
- **`terminalLine(kind, text)`** — push a line to the active session; **`terminalLineFor(session, …)`** targets a specific one (simulation results go to the *origin device's* session even if another tab is active when the run finishes); **`terminalPromptText(device)`** — the prompt string, per reference NOS: root shells read `root@<name>:~#` (the dnsmasq server and the Snort IDS sensor, which edits `/etc/snort` — it used to fall through to the router's `<name>>`), other hosts `<name>$`, the SONiC switch `<name>#`, the firewall `root@<name>#`, and the router's vtysh prompt follows its CLI mode.
- **`runDeviceCommand(device, command)`** — run a CLI command on a device's terminal **as if the simulator typed it**: surfaces the device's session, echoes the command, dispatches it, and flags the echo + output `injected` (`TerminalLine.injected` → a dark-grey band, distinct from user-typed lines). The inspector uses this so a host's GUI static-config edits (IP/gateway/DNS/MAC) become real, visible Linux commands (`ip addr add …`, `ip route add default via …`, etc.) rather than silent config writes — invalid input fails in the terminal like a real shell.

## How it fits

The terminal is a major surface area. The dispatchers parse user input and call the mutators/display helpers; the mutators are shared with `inspector.ts` so CLI and GUI edits are consistent. `ping`/`dhcp` build events via `simulation.ts` and start the run via `engine.startSimulation`. The host shell's animated commands (`ping`/`nc`/`curl`/`dhcp`/`nslookup`) first ask `engine.animatedRunBlockReason()` (`refuseIfRunning`) and print the reason instead of building when another run owns the simulator; `traceroute` is headless, so it stops an animated run in flight instead, and the interrupted run's session says why (see [engine.md](engine.md#run-ownership)). The mutators are unit-tested directly, and the dispatchers + mode machine have their own dispatcher test file.


## Router sub-interfaces (router-on-a-stick) from the FRR shell

- **A sub-interface is created by naming it.** `interface Ethernet1.20` on a cabled base creates the tagged entry (`routerBaseOrNewSubInterface` → `routerInterfaceFor(router, peer, 20)`) and enters it, as IOS/FRR do. `interface Ethernet1` remains enterable for the **base** even once its sub-interfaces exist (the listing shows only the sub-interfaces then; the base is resolved through them).
- **`encapsulation dot1q N` on the base creates (or selects) the `.N` sub-interface and moves the session onto it** — the base keeps its own untagged identity. On a sub-interface it changes the VLAN that sub-interface carries (its name follows the tag).
- **`no encapsulation dot1q`** is refused on the base, and on a sub-interface when a base entry already exists (un-tagging would leave two untagged entries for one peer).

Before this, `encapsulation dot1q 10` **retagged the base itself**; afterwards `interface Ethernet1` and `interface Ethernet1.20` were both "Unknown", and a second `encapsulation` on `.10` retagged it rather than creating a second sub-interface — router-on-a-stick, one of the built-in topologies, could not be configured from the router's own terminal. `tests/terminal-commands.test.ts` pins the six-step sequence.


## Group B fixes from the uncovered-modules review

- **Host targets by name resolve like the builders do.** `resolvePingTargetIp` (host.ts) — which sets the address the run's success check compares replies against — now uses `findPingTarget` / `hostnameToIp`. A private copy covered `computer`/`server` only, so `ping <laptop>` (or a Kali / Red Team host) from a PC terminal started a run whose target was the literal name and could never report success although the frames flowed. `nc` and `curl` shared it.
- **`no network` is symmetric with `network`** on the router: the same masking (`192.168.1.5/24` → `192.168.1.0/24`) and the same `<ifname>` form, and a non-member is reported rather than silently ignored. Comparing the unmasked token meant `no network 192.168.1.5/24` could never remove what `network 192.168.1.5/24` had stored.
- **The IDS shell keeps the undo contract.** `echo 'alert …' >> local.rules` (→ `addIdsRule`) and `echo -n > local.rules` push an undo point after validation, like every setter in the other shells.


## P3 sweep (uncovered-modules review)

**Switch shell.** `setSwitchMirror` validates its ports *before* pushing undo, and `config vlan member del` decides membership before pushing — a rejected mirror or a non-member delete no longer leaves a spurious entry (which also wiped the redo stack). `config vlan del N` now clears trunk allow-lists and native VLANs that referenced N, not only access memberships (a trunk kept "carrying" a VLAN that no longer existed). `show runningconfiguration all` names a trunk carrying all VLANs with a comment line — SONiC has no command that expresses "tagged member of everything", so the replayable form could not; emitting nothing replayed the port as access.

**Router shell.** `iptables` is refused in interface/rip mode, matching the registry (and `?`); `no ip nat inside source static …` reports "No port-forward" for a rule that does not exist instead of "Removed", and pushes no undo; `passive-interface` validates the interface and stores its canonical name (the RIP send loop compares names exactly); `show running-config` includes the static port-forwards configured in this same mode.
