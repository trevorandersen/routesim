High-priority issues
--------------------
1. Console command mutations are not consistently undoable.

   Evidence:
   - `src/commands.ts:118-129` implements `unlink` by filtering `state.links` directly, with no `pushUndo()`.
   - `src/commands.ts:186-193` implements `rename` by assigning `device.name` directly, with no `pushUndo()`.
   - `src/devices.ts:331-338` already has `deleteLink()` with undo + STP recompute, but `cmdUnlink` bypasses it.
   - `src/devices.ts:401-405` `moveDevice()` only mutates coordinates and renders; `cmdMove` uses it directly, so scripted moves are not undoable unless the caller took a snapshot elsewhere.
   - Additional direct config writes in `commands.ts` include `mac`, `ssid`, `route`, `supplicant`, `portauth`, `radius`, `ports`, `macsec`, `managed`, `idsrule clear`, `redteam`, and `stp` config paths.

   Why it matters:
   The app advertises undo/redo as a core editing surface, and commands/scripts are first-class. If the console can mutate topology/config outside the undo stack, learners can get stuck after a command or imported script step.

   Suggestion:
   Add a shared mutation convention for `commands.ts`: either call existing helper APIs that already push undo, or wrap every successful state-changing command with `pushUndo()` before mutation. Add focused tests that run a representative command, call `undo()`, and assert state is restored.

2. `rename` bypasses hostname validation for CLI devices.

   Evidence:
   - `src/devices.ts:15-28` centralizes RFC-1123 hostname validation in `applyHostname()`.
   - Host/router/switch terminal hostname flows use `applyHostname()` via terminal code.
   - `src/commands.ts:186-193` `cmdRename` writes any token directly to `device.name`.

   Why it matters:
   The README and docs say a CLI device's canvas name is its hostname and resolver identity. Allowing the command surface to create names the terminal surface rejects makes DNS/host identity rules inconsistent.

   Suggestion:
   Route command renames for hostname-bearing devices through `applyHostname()`. For non-hostname devices, still push undo and consider using the same validation policy or documenting why display names can be freer than hostnames.

3. Simulation setup uses nondeterministic ports and IDs despite the project goal of deterministic runs.

   Evidence:
   - `src/simulation.ts:233` chooses TCP source ports with `Math.random()`.
   - `src/simulation.ts:381` builds DHCP transaction IDs with `Date.now()` and `Math.random()`.
   - `src/simulation.ts:506` chooses attack scan source ports with `Math.random()`.
   - `src/frame.ts:5` frame IDs include `Date.now()`.
   - Project guidance in `CLAUDE.md` emphasizes same topology + same inputs should produce the same result.

   Why it matters:
   Outcomes may remain stable, but captures, NAT translations, DHCP traces, and comparison views can differ between identical runs. That weakens saved-capture comparison and makes debugging harder.

   Suggestion:
   Introduce a deterministic per-run sequence allocator for ephemeral ports, DHCP transaction IDs, and frame IDs. Keep truly visual timing based on `performance.now()`, but keep protocol-visible fields repeatable.

Medium-priority issues
----------------------
4. Test type-check coverage is weaker than the test count suggests.

   Evidence:
   - `tsconfig.json` includes only `src/**/*.ts`.
   - Tests run under Bun and are extensive, but the TypeScript project check does not type-check `tests/**/*.ts`.
   - Tests use many `as any` casts and the preload DOM proxy returns a single shared loose element.

   Why it matters:
   The app source is strict, but test helper drift, bad imports, or stale fixture assumptions may not be caught until runtime. This is especially risky because tests encode a lot of protocol and scenario contract knowledge.

   Suggestion:
   Add a separate `tsconfig.tests.json` or documented `bunx tsc --noEmit -p tsconfig.tests.json` path that includes tests with Bun types. Keep tactical `as any` where fixtures intentionally probe malformed data, but avoid it for ordinary happy-path fixture wiring.

5. The DOM test harness is intentionally minimal and can miss browser integration defects.

   Evidence:
   - `tests/preload.ts:13-46` uses one broad stub element with no meaningful layout, event dispatch, or DOM tree semantics.
   - `docs/testing.md:34-43` documents that canvas, computed styles, and rAF behavior are mocked/special.
   - Current tests heavily validate pure engine logic, command behavior, and rendered HTML strings, but not many real browser interactions.

   Why it matters:
   UI regressions around focus, keyboard behavior, menu positioning, modal/pane overflow, event delegation, or actual DOM replacement may pass unit tests.

   Suggestion:
   Add a small Playwright or browser-run smoke suite for `rs-web.html`: load the built single file, place/connect a few devices, open terminal/inspector/settings/help, run one animated ping, and assert visible packet-log rows. Keep it narrow so it does not fight the fast Bun suite.

6. Large modules are carrying too many responsibilities.

   Evidence:
   - `src/engine.ts` is about 2,652 lines.
   - `src/inspector.ts` is about 1,446 lines.
   - `src/commands.ts` is about 1,135 lines.
   - `src/devices.ts` is about 1,058 lines.

   Why it matters:
   The current test suite keeps behavior safe, but large files make review and change isolation harder. `engine.ts` mixes run orchestration, per-device processors, NAT/firewall/IDS hooks, capture rendering, and UI sync. `inspector.ts` mixes HTML templates, validation, and many config bindings.

   Suggestion:
   Extract along already-visible seams: simulation run lifecycle vs packet-log UI, per-device processors, inspector renderers/binders by device family, and command mutator helpers. Do this gradually, with no behavioral refactor unless tests pin the move.

7. Command parser tokenization likely limits legitimate names and values.

   Evidence:
   - Many command handlers receive `args: string[]`, and examples like `cmdRename` use `args[1]` only.
   - Some commands manually recover rest text, e.g. `cmdLinkSet` and `cmdWeb`, which suggests the parser surface is uneven.

   Why it matters:
   Script import/export is a portability feature. Any mismatch between GUI-allowed values and script-command parsing can make exported/imported or hand-written scripts lossy.

   Suggestion:
   Centralize quoting/token parsing and command argument helpers. Add tests for names/titles/SSIDs/rules with spaces, quotes, and shell-like special characters where the app intends to support them.

Lower-priority suggestions
--------------------------
8. Make the command mutation contract explicit.

   Add a short comment near `runCommand` or the command-handler table: every successful state mutation must either push undo itself or call a helper that does. Then test that rule for the common topology/config command families.

9. Consider a small "determinism mode" test.

   Build the same TCP/HTTP/NAT/DHCP flow twice from the same fixture and compare normalized packet columns/log summaries. Exclude visual timestamps if needed, but require protocol-visible fields to match.

10. Keep generated build output policy explicit.

   The repo tracks `rs-web.html`, and `bash build.sh` currently succeeds without dirtying the tree. Keep documenting when generated output must be committed, because the source/build-output pairing is easy to forget in a single-file distribution project.
