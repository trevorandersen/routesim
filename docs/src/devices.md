# `src/devices.ts` — Device/link CRUD, lookups, LAN grouping

Owns the device and link collections: creating, deleting, hit-testing, looking up, enumerating ports/interfaces, and the LAN collapse/expand feature. Also hosts the port-selection modal and a callback bridge back to the UI.

## Key areas

### Capability roles (device-registry.ts)
What a device type *is* lives in its `DEVICE_SPECS` entry as `roles` — `host`, `singleNic`, `bootable`, `dot1xSupplicant`, `hostname`, `terminal` (the last two `true`/`false`/`"managed"`, i.e. only with a switch's management plane on) — plus `defaultPorts`, the Ethernet port count a fresh device gets (`defaultConfigFor` adds it to the type's defaults; `defaultPortCount(type)` is the fallback everywhere a config names none — normalise, serialise, the inspector, `show`, the script export). This module and the rest of the app ask `isHost`/`hasSingleNic`/`isBootable`/`isDot1xSupplicant`/`hasHostname`/`offersTerminal` rather than listing types: about twenty hand-written lists with six different memberships had drifted apart (a Red Team actor was missing from the boot set; only a PC, laptop or server faced 802.1X port control). `tests/device-registry.test.ts` checks every consumer agrees with the spec for every type.

### Data-path gate
- **`linkDataBlockReason(link)`** — the single "does this link carry data now, and if not, why?" gate: null when it does, else a plain-language reason for an administratively down link, a spanning-tree alternate port, an unauthenticated WiFi association (`wifiLinkBlockReason` — the laptop's SSID no longer matches the AP's, or its password is wrong; `wifiLinkAuthenticated` is the boolean wrapper, checked live so it tracks `ssid`/password edits after the link forms), an unauthorised 802.1X port (naming the switch port, and whether it is force-unauthorized or an `auto` port awaiting authentication — the latter with the next console command to run, the host's name quoted via `quoteArg` and `supplicant` first when it has no identity yet), or a failed MACsec link (`macsecState`, with which mismatch failed it). The common open link returns null without building a string. **`linkAuthorizedForData(link)`** is its boolean wrapper. **`dot1xPortFacing(sw, peerId)`** is the authenticator's own view — the port of `sw` that faces one peer — which `handleDot1x` reads to obey the port's control mode. **`dot1xLinkInfo(link)`** returns the authenticator end — `{ sw, peer, mode, port }` — of a wired link whose switch has port control; port control is keyed on the **switch port alone**, whatever the peer type (a Kali PC, Red Team host, hub, AP uplink or router faces it like a PC), and `dot1xPortAuthorized` checks both ends of a switch↔switch link. See [engine.md](engine.md). The 802.1X half resolves a cable's switch port through **`switchPortOfLink`**, a lazily built index (switch id → link id → `Ethernet<n>`) that is valid until the link or device array is replaced or changes length — the `linksFor` invalidation key; a link's ports are fixed when it is made. Before, every gate call on a network with any port control rebuilt the switch's whole port list with `linkedPortsFor`, several times per transit (review R105).

### CRUD
- **`addDevice(type, x, y, name?)`** — creates a device with a default config (`defaultDeviceConfig`) and auto-generated name (`PC-1`, `SW-1`, `RTR-1`, `RT-1`), selects it, returns it. The auto-generated name skips any number whose name a device already has (`nextName` / the placement preview / the server-preset prefixes share `freeNameNumber`), so it never collides with a name the learner typed. Every `isHost` type gets a MAC on creation — including both offensive hosts: the hand-driven **Kali PC** (`kali`) and the autonomous **Red Team actor** (`attacker`). See [red-team.md](red-team.md).
- **`addLink(fromId, toId, fromPort?, toPort?)`** — connects two devices, optionally on specific ports. Hosts (computer/server), the passive **IDS** sensor, and both offensive hosts (the **Kali PC** `kali` and the **Red Team actor** `attacker`) model a **single NIC** and refuse a second cable (the `hostNicTaken` guard, keyed on the registry's `singleNic` role via `hasSingleNic`). **It returns a `LinkResult`** (`{ ok, error?, message?, warnings[], link?, created }`, types.ts) and never writes the status line: refused → `ok: false` with the reason; already linked → `ok: true, created: false` ("A ↔ B are already linked.", plus a warning when ports were requested that the cable is not on — they are not applied); made → `created: true` with a warning for each requested port that could not be honoured (which, why, where the cable went) and for a WiFi association that formed but cannot authenticate (wrong password). Every front door shows that same result through `mutationText(result)` (utils.ts) — the Connect tool and the port picker on the status line, the `link` command as its output — so the console no longer duplicates the validation or prints a bare "Linked" (review R60). Loaded topologies are unaffected — `normalise`/`applyConfig` build links directly. A new cable still fires the optional **`linkUp`** hook, but nothing registers it: an unconfigured host now boots when the user presses Play (`startNetworkBoot` — see [engine.md](engine.md)).
- **`deleteLink(linkId)`** — remove a single link (undoable; clears the link selection). Backs the inspector's **Delete link** button.
- **Link changes invalidate learnt state.** `addLink`, `deleteLink`, `toggleLinkShutdown` and `deleteSelection` end with `linksChanged(ids)` ([state.md](state.md)): the learnt MAC tables on the affected L2 domain are flushed (implicit ports renumber densely, so a stale entry would name the wrong port) and the spanning tree is recomputed.
- **`placementPreview(tool, x, y)`** — the device a click at `(x, y)` *would* place for this tool: the same type, size, name and badge-bearing config as `placeToolDevice`, as a detached `Device` (empty `id`) — nothing is added to the network, no name counter moves and no undo step is pushed; `null` for a tool that places nothing. The canvas draws it as the translucent placement ghost ([canvas.md](canvas.md)). It and `placeToolDevice` both read the internal `placementVariant(tool)` table (real type, optional name prefix, optional seeded config), so the preview cannot promise a device the click won't drop — `tests/placement.test.ts` checks the two agree for every placement tool.
  A new host gets a random NIC MAC; a new **switch** gets its base MAC from its name (`freeBridgeMac` → `defaultBridgeMac`, the spanning-tree tie-break — deterministic, so a replayed script builds the same tree; see [stp.md](stp.md)).
- **`placeToolDevice(tool, x, y)` / `PLACEMENT_TOOLS`** — place the device for a drawing tool, resolving UI variants to real types: `managed-switch` (a Switch-group tool variant) becomes a `switch` with `config.managed = true`; `border-router` (a Router-group variant) becomes a `router` with `config.role = "border"` and a `Border-N` name (the edge archetype — a "B" badge, the natural place for NAT + a firewall; the plain `router` tool is an internal/core router with no role; the role is editable via the inspector Role select or the `role <router> border|internal` console command, and round-trips through JSON + the script export). The Router group's **Internet** entry places the `internet` cloud — a real `DeviceType` (so it falls through to `addDevice`, no preset), an **L3 transit** (`processAtInternet`) representing the public internet that routes between connected routers (each on its own public subnet) by destination, presenting a default gateway to each. `PLACEMENT_TOOLS` is the set the canvas treats as device-placement tools; it includes both offensive hosts — the **Kali PC** (`kali`, a Computer split-group tool alongside Client PC/Laptop, shortcut `K`) and the **Red Team actor** (`attacker`, a Security split-group tool alongside Firewall/IDS, shortcut `A`). Each places an ordinary single-NIC host (it has an IP/MAC/ARP cache, answers ARP, can be pinged — the attack logic lives in the engine, see [red-team.md](red-team.md)). Both also take a hostname. `hasHostname` (re-exported from `device-registry.ts`) reads the spec's `hostname` role — `true` for hosts, router, firewall and IDS, `"managed"` for a switch. `PLACEMENT_TOOLS` itself is `USER_ADDABLE_TYPES` plus the UI variant tools, so a new user-addable type is placeable with no list to edit.
- **`deleteSelection()` / `clearNetwork()`** — remove the selected device (and its links) or the selected link / wipe the topology. A MAC that leaves the wire takes every ARP entry on the remaining devices (a host's `arpTable`, each router interface's) that points at it along (`forgetArpEntries`): deleting a device drops all of its MACs (`macsOwnedBy` — NIC, router interfaces and the derived MAC), and removing a cable — `deleteLink`, or the device at the far end — drops the MAC of each router interface it fed once no cable joins the pair (`orphanedIfaceMacs`). That second case matters because a router interface is keyed by its peer: re-cabling a port to a different switch creates a fresh interface with a new MAC and leaves the old one cable-less in the config, so the hosts' cached gateway MAC would otherwise name an interface nothing answers on, and the router's L2 admission rightly ignores frames sent there. This is the stand-in for ARP ageing (the clockless simulator has none). Undo restores the entries with the snapshot.
- **`macsOwnedBy(device)`** — every MAC a device answers to, cabled or not; names the owner in the stale-ARP diagnosis.
- **`liveMacsOf(device)`** — the MACs a device presents on a cable right now: none without a cable, and for a router only the interfaces whose peer it is still cabled to. The engine's stale-ARP post-mortem checks cache entries against it.
- **`linkName(link)`** — a link's display name: the user-given `link.name` if set, else the derived endpoint combo (`"PC1 ↔ SW"`), which follows device renames. Used by the packet list's Link column, `list links`, and the link inspector.
- **Admin status** — a link may be `shutdown` (administratively down): it stays in the topology but the two frame-path chokepoints (`findFirstHop` in simulation.ts, the transit creation in engine.ts) skip it — as does `l2Reachable`, the L2 path query behind RIP's neighbour discovery — naming it through `linkDataBlockReason` ("… is administratively down, so it carries no traffic"). **`toggleLinkShutdown(linkId)`** flips it (and selects the link) — the canvas double-click path; the link inspector toggle and the `shut`/`noshut` console commands set it too. Round-trips through config.
- **Shared state mutators (review R46)** — one function per action, called by every front door: **`setLinkShutdown(link, down)`** (the link inspector's toggle, `shut`/`noshut`, and `toggleLinkShutdown`, which adds the selection), **`setDevicePower(device, on)`** (the inspector's Power button, the context menu, `power`), **`setSwitchManaged(device, managed)`** (the inspector's Managed toggle, `managed`). Each returns a `MutationResult`, takes no undo point when nothing would change ("S1 is already managed."), and recomputes **before** the panel re-renders: `setLinkShutdown` through `linksChanged` (MAC flush + spanning tree), the other two through the `recomputeStp` bridge — a powered-off or unmanaged switch leaves the tree. Previously each front door had its own copy; the inspector's Managed toggle and both power buttons skipped the recompute, so stale "blocked" dashes, the root badge and port roles stayed on screen until the next run.

- **`deviceNamed(name, self?)` / `deviceNameBlockReason(name, self?)`** — device names are **unique, ignoring case**: they are the handle the console, scripts, the script export and ping-by-name use, all matched case-insensitively, so two devices sharing one (`PC1`/`pc1`) could never be addressed again — every reference answered "Ambiguous" and the exported script would not replay (review R38). `deviceNameBlockReason` is the one rule: the reason a name is taken (naming the holder when only the case differs), or null; `self` lets a device keep its name or change its case. `applyHostname` (every shell's `hostname`, the inspector's Hostname field), the console's `add` and `rename`, and the inspector's plain Name field all ask it before taking an undo point. Loads are not rewritten — the script export copes with duplicates it finds (see [scripting.md](../scripting.md)).

### Hit testing
- **`findDeviceAt(point)` / `findLinkAt(point)`** — translate a canvas coordinate to the device/link under it (used by `ui.ts` pointer handling).

### Lookups (with lazy indexes)
- **`getDevice(id)`** — O(1) lookup via a `Map` index.
- **`linksFor(id)`** — all links touching a device, via a `Map<deviceId, Link[]>` adjacency index.
- **`linkById(id)`** — O(1) link-by-id lookup via a `Map` index on the same lazy (ref, length) signal; replaces per-frame `state.links.find(l => l.id === …)` scans in the engine.
- **`connectedIds(id)`, `linkedPortsFor(id)`** — neighbours and per-port peer resolution, built on `linksFor`.
- **`isVisibleDevice(device)`** — type guard for "defined and not hidden" — a **drawing** question (canvas, inspector lists).
- **`isPhysicalLink(link)`** — whether a link is a real cable: every link except a collapsed LAN's `proxy` links. The **simulation** question — see LAN grouping below.

> **Performance:** both indexes are **lazily rebuilt** when `state.devices`/`state.links` change, detected by an array **identity + length** guard (`ref !== state.devices || len !== state.devices.length`). No invalidation calls are needed at mutation sites because every add/remove either reassigns the array or pushes. In-place field changes (config, `hidden`, port number) are visible through the cached object references — which is why the adjacency stores **all** links and callers filter themselves (`isPhysicalLink` to simulate, `hidden` to draw). These paths are benchmarked (`getDevice`, `linkedPortsFor`, `connectedIds`, `linkById`).

### Interface enumeration
- **`routerInterfacesWithNames`, `routerInterfaceFor`, `routerInterfaceByName`** — resolve a router's interfaces (including VLAN sub-interfaces) to names like `Ethernet1`. `routerInterfacesWithNames(router, cabledOnly = true)` stops after the cabled interfaces — the same entries, in the same order, without the free-port placeholders — for the routing table and RIP, which only read interfaces with a peer and run per routed frame / per convergence. Connected ports key by peer id; unconnected ports surface a saved by-name config when one exists. Every normalise pass here passes the **router id** so `generateRouterIfaceMac` seeds per router (omitting it once made every console-built router share `02:00:00:00:0i:01` MACs), and `routerInterfaceFor`/`routerInterfaceForName` **re-normalise after creating an entry**, so a new interface carries its deterministic MAC and empty tables from birth — no window where an ARP reply could leak an undefined MAC.
- **`routerInterfaceForName(router, name)`** — find/create the config entry for an **unconnected** port (keyed by name, e.g. `Ethernet3`), so a pre-assigned IP persists before any cable exists (`normaliseRouterInterfaces` keeps it because it has a name). Once a cable occupies the port, the by-peer entry takes over. **The configuration follows the port onto a cable**: when `addLink` puts a cable on a port that has a by-name entry, `adoptUncabledRouterPort` re-keys that entry to the new peer (inside the link's undo point), so its address, prefix, NAT role and MAC carry over and the link's result says `R1 Ethernet3 keeps its address 10.3.0.1/24.` Only the port the cable actually lands on is adopted — an auto-assigned cable takes the lowest free port, a pinned one its chosen port; an entry with nothing configured is simply dropped; and what the port showed wins over a stale untagged entry left by an earlier cable to the same peer. Before, the by-name entry was left behind and the cabled interface came up blank.
- **Identity invariant (pinned by `tests/devices.test.ts`):** interface **names are positional** — derived from link order, so removing an earlier link renumbers later ports (`Ethernet2` → `Ethernet1`) — while interface **config keys on the peer** and follows it through any renumbering (IP, `natRole`, sub-interfaces are safe). The caveat: anything that references an interface **by name** (`rip.passiveInterfaces`, a saved by-name entry for an unconnected port) does *not* follow a renumbering — re-cabling can silently detach such references. Prefer peer-keyed state for new features.
- **`switchInterfacesWithNames`** — a switch's ports with their VLAN/mode/peer, named `Ethernet1..N`. Port numbers derive from link order (see [testing.md](../testing.md)).

### LAN grouping
- **`collapseLan` / `expandLan` / `collectLanMembers`** — collapse a switch and its hosts into a single "LAN" cloud node and back. Both return a `MutationResult`: what was done (`Collapsed 3 devices into SW1 LAN.`), or why nothing was — the target is not a switch, the switch has nothing attached, it is already inside a collapsed LAN, or (expand) it is not a collapsed LAN. A refusal takes no undo point; the `collapse`/`expand` commands used to report success for every one of these (review R80). Collapsing sets `hidden`/`collapsedBy` on members in place and adds a `proxy` link from the cloud to each boundary router.
- **Collapse is presentation, never topology (review R4).** `hidden` means "not drawn", not "unplugged": every path that simulates, routes, numbers ports or checks cabling filters on **`isPhysicalLink`** (keeps collapse-hidden cables, drops proxy links) and does not skip hidden devices — `linkedPortsFor` (so router interface names, addresses and connected routes, switch port numbers, STP and 802.1X keys), `occupiedPorts`, `l2Reachable`/`findFirstHop`/`getVlanForDevice`, the engine's transit link lookup, STP participants and edges, DHCP pool allocation (a collapsed host keeps its address), the boot/Red Team "cabled?" checks, the scenario `link` goal, and the `shut`/`noshut`/`linkset` commands (which name the real cable, hidden or not). Before, the router's cable to a collapsed LAN read as unplugged: its interface lost its address, the connected route vanished, ports renumbered, and a ping across failed with a false `No route`. Drawing and hit-testing still filter `hidden`; a frame crossing a hidden cable is drawn against the LAN cloud (canvas.md). Because nothing structural changes, collapse/expand only re-render — they no longer fire `linksChanged`. Pinned by `tests/collapse.test.ts`.

### Port-selection modal & callback bridge
- **The port picker lives in `port-picker.ts`** (`openPortSelectionModal`, `syncPortSelectionModal`, `confirmPortSelection`, `cancelPortSelection` — presentation, moved out of this model file; only `buildPortList`, the data behind its rows, stays here). It is the manual port picker, opened only when the user **Shift-clicks** the second device with the Connect tool. A plain Connect click skips it and calls `addLink`, which resolves the first free port on each end; the modal also auto-links host↔host / wireless pairs that have nothing to pick. The single-NIC host branch of `buildPortList`/`openPortSelectionModal` now covers both offensive hosts — `kali` and `attacker` (the latter previously fell through and showed an empty, un-confirmable column).
- **`registerDeviceCallbacks({ setTool, setNetworkPanel, openTerminal, stopSimulation, linkUp? })`** — lets `devices.ts` trigger UI/engine work without importing `ui.ts`/`engine.ts`/`terminal/`: `setTool`/`setNetworkPanel` (UI changes after CRUD), `openTerminal` (open a device's CLI), `stopSimulation` (`clearNetwork` tears the run down first). `linkUp` is vestigial — `addLink` fires it, but `app.ts` no longer registers it since first boot moved to Play. Wired in `app.ts`; tests register the pieces they need. See [architecture.md](../architecture.md#6-the-callback-bridges).
- **`configureDevice(device)`** — selects a device, shows its config, and **reverts to the select tool** (configuring is a one-shot action, not a sticky mode — so the configure tool is single-use and double-clicking from any tool lands back in select). Also fires `openTerminal` — which `app.ts` gates on `canOpenTerminal` (see [terminal.md](terminal.md)), so configuring a CLI device auto-opens its terminal while unmanaged switches/LANs just show their config.

## How it fits

The data layer beneath the UI: `canvas.ts` renders `state.devices`/`state.links`, `ui.ts` calls the CRUD/hit-testing functions on pointer events, and `engine.ts`/`simulation.ts` traverse the topology through `getDevice`/`linksFor`/`linkedPortsFor`. The lookup indexes here are the single biggest steady-state performance lever.


## Teardown order and port bounds

- **`clearNetwork()`** calls the `stopSimulation` device callback **first**, then deletes devices/links, drops sessions and captures, and clears `selectedId`/`selectedLinkId`. Before this the animation loop kept running against deleted devices (status stuck on `running`, a transit pointing at a missing link — `diagnoseState` reported four issues). Engine-owned work reaches devices.ts through the callback bridge because a direct `devices → engine` import would be a cycle.
- **Physical port numbers are bounded** by `MAX_PHYSICAL_PORT` (utils.ts, 64 — a sanity ceiling above every device's real cap). `portBlockReason` refuses a requested port above it (the cable is auto-assigned) and `linkedPortsFor` treats an out-of-range stored port as implicit rather than growing its sparse array to it. The normaliser enforces the same bound on import (see normalise.md); the two later checks are defence in depth.

- **`physicalPeerIds(id)`** — peers over physical cables (`isPhysicalLink`), *including* those a collapsed LAN has hidden and *excluding* the LAN's proxy links. The persistence layer asks this rather than `connectedIds` (which is the drawn set): collapse is presentation, and a save must not depend on it.


## Port occupancy: one function

`occupiedPorts(deviceId, media)` is the single answer to "which numbered ports of this device are in use?" — port number → the peer cabled there. It counts **every physical cable, pinned or implicit**, and reads them from the same views that *name* the ports (`routerInterfacesWithNames` for a router, the slots of `linkedPortsFor` otherwise, wireless associations excluded), so "occupied" cannot disagree with what the inspector and terminal show. Three helpers build on it:

- **`portBlockReason(deviceId, peerId, port)`** — why a cable to `peerId` cannot take `port` at this end, or null when the port exists and is free: `SW1 Ethernet1 is already cabled to PC1`, `SW1 has 8 ports, so there is no Ethernet12`, `R1 has 2 serial ports, so there is no Serial3`, `PC3 has a single NIC (eth0), so it has no port 2`. `addLink` pins a requested port only when this returns null (otherwise the cable is made unpinned and auto-assigned), and the `link` console command prints the reason and where the cable went instead.
- **`linkPortName(link, deviceId)`** — the name of the port a cable occupies at one end (`Ethernet3`, `Serial1`, `eth0`); what the `link` command reports and the script export reads.
- **`buildPortList(deviceId, peerId?)`** — the picker's rows. Given the other end of the cable being made, a router lists only the kind of port that cable will use (serial to a router, Ethernet to anything else), so every port offered as free is one `addLink` honours under that name.

Before this (review R28) the `link` command's check (`portTaken`/`nextAvailablePort`) counted only *pinned* cables: `link SW1 PC2 1` landed on the slot PC1's implicit cable held, PC1 shifted to Ethernet2 (cascading down the switch), and the VLAN membership keyed on `Ethernet1` moved to the newcomer. `linkedPortsFor` also no longer overwrites a slot when two cables carry the same number (a router's `Ethernet3` and `Serial3`): the later one takes a free slot, so neither cable is orphaned.

## Router interface names and the port picker

Two kinds of cable, one naming rule:

- **A chosen port is pinned.** When the picker (or `link A B 4 1`) selects a port, the link stores that number and the interface *is* `Ethernet4` — in the inspector, the terminal, and the picker alike, and it stays `Ethernet4` when earlier cables are added or removed. The free ports offered are every unused number up to capacity, so the gap a pick leaves is shown as free rather than hidden. (Before, `routerInterfacesWithNames` dropped the sparse gaps and renumbered by array position: a sole cable on port 4 read as `Ethernet1`, and the name moved whenever another cable came or went.)
- **An auto-assigned cable is implicit.** `addLink` persists a port number only when the caller chose one *and* it was honoured; an auto-assigned cable stores none, fills the lowest free slot, and names densely **per media** — `Ethernet1, Ethernet2, …` and `Serial1, Serial2, …` — exactly as before. (Persisting the auto slot would have put every cable in one shared numbering space, so a router's first serial cable came out as `Serial2`.) This is the "positional names shift" invariant `tests/devices.test.ts` pins: *implicit* names are positional; *chosen* names are not.

**A router numbers its two media separately.** A stored port number means *that number of the cable's own kind of port*: serial for a cable to another router, Ethernet otherwise (`portMediaFor`). So `Ethernet2` and `Serial2` can both be chosen on one router. (They used to share one number space per device: with `Ethernet3` pinned the picker still offered `Serial3`, and choosing it silently produced `Serial1` — review R29.) `wiredPortCapacity(device)` is the per-type capacity the picker and `switchInterfacesWithNames` share — a firewall's 2 ports are no longer clamped up to a switch's minimum of 4 — and `buildPortList` now enumerates **firewall** and **internet** ports (they fell through to an empty list, leaving the picker with a blank column and nothing to confirm) and auto-selects the single-NIC **IDS** like a host.
