# `src/terminal/` — Per-device CLI

> Layout: `core.ts` (line buffer, prompt, CLI dispatch via `CLI_DISPATCH`, open/close/sync/submit UI) + one module per NOS — `host.ts` (Linux PC), `server.ts` (Linux + dnsmasq), `router.ts` (FRRouting), `switch.ts` (SONiC), `firewall.ts` (iptables), `ids.ts` (Snort 3 on Linux), `attacker.ts` (Kali Linux — shared by the Kali PC and the Red Team actor), `completion.ts` (Tab completion for the Linux shells) — plus `iptables.ts` and `nftables.ts`, the two shared netfilter command front doors over one rule model (firewall device: FORWARD; routers: INPUT + FORWARD; `config.ruleLang` picks the dialect the native view / rule rows / export speak — see [firewall.md](firewall.md)). The public API is unchanged, re-exported through `terminal/index.ts`, so `import { … } from "./terminal"` still works everywhere.

The bottom-panel terminal: a per-device command-line that emulates a Linux host shell, a server shell, a router CLI, and a managed-switch CLI. It contains three concerns — command **parsing/dispatch**, state **mutation**, and terminal **rendering**.

**CLI lineage (open-source references):** the router CLI follows **FRRouting** (vtysh — Cisco-IOS-like, with a mode state machine); the managed-switch CLI follows **SONiC** (flat, mode-less `config …` / `show …`); the server follows **dnsmasq** conventions (append directives to `/etc/dnsmasq.conf`, manage the daemon with `systemctl`); the IDS follows **Snort 3 on Linux** (no interactive CLI — edit the `local.rules` file, validate and run the sensor with `snort`, `cat` the alert log); the offensive hosts — the **Kali PC** (`type: "kali"`) and the **Red Team actor** (`type: "attacker"`) — both follow **Kali Linux** (a plain shell that drives the offensive tools — `nmap`, `arpspoof` — then falls through to the host shell for ordinary commands). Each device speaks the language of a real open-source NOS rather than an invented syntax.

## Command dispatchers
- **`runTerminalCommand(rawCommand)`** (`core.ts`) — top-level entry. Reads the active device from `state.terminal.deviceId`, echoes the prompt, and dispatches via the `CLI_DISPATCH` map: computers → `runHostTerminalCommand` (`ip addr`, `ip route`, `arp`, `ip neigh flush all` (`flushHostArp` — empties the ARP cache, undoably: the remedy the post-mortem names for a stale entry, since the simulator never ages ARP out), `cat /etc/resolv.conf`, `echo nameserver <ip> > /etc/resolv.conf`, `ping`, `traceroute`/`tracert`, `nslookup`/`host`/`dig <name>`, `nc -z <host> <port>`, `dhcp`, `help`, `clear`), servers → `runServerTerminalCommand`, routers → `runRouterTerminalCommand` (which also takes the Linux `ip neigh flush all` in privileged/config mode — `flushRouterArp` empties every interface's ARP cache, undoably, the router-side remedy for a stale next-hop entry), switches → `runSwitchTerminalCommand`, firewalls → `runFirewallTerminalCommand`, IDSes → `runIdsTerminalCommand`, **both** the Red Team actor and the Kali PC (`attacker` and `kali`) → `runAttackerTerminalCommand`. **A powered-off device has no working shell**: a session opened while it was on stays in the dock, but `runTerminalCommand` refuses every line except `clear` with `<name> is powered off.` (`ok: false`, nothing echoed, no undo point) — the same sentence `openTerminalFor` shows — and `syncTerminal` puts the reason in the input's placeholder. The inspector's injected `runDeviceCommand` is the simulator's own edit, not a typed command, and still applies. `hasTerminal(device)` derives the "has a CLI" check from the same map, which must agree with the registry's `terminal` role (`tests/device-registry.test.ts`); `canOpenTerminal` adds power and the role's management-plane gate (`offersTerminal` — an unmanaged switch has no shell), and the inspector's Terminal button shows for any device `offersTerminal` admits.
- **`runServerTerminalCommand(server, command)`** (`server.ts`) — the **dnsmasq** server shell: `cat /etc/dnsmasq.conf`, `echo <directive> >> /etc/dnsmasq.conf` (directives `address=/name/ip` — appending an existing name replaces it; `dhcp-range=start,end` — enables DHCP; `dhcp-option=option:router,ip`), and `systemctl start|stop|restart|status dnsmasq` (stopping stops both DNS and DHCP — one daemon). Everything else falls through to the host handler, so a server is also a full Linux endpoint. See [dns.md](dns.md).
- **`runRouterTerminalCommand(router, command)`** — the **FRRouting**-style CLI. Implements a **mode state machine** (`exec → privileged → config → interface/rip`) and the commands within each mode: `enable`, `configure terminal`, `interface <name>`, `ip address`, `encapsulation dot1q`, `ip route`, `router rip` + `network <cidr|ifname>`/`passive-interface`, `show ip route [rip]`, `show ip rip [status]`, `do <show …>`, `exit`/`end`/`disable`; **NAT**: `ip nat inside|outside` (interface mode), `[no] ip nat inside source static tcp <insideIp> <insidePort> <outsideIp> <outsidePort>` (config mode — a static destination-NAT / port-forward), `show ip nat translations` (lists dynamic PAT + the static port-forwards), `clear ip nat translation *`; **netfilter**: `iptables …` on INPUT/FORWARD (privileged mode, shared engine). Decomposed into focused handlers (session/show/interface/RIP/static-route). A small command **registry** (`ROUTER_COMMANDS`) drives two vtysh conveniences: **command abbreviation** (`expandRouterCommand` expands any unambiguous prefix — `sh ip ro` → `show ip route`, `conf t` → `configure terminal`; ambiguous prefixes error) and a **context-sensitive `?`** (`routerHelp` lists the commands valid in the current mode, filtered by what's typed). Expansion is additive — a command missing from the registry just isn't abbreviated; typed in full it still dispatches. A spec may set **`min`**, the fewest characters of its first keyword that abbreviate it: `iptables` needs three (`ipt`), because it is a program rather than a vtysh keyword and shares `ip` with every `ip …` command — without it, `ip add 10.0.0.1/24` typed in config mode (forgetting `interface Ethernet1`) expanded to `iptables add …` and answered `iptables: unknown operation "add"` instead of `% Interface mode required.` (review R11). A command spelled out in full for *another* mode beats a mere prefix match in the current one, so `ip address …` typed in config mode is answered by its own handler (`% Interface mode required.`) and not expanded to `iptables address …`.
- **`addStaticRoute(router, network, nextHop)` / `removeStaticRoute(router, network, nextHop?)`** (`router.ts`) — the static-route mutators, returning a `MutationResult`. The shell's `[no] ip route` and the console's `route` verb both call them, so the two front doors refuse the same input (a network that is not CIDR, a next hop that is not an IPv4 address, a device that is not a router) and store the same form: the network with its host bits masked (`10.0.0.5/24` → `10.0.0.0/24`, as FRR stores it). A duplicate add is a no-op that says so, and a removal that matches nothing is an error; neither takes an undo point. The console verb used to check only its token count — it stored `garbage nonsense`, a prefix-less network `no ip route` could never match, and the same route repeatedly (review R37).
- **The route show commands converge first.** `show ip route [rip]`, `show ip rip` and `show ip rip status` (and their `do` forms) call `runRipConvergence()` before reading: learned routes are derived state, true only for the topology they were computed over. Printing them as stored showed dead paths after an unlink and no RIP routes at all until the first simulation (review R58). `show spanning-tree` does the same for STP. `clear ip rip database` clears the derived list without an undo point; the next convergence relearns it, as a real router does from its neighbours' next updates.
- **`reconcileRouterSession(session, router)`** — a router session's CLI mode points at configuration: `rip` mode at the router's RIP process, `interface` mode at one cabled (sub-)interface. Undo/redo, an unplugged cable or a change made elsewhere can remove that configuration behind the shell's back, so the mode is checked against the live router wherever it is read — at the top of `runRouterTerminalCommand`, before the command echo in `runTerminalCommand`, and in `syncTerminal` before the prompt is drawn (`restoreSnapshot` calls the `syncTerminal` bridge, so the prompt follows an undo at once). A mode whose target is gone falls back to configuration mode with a one-line notice in the session (`% RIP is no longer enabled on R1 — back in configuration mode …`). Before this (review R33) the next `network` dereferenced a RIP block that no longer existed — a TypeError that escaped the submit — and `ip address` silently recreated an undone sub-interface. `submitTerminalCommand` now re-renders in a `finally`, so a handler that throws can't leave the pane stale.
- **Config-if on a port with no cable.** A cabled interface is keyed by its peer (`interfacePeerId` + `interfaceVlanTag`); an unplugged port has no peer, so the session holds its **name** instead (`interfaceName`, e.g. `Ethernet3`) and `ip address`, `no ip address` and `ip nat inside|outside` edit the by-name entry the inspector's "not connected" rows use (`routerInterfaceForName`; `setUncabledRouterInterfaceIp` is the address setter). As on a real router the port takes its configuration while unplugged; the shell adds a one-line note that it stays down, with no connected route, until a cable is plugged in. A **sub-interface** can be made on an unplugged port too, as FRR and IOS allow: `interface Ethernet3.10` (or `encapsulation dot1q 10` on `Ethernet3`) creates it — one undo point, none when it already exists and is only selected — with the same note that it stays down. It is the entry an unplugged cable leaves behind (`uncabledSubInterfaceFor`: keyed by the port's name, with its tag), so the inspector lists it, a save keeps it and the next cable adopts it like any parked sub-interface; `encapsulation dot1q` retags it and `no encapsulation` untags it under the same rules as on a cable (`sessionPortEntries`/`sessionPortEntry` serve both). It used to be refused ("a sub-interface needs a cable to carry its VLAN"), which also meant a script could not re-create one. `reconcileRouterSession` keeps the name honest too: a cable plugged into the port mid-session moves the session onto the now-cabled interface (with a notice), and a port that no longer exists (a reduced port count) falls back to configuration mode. The guards used to test `interfacePeerId` alone — an unplugged port's is `""` — so `interface Ethernet3` entered config-if and every command in it answered "Interface mode required" (review R39). Choosing faithfulness here costs a beginner nothing: the note says what an address on an unplugged port does and does not do. **The configuration follows the port onto a cable**: when `addLink` puts a cable on a port that has a by-name entry, `adoptUncabledRouterPort` re-keys that entry to the new peer (inside the link's undo point), so its address, prefix, NAT role and MAC carry over and the link's result says `R1 Ethernet3 keeps its address 10.3.0.1/24.` Only the port the cable actually lands on is adopted — an auto-assigned cable takes the lowest free port, a pinned one its chosen port; an entry with nothing configured is simply dropped; and what the port showed wins over a stale untagged entry left by an earlier cable to the same peer. Before, the by-name entry was left behind and the cabled interface came up blank. **And it stays on the port when the cable goes**: `deleteLink` and `deleteSelection` call `releaseRouterPorts` around the removal, which re-keys the departing peer's entries (the interface and any sub-interfaces) to the name of the port that is now free and clears their ARP tables — so `show ip interface brief` and the inspector keep showing the address on a `down` port, the JSON save keeps it, and the next cable on that port adopts it, MAC included. Auto-assigned cables number densely, so when one is removed the later ones move down and the configuration lands on the port that ends up free (found by comparing the cabled port names before and after); a pinned cable frees exactly its own port. Sub-interfaces parked on an unplugged port are listed under it, down (`Ethernet1.10 … down down` in `show ip interface brief`, in the running-config and the inspector), can be selected and re-addressed (`interface Ethernet1.10`; a new one is made the same way), and return with the next cable. **A shell in config-if stays on its port when the cable goes**: `releaseRouterPorts` moves the session from the departed peer to the port's name (keeping a sub-interface's tag) and says `% Ethernet1 is no longer cabled — still configuring it…`; `reconcileRouterSession` moves it back when a cable lands (or the unlink is undone). It used to be thrown back to configuration mode mid-edit. Before, the entry stayed keyed by the departed peer: the port read "unassigned", the address returned only if that same device was re-cabled, and a save dropped it.
- **`runFirewallTerminalCommand(device, command)`** — the **iptables**-style firewall CLI (FORWARD chain): `iptables -L/-A/-I/-D/-P/-F`, matches `-s`/`-d`/`-p`/`--icmp-type`, targets `ACCEPT`/`DROP`/`REJECT`. Parses into `FirewallRule`s; `showFirewallRules` renders `-L`. See [firewall.md](firewall.md).
- **`runIdsTerminalCommand(device, command)`** — the **Snort 3 on Linux** sensor shell (no interactive CLI — you edit the rule file and run the sensor): `snort -V` (version), `snort -T` (validate the rule set), `cat /etc/snort/rules/local.rules`, `echo <rule> >> /etc/snort/rules/local.rules` (append), `echo -n > /etc/snort/rules/local.rules` (clear), and `cat /var/log/snort/alert` (the alert log). Edits `config.idsRules` (the raw Snort lines); the alert log reads `config.alerts` (the runtime, non-serialised fast-alert log). See [ids.md](ids.md).
- **`runAttackerTerminalCommand(device, command)`** — the **Kali-Linux**-style shell, registered in `CLI_DISPATCH` for **both** the Kali PC (`kali`) and the Red Team actor (`attacker`) — the hand-driven workstation and the autonomous adversary share one shell (reference: Kali Linux with nmap 7.94). It drives the offensive tools and info commands: `nmap -sS <target>` (TCP SYN port scan), `nmap -sn <subnet>` (ping sweep / host discovery), `arpspoof [-t <victim>] <gateway>` (ARP cache poisoning — the last argument is the IP to impersonate), `nmap -V` (version), `clear`, and `?`/`help`. **Anything else falls through to `runHostTerminalCommand(device, command)`** — so the standard Linux host commands all work (`ip addr`, `ip route`, `ping`, `traceroute`, `nc`, `hostname`, `cat /etc/resolv.conf`), and both offensive hosts get a Linux shell prompt (`<name>$`). That fall-through is also what drives the inspector's host IP/gateway/DNS/MAC fields — they commit through the device terminal (`runDeviceCommand`), so they reach the host handler rather than dying on a "command not found". Each attack command starts the animated simulation (`startSimulation(…, "attack")`; refused with the engine's `RUN_BUSY` reason while another run is in flight — checked before the attack's frames are built, since building reseeds the run PRNG) and the nmap-style report lands in this terminal session when the run finishes (`finishSimulation`). See [red-team.md](red-team.md).
- **`runSwitchTerminalCommand(device, command)`** — the **SONiC**-style managed-switch CLI (flat, no modes): `show vlan brief`, `show mac`, `show interfaces status`, `show runningconfiguration all`, `config vlan add/del <vid>`, `config vlan member add [-t] <vid> <port>` (untagged/tagged), `config vlan member del <vid> <port>`. Rejects unmanaged switches. VLAN membership maps onto the internal access/trunk model: an untagged member is the port's access/native VLAN; a tagged member makes the port a trunk carrying that VLAN. The `sonicVlanMemberAdd`/`Del` helpers apply this in a single undo snapshot. The switch CLI is **exact** (no prefix abbreviation or `?` completion) — SONiC's `config`/`show` CLI is click-based and exact, so matching it keeps fidelity; abbreviation lives only on the FRR router side.

The current mode and interface selection live on the **session** (`state.terminal` — the active `TerminalSession`): `mode`, `interfacePeerId`, `interfaceVlanTag`, and `interfaceName` (the port being configured when it has no cable, so no peer). Every open device terminal is a session in `state.terminalSessions` with its own scrollback, history, and mode, so the router's config mode survives switching tabs; the console's `cli` command attaches to the same sessions (silently creating one when needed), which is why multi-line vtysh scripts work.

## State mutators
Pure-ish functions that change device config, `pushUndo`, and re-sync — shared across the terminal, the inspector GUI, and the console scripting engine (`commands.ts`):
- Host: `setHostIp`, `flushHostIp`, `setHostGateway`, `setHostDns` (the resolver).
- Server: `applyDnsmasqConfLine` (parses/applies one conf directive), `showDnsmasqConf`, and the mutators it and the inspector share — **`setDhcpRange(device, start, end)`** (both bounds committed together; empty + empty turns DHCP off; a bad address or an inverted range is refused, as real dnsmasq refuses it) and **`setDhcpRouterOption(device, ip)`** (empty clears). Both return a `MutationResult`; the shell prints the reason as `dnsmasq: <reason> (at line: …)`.
- Host: **`setListeningPorts(device, ports | null)`** — `null` = no list (accept on any port), `[]` = listen on nothing, otherwise the ports (each 1–65535, de-duplicated). Shared by the console's `ports` command and the inspector's Listening ports field.
- Router: `setRouterInterfaceIp`, `clearRouterInterfaceIp`.
- Switch: `addSwitchVlan`, `removeSwitchVlan`, `setSwitchPortVlan`, `setSwitchPortMode`, `setSwitchTrunkNative`, `modifySwitchTrunkAllowed` (the inspector + console use these directly; the SONiC switch terminal applies membership via `sonicVlanMemberAdd`/`Del`).

They return a result string (the message shown in the terminal); callers detect errors by prefix (`"Invalid…"`, `"Unknown…"`).

## Display helpers
`show*` functions that format read-only output: `showHostIp`/`Route`/`Arp`, `showRouterInterfaceBrief`/`Route`/`RouteRip`/`Arp`/`DhcpBindings`/`Rip`(status)/`RipRoutes`/`RunningConfig`, `showSwitchInterfaces`/`Vlans`/`MacTable`/`RunningConfig` (the switch running-config is emitted as replayable SONiC `config …` commands).

## Dock & terminal UI
The bottom **dock** (`core.ts`) hosts three pane kinds behind one tab strip: the per-device terminal sessions (one tab each, closable), the command console, and the sim log (with a live entry-count badge). It is drag-resizable via its top edge (`startDockResize` → `--terminal-height`).

- **`openTerminalFor(device)`** — find-or-create the device's session (`ensureSession`, greeting on creation), make it active, open the dock on the terminal pane. Open failures (powered off, unmanaged switch) show a detached placeholder instead of creating a session.
- **`canOpenTerminal(device)`** — the gate: has a CLI (`hasTerminal`), powered on, and not an unmanaged switch. `configureDevice` consults it via the `openTerminal` device callback, so double-clicking a CLI device opens its terminal.
- **`closeSession(deviceId)`** — close one tab; the active pointer falls back to a neighbour, and closing the last tab closes the dock. A router's `exit` at user exec **or privileged exec** calls this (logout, as on IOS and in vtysh; `disable` is the step from privileged back to user exec).
- **`openDock(tab)` / `closeDock()` / `toggleDockTab(tab)` / `setDockTab(tab)`** — dock state; `syncDock()` rebuilds the tab strip and pane visibility.
- **`syncTerminal()`** — render the active session into the terminal pane (a session whose device vanished is closed automatically). It also **derives the input lock** on every sync (`terminalBusy`), from the engine's own policy — `animatedRunBlockReason() !== null` — **scoped to the session whose device started the run** (`sim.originDeviceId`): that shell's input is `readOnly` (placeholder "Simulation running — Ctrl+C to stop", or "paused"), as a real shell is busy only while its own foreground job runs. Every other session stays usable mid-run — `arp -n`, `ip route`, `show ip route`, `show mac address-table`, router config mode — so the learner can pause on a frame and check a table to see why; a run-starting command there is refused with `RUN_BUSY` by the command itself (`refuseIfRunning`). A network boot locks nothing: a user's run may preempt it, so a terminal `ping` takes over from the boot just as the console's does. The lock used to be set by the command that started the run (`disabled = true`) and cleared again by the `syncTerminal` at the end of the very same submit, so it never actually held. It is `readOnly`, not `disabled`, because a disabled input can't keep focus or see the **Ctrl+C** that interrupts the run.
- **`submitTerminalCommand()` / `handleTerminalKeydown()`** — handle Enter, up/down history navigation (per-session history) and Tab completion (see below). A submit to the busy shell that slips through mid-run (a value typed before the run began) is refused with the engine's `RUN_BUSY` reason rather than run.
- **`runTerminalCommand(command)`** — echoes the command and dispatches it via `CLI_DISPATCH`. If the command stopped another run (a ping preempting a network boot, a traceroute stopping an animation), it collects the engine's note (`takePreemptionNote`) and writes it under the command in this session — unless the interrupted run was this device's own, whose session the engine already wrote it to. It **returns `{ ok, lines }`** — the lines the command itself printed (found by its echo line, so a trimmed scrollback can't misattribute them) and `ok` = none of them is an error line. The preemption note is information, not a failure, and is added after `ok` is decided; only synchronous output counts, so an animated ping's later verdict does not. The console's `cli` verb returns that verdict (review R56).
- **`terminalLine(kind, text)`** — push a line to the active session; **`terminalLineFor(session, …)`** targets a specific one (simulation results go to the *origin device's* session even if another tab is active when the run finishes); **`terminalPromptText(device)`** — the prompt string, per reference NOS: root shells read `root@<name>:~#` (the dnsmasq server and the Snort IDS sensor, which edits `/etc/snort` — it used to fall through to the router's `<name>>`), other hosts `<name>$`, the SONiC switch `<name>#`, the firewall `root@<name>#`, and the router's vtysh prompt follows its CLI mode.
- **`runDeviceCommand(device, command)`** — run a CLI command on a device's terminal **as if the simulator typed it**: surfaces the device's session, echoes the command, dispatches it, and flags the echo + output `injected` (`TerminalLine.injected` → a dark-grey band, distinct from user-typed lines). The inspector uses this so a host's GUI static-config edits (IP/gateway/DNS/MAC) become real, visible Linux commands (`ip addr add …`, `ip route add default via …`, etc.) rather than silent config writes — invalid input fails in the terminal like a real shell.

## Tab completion (Linux host and server shells)

`completeShellLine(device, line)` (`completion.ts`) is pure — no DOM: it completes the last word of the line (the caret is at its end) and returns `{ line, candidates }`, as bash does — one candidate completes with a trailing space, several complete their common prefix, none leaves the line alone. Matching ignores case (device names resolve case-insensitively) and completes to the candidate's own spelling.

The words are **read from the shell's `help`**, never a second list: `shellGrammar(helpLines)` reads each usage line of `hostHelpLines()` (or `serverHelpLines()`, the host lines plus dnsmasq) as a word tree — `ip addr show` → ip → addr → show, `start|stop` giving alternatives — stopping at the first placeholder (`<ipv4>`, `[name]`); literal text in front of a placeholder (`dhcp-range=<start>,…`, `address=/<name>/…`) is a stem, completed without a space. A command whose first non-flag argument is a `<name…>` placeholder takes a **host name** there (the hosts `findPingTarget` resolves — not routers or switches), so `ping`, `traceroute`, `nc [-z]`, `curl`/`wget` (keeping an `http://` in front) and `nslookup` complete names while `hostnamectl set-hostname <name>` does not. Every literal `/path` in the help is a file the shell understands, completed wherever a word starts with `/`. `HOST_COMMAND_ALIASES` (host.ts) adds the spellings the dispatcher accepts but help omits (`tracert`, `host`, `dig`, `wget`, `dhclient`, `route`, `help`), each completing its arguments as its listed twin. Which devices complete is the registry's `host` role (`hostShellHelpLines`): the Kali PC and the Red Team actor get the host commands they fall through to and nothing for `nmap`/`arpspoof`; the router keeps `?` + abbreviation (`ROUTER_COMMANDS`).

The wiring (`completeOnTab` in `core.ts`) respects keyboard reach: **Tab is how a keyboard user leaves the input**, so only a bare Tab is taken, only with text in the input (not just spaces), the caret at its end and no selection, and not while the shell is busy (read-only). An empty line lets Tab move focus as before; Shift+Tab is never taken. A second Tab on the unchanged line echoes the line and prints the candidates (`muted`), leaving the input as it was.

## How it fits

The terminal is a major surface area. The dispatchers parse user input and call the mutators/display helpers; the mutators are shared with `inspector.ts` so CLI and GUI edits are consistent. `ping`/`dhcp` build events via `simulation.ts` and start the run via `engine.startSimulation`. The host shell's animated commands (`ping`/`nc`/`curl`/`dhcp`/`nslookup`) first ask `engine.animatedRunBlockReason()` (`refuseIfRunning`) and print the reason instead of building when another run owns the simulator; `traceroute` is headless, so it stops an animated run in flight instead, and the interrupted run's session says why (see [engine.md](engine.md#run-ownership)). The mutators are unit-tested directly, and the dispatchers + mode machine have their own dispatcher test file. A flow the builder refuses goes through `refuseFlow` (host.ts): the refusal, then a `hint` line where it only reports a symptom (`refusalHint`, [hints.md](hints.md)); a flow that runs and fails gets the same line from the engine when it finishes.


## Router sub-interfaces (router-on-a-stick) from the FRR shell

- **A sub-interface is created by naming it.** `interface Ethernet1.20` on a cabled base creates the tagged entry (`routerBaseOrNewSubInterface` → `routerInterfaceFor(router, peer, 20)`) and enters it, as IOS/FRR do; on an unplugged base it creates the by-name entry (`uncabledSubInterfaceFor`). `encapsulation dot1q N` on a base whose `.N` already exists only selects it — no undo point, since nothing changed. `interface Ethernet1` remains enterable for the **base** even once its sub-interfaces exist (the listing shows only the sub-interfaces then; the base is resolved through them).
- **`encapsulation dot1q N` on the base creates (or selects) the `.N` sub-interface and moves the session onto it** — the base keeps its own untagged identity. On a sub-interface it changes the VLAN that sub-interface carries (its name follows the tag).
- **A VLAN belongs to one sub-interface per port.** `encapsulation dot1q N` on a sub-interface whose sibling already carries VLAN N is refused (`% VLAN 10 is already carried by sub-interface Ethernet1.10 …`, no undo point) — it used to create a second `Ethernet1.10` with another subnet, which could not be selected again and whose `ip address` then overwrote the first (review R40). Re-stating the sub-interface's own VLAN is a no-op with no undo point.
- **`no encapsulation dot1q`** is refused on the base, and on a sub-interface when a base entry already exists (un-tagging would leave two untagged entries for one peer).

Before this, `encapsulation dot1q 10` **retagged the base itself**; afterwards `interface Ethernet1` and `interface Ethernet1.20` were both "Unknown", and a second `encapsulation` on `.10` retagged it rather than creating a second sub-interface — router-on-a-stick, one of the built-in topologies, could not be configured from the router's own terminal. `tests/terminal-commands.test.ts` pins the six-step sequence.


## Group B fixes from the uncovered-modules review

- **Host targets by name resolve like the builders do.** `resolvePingTargetIp` (host.ts) — which sets the address the run's success check compares replies against — now uses `findPingTarget` / `hostnameToIp`. A private copy covered `computer`/`server` only, so `ping <laptop>` (or a Kali / Red Team host) from a PC terminal started a run whose target was the literal name and could never report success although the frames flowed. `nc` and `curl` shared it.
- **`no network` is symmetric with `network`** on the router: the same masking (`192.168.1.5/24` → `192.168.1.0/24`) and the same `<ifname>` form, and a non-member is reported rather than silently ignored. Comparing the unmasked token meant `no network 192.168.1.5/24` could never remove what `network 192.168.1.5/24` had stored.
- **The IDS shell keeps the undo contract.** `echo 'alert …' >> local.rules` (→ `addIdsRule`) and `echo -n > local.rules` push an undo point after validation, like every setter in the other shells.


## P3 sweep (uncovered-modules review)

**A command that changes nothing takes no undo point** (review R88): it used to leave a dead Undo press, clear the redo branch, and sometimes report a change that had not happened. The mutators decide before pushing — `addSwitchVlan` on an existing VLAN with no new name answers `VLAN 10 already exists.` (the SONiC shell prints `Error: Vlan10 already exists`, the console's `vlan … add` stays idempotent so a replayed script is not rejected; with a new name it answers `Renamed VLAN 10 to Sales.`), `removeSwitchVlan` on a missing VLAN is an error (`Error: Vlan999 doesn't exist`), and `setSwitchStp`, `setSwitchPortVlan`/`PortMode`/`TrunkNative`, `modifySwitchTrunkAllowed`, removing a mirror session that does not exist, a host's unchanged `nameserver`, a router's `no ip address` with no address set, and an unchanged `redteam` setting each say the value is already so. The console's `stp <switch> on|off|priority` now goes through `setSwitchStp` like the shell and the inspector.

**Switch shell.** `show runningconfiguration all` is made of lines the shell accepts, so it can be typed back: it opens with `config hostname <name>` (it used to read `hostname <name>`, which the SONiC shell rejects — review R89) and anything that is not a command is a `#` comment. `setSwitchMirror` validates its ports *before* pushing undo, and `config vlan member del` decides membership before pushing — a rejected mirror or a non-member delete no longer leaves a spurious entry (which also wiped the redo stack). `config vlan del N` now clears trunk allow-lists and native VLANs that referenced N, not only access memberships (a trunk kept "carrying" a VLAN that no longer existed). `show runningconfiguration all` names a trunk carrying all VLANs with a comment line — SONiC has no command that expresses "tagged member of everything", so the replayable form could not; emitting nothing replayed the port as access.

**Router shell.** The mode machine holds its edges (review R86): `end` at user exec is refused (it used to hand out privileged mode with no `enable`), `disable` steps privileged back to user exec, `exit` at privileged exec logs out like `exit` at user exec, and `clear ip nat translation *` / `clear ip rip database` run only in the modes the registry and `?` advertise (privileged and config; RIP mode too for the database) — elsewhere they answer `% Privileged mode required. Enter enable first.` or `% Leave the sub-mode first (exit) …`, where they used to run in any mode. `no passive-interface <name>` resolves the name as `passive-interface` does (`routerInterfaceByName`, so `ethernet1` removes what `Ethernet1` stored) and answers `% <name> is not a passive interface on this router.` — with no undo point — when there is nothing to remove; it used to compare the raw token, so a case variant removed nothing yet reported success and took an undo point (review R84). Re-stating an interface that is already passive is a no-op too. `iptables` is refused in interface/rip mode, matching the registry (and `?`); `no ip nat inside source static …` reports "No port-forward" for a rule that does not exist instead of "Removed", and pushes no undo; `passive-interface` validates the interface and stores its canonical name (the RIP send loop compares names exactly); `show running-config` includes the static port-forwards configured in this same mode.
